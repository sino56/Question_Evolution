# 模型请求幂等去重与精确恢复方案

> 版本：v1.0  
> 日期：2026-07-26  
> 状态：方案已确定，尚未实施  
> 上位方案：[模型输入与调用效率后续优化总览](模型输入与调用效率后续优化总览.md)

## 1. 目标

为每一次模型逻辑调用建立稳定身份、状态账本和响应持久化边界，使项目在重复入队、局部失败或进程恢复时优先消费已完成结果，减少重复远端调用和重复计费。

本方案不把不同实验 trial/repeat 合并，也不把相似 prompt 当成同一个请求。

## 2. 需要解决的重复来源

- 同一候选被多个本地任务重复入队；
- 超时或异常发生在“收到响应”和“写入阶段输出”之间；
- 进程退出后只看最终 JSONL，无法判断某个中间请求是否已经完成；
- 批量调用部分成功时，失败重试把成功项一起重跑；
- 写入 `.failed` 或 checkpoint 前后的状态缺少统一请求级边界；
- 本地 retry 和业务层重新执行被混为一谈。

## 3. 幂等边界

### 3.1 可以复用

- 同一 `logical_request_id` 的进程内重复提交；
- 同一逻辑请求的网络重试；
- 同一逻辑请求已经收到并持久化的成功响应；
- 联合调用中已经独立持久化的成功候选项。

### 3.2 不可以复用

- 不同评分 trial；
- 不同 repeat；
- Qwen 决策评分与 GPT 实验评分；
- 不同候选、不同 operator 或不同 frontier；
- model、base URL 身份、temperature、seed、max tokens、schema 或 prompt 版本不同的请求；
- 只是文本相似但业务身份不同的请求；
- 需要独立随机性的多次生成。

因此，内容指纹和逻辑请求身份必须分开：

```text
content_fingerprint = hash(model-visible input + request parameters + versions)

logical_request_id = hash(
  run_id + stage + sample_id + candidate_id + model_role
  + trial_id + repeat_id + generation_index + content_fingerprint
)
```

不同 trial/repeat 即使 `content_fingerprint` 相同，`logical_request_id` 也不同。

## 4. 请求指纹

指纹输入至少包括：

- 模型标识和不含密钥的服务端身份；
- system/user messages 或等价的稳定 prompt；
- temperature、top_p、max tokens、seed 等会影响结果的参数；
- 输入投影版本、prompt 模板版本；
- 输出 schema 和解析协议版本；
- 工具调用定义（若使用）；
- 批量请求中的候选 ID 有序列表。

若服务端支持客户端请求 ID，则发送由 `logical_request_id` 派生的 ASCII `X-Client-Request-Id`，并记录返回的 `x-request-id`。两者用于跨日志追踪和故障定位；除非具体服务端明确承诺幂等语义，否则不能据此跳过本地账本或断言请求只执行了一次。

指纹不得包括：

- API key；
- 本地绝对路径；
- 纯日志时间戳；
- 不影响模型输出的 trace 字段。

## 5. 请求账本

新增 append-only 请求账本，建议每个实验/round 独立存储：

```json
{
  "logical_request_id": "...",
  "content_fingerprint": "sha256:...",
  "run_id": "...",
  "stage": "scoring",
  "sample_id": "...",
  "candidate_id": "...",
  "trial_id": "qwen-2",
  "state": "response_persisted",
  "attempt": 1,
  "provider_request_id": "...",
  "response_ref": "responses/...json",
  "created_at": "..."
}
```

状态机建议为：

```text
planned
  -> queued
  -> submitted
  -> response_received
  -> response_persisted
  -> consumed

任意可重试状态 -> retry_queued
确定失败       -> failed
不再需要       -> abandoned
```

`response_received` 只是内存事实；只有 `response_persisted` 才能在重启后安全复用。

## 6. 持久化顺序

正确顺序：

```text
1. 创建或确认 logical_request_id
2. 账本写 queued/submitted
3. 执行远端调用
4. 将原始响应和必要 usage 原子写入 response sidecar
5. 账本写 response_persisted
6. 解析并写阶段 checkpoint/JSONL
7. 账本写 consumed
```

不能先把账本标成成功再写响应，也不能仅凭 `submitted` 推断请求失败。

响应 sidecar 应沿用现有原子发布和 checkpoint 机制，普通汇总文件只保存引用、hash、usage 和解析结果。

## 7. 进程内合并

维护：

```text
inflight[logical_request_id] -> Future
```

当同一逻辑请求再次入队：

- 若已有在途 Future，则等待同一 Future；
- 若已有 `response_persisted`，直接读取响应；
- 若已有 `consumed` 且目标阶段输出存在，直接跳过；
- 若前一次为可重试失败，按 retry 策略重新排队；
- 若为确定的 schema/config 错误，不自动无限重试。

这只合并完全相同的 `logical_request_id`，不做模糊去重或 embedding 相似度去重。

## 8. 恢复规则

| 恢复时状态 | 处理方式 |
|---|---|
| `planned` / `queued` | 重新入队 |
| `submitted` 且无响应 | 状态不明；按策略重试并记录可能重复 |
| `response_received` 但未持久化 | 无可靠响应，重新调用 |
| `response_persisted` | 不调用模型，重新解析/消费 |
| `consumed` 且阶段输出完整 | 跳过 |
| `failed` | 根据错误分类决定终止或人工重试 |
| `abandoned` | 默认不恢复，除非业务重新生成新的逻辑 ID |

必须明确一个现实限制：若服务端已完成请求，但本地在收到或落盘前崩溃，而服务端又不支持可查询的 request ID/idempotency key，则无法严格证明没有重复计费。此时只能记录 `submitted_unknown` 风险并重试，不能宣称 exactly-once；本方案提供的是“已持久化结果不重复消费”和“可识别边界内的 at-most-once 复用”。

## 9. 错误分类与缓存

### 9.1 可重试

- 429；
- 连接失败；
- 读取超时；
- 明确的 5xx；
- 服务端临时不可用。

这些错误不写永久负缓存。

### 9.2 默认不可重试

- 无效鉴权；
- 不支持的模型或参数；
- 请求超过确定的上下文限制；
- 本地 schema 配置错误。

不可重试失败只能在请求参数、版本或人工 retry generation 变化后重新执行。

### 9.3 解析失败

原始响应已持久化但解析失败时，优先在本地用新解析器重放；若协议允许现有 repair 调用，则 repair 是新的逻辑请求，并关联原请求 ID，不能覆盖原响应。

## 10. 批量调用的特殊处理

一次联合验证请求包含多个候选时：

- 外层有一个 batch logical request ID；
- 每个候选有独立 item ID 和解析状态；
- 原始 batch 响应先整体持久化；
- 成功解析的 item 立即写 item checkpoint；
- 只对缺失或失败 item 生成新的单候选 fallback 请求；
- 不因一个 item 失败而重跑整个成功 batch。

## 11. 配置与文件建议

```text
MODEL_REQUEST_LEDGER_ENABLED=false
MODEL_REQUEST_DEDUPE_ENABLED=false
MODEL_RESPONSE_SIDECAR_ENABLED=false
MODEL_REQUEST_RESUME_MODE=legacy|ledger_v1
MODEL_REQUEST_UNKNOWN_SUBMISSION_POLICY=retry_and_mark
```

建议代码落点：

- 新增 `model_request_ledger.py`：ID、状态机、append-only ledger、索引恢复；
- `pipeline_runtime.py`：统一请求包装、inflight Future 合并、原子响应持久化；
- 各模型调用脚本只提供业务标识、输入和解析函数；
- `multi_operator_search.py`、`vertical_operator_search.py`：恢复时从账本重建未完成请求；
- manifest 记录账本版本、请求配置和恢复策略。

启用 ledger 模式时，所有 OpenAI-compatible 客户端应关闭 SDK 内建自动重试，由请求包装层统一增加 `attempt`、释放/重取全局 permit 并执行退避。否则一个表面上的调用可能包含多个未记账的实际 HTTP attempt。

不得把完整 API key 写入指纹、ledger、sidecar 或错误日志。

## 12. 测试方案

### 12.1 单元测试

- 同一 logical request 并发入队只触发一次 mock API；
- 不同 trial/repeat 必须触发独立 API；
- 模型参数、prompt 版本或 schema 变化会产生新 ID；
- 429 重试沿用 logical ID，但 attempt 增加；
- response sidecar 原子写入后才能进入 `response_persisted`；
- 解析失败可从 sidecar 本地重放；
- transient error 不进入永久负缓存；
- 日志和 ledger 不包含密钥。

### 12.2 故障注入

分别在以下位置强制退出并恢复：

1. 入队前；
2. submitted 后、远端返回前；
3. 收到响应后、sidecar 写入前；
4. sidecar 写入后、阶段 JSONL 写入前；
5. 阶段 JSONL 写入后、consumed 标记前；
6. 联合调用只解析部分 item 后。

验证已持久化结果不再次调用，状态不明请求会被明确标记，部分成功不会整体重跑。

## 13. 验收标准

1. 同一进程内同一逻辑请求最多发起一次并发远端调用；
2. 已达到 `response_persisted` 的请求恢复时零重复调用；
3. 不同 trial/repeat、模型角色和候选不会被误合并；
4. 所有失败恢复路径保留现有 `.failed` 非零退出要求；
5. 批量部分失败只回退失败项；
6. 能量化报告逻辑请求数、实际请求数、复用数和状态不明重试数；
7. 文档和指标不宣称服务端不支持条件下的严格 exactly-once。

## 14. 风险与回退

- 指纹缺字段会误复用，因此初版宁可少复用，也不能跨业务身份复用。
- ledger 索引损坏不能阻塞原始 append-only 数据读取，应可重建索引。
- sidecar 增加小文件数量，可按 round 分片，但不能牺牲原子边界。
- 启用前先只记录 shadow ledger，不进行结果复用；核对 ID 稳定后再开启 dedupe。
- 任一异常可关闭复用，继续使用现有 checkpoint/partial 路径。
