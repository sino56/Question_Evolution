# 模型输入与调用效率后续优化总览

> 版本：v1.0  
> 日期：2026-07-26  
> 状态：方案已确定，尚未实施  
> 前置方案：[树搜索共享前缀与输入复用优化方案](树搜索共享前缀与输入复用优化方案.md)

## 1. 背景

现有方案已经覆盖树搜索阶段的共享前缀整理、输入复用和同父节点生成小批次合并。继续优化时，约束调整为：

1. 不改模型服务端和模型推理实现，不能依赖 KV cache 分叉、Paged Attention、服务端 prefix cache 等能力。
2. 只优化传给模型的内容，以及项目内模型请求的组织、调度、恢复和合并方式。
3. 全项目任意时刻实际在途的模型请求总数不得超过 20；不能把“每个模块 20”误当成“全局 20”。
4. 不改变 question evolution 主流程、候选分流语义、Qwen 决策评分和 GPT 实验评分的职责。
5. 不通过减少评分 trial、repeat 或候选真实评分数量来伪造吞吐收益。

现有优化之后，剩余开销主要来自四类问题：

- 不同阶段仍携带与当前任务无关的完整对象或历史字段；
- 多个阶段各自维护并发池，缺少跨阶段的统一上限、优先级和公平调度；
- 进程中断、超时边界和重复入队可能导致同一个逻辑请求被再次提交；
- 验证阶段仍以候选为单位独立发送高度相似的指令。

因此，本轮不再扩展生成阶段的共享前缀方案，而是拆成四个可独立灰度、独立回滚的专项方案。

## 2. 方案组成

| 顺序 | 专项方案 | 核心收益 | 是否改变业务判断 |
|---|---|---|---|
| 1 | [全链路模型输入裁剪与阶段字段投影方案](全链路模型输入裁剪与阶段字段投影方案.md) | 减少每次请求的输入 token 和序列化开销 | 否 |
| 2 | [全局模型调用调度与20并发配额方案](全局模型调用调度与20并发配额方案.md) | 在硬上限 20 内提升利用率、降低队首阻塞 | 否 |
| 3 | [模型请求幂等去重与精确恢复方案](模型请求幂等去重与精确恢复方案.md) | 减少崩溃恢复和重复入队造成的重复调用 | 否 |
| 4 | [候选验证小批量联合调用方案](候选验证小批量联合调用方案.md) | 合并重复验证指令，降低验证调用数 | 否；候选结论仍独立 |

四个方案的职责边界如下：

```text
阶段字段投影
  负责“单个逻辑请求应该携带什么”
          ↓
全局调用调度
  负责“何时提交、谁先提交、最多提交多少”
          ↓
幂等与精确恢复
  负责“这个逻辑请求是否已经完成、能否安全复用结果”
          ↓
验证小批量联合调用
  负责“多个独立验证请求能否共享一次固定指令输入”
```

## 3. 统一设计原则

### 3.1 语义不变优先

- 字段裁剪只能删除当前阶段不消费的信息，不能总结、改写或压缩题目、参考答案、rubric 中的事实。
- 调度只改变执行顺序和资源分配，不能改变候选选择、评分聚合和停止条件。
- 幂等复用以“同一个逻辑调用”为边界；不同 trial 或 repeat 即使输入文本相同，也必须视为不同实验调用。
- 联合验证只共享静态指令，不允许候选间比较、排名或生成组级结论。

### 3.2 全局并发硬约束

统一定义：

```text
global_inflight_model_requests <= 20
```

这里的在途请求指已经取得调用配额、正在执行一次实际远端模型调用的请求。排队任务、重试退避和本地解析不占用该配额。

若以后确实存在互不共享限额的多个服务端配额域，可以为每个域设置更小的子上限；所有域合计仍默认不得超过 20，除非用户明确修改本项目约束。

### 3.3 可观测、可灰度、可回滚

所有专项都应：

- 默认保留 legacy 路径；
- 记录版本号和开关值；
- 使用同一批样本做 A/B；
- 单次实验只启用一个主要变量；
- 失败时可按阶段回退，不要求迁移历史 JSONL；
- 不把完整私有 prompt、模型回答或 API 凭据写入普通日志。

## 4. 暂不纳入本轮的优化

以下方向暂不进入本轮实施范围：

1. 模型侧 KV cache、prefix cache、continuous batching、投机解码等推理服务优化。
2. 通过降低 trial、repeat、评分模型数或探索预算减少调用量。
3. 根据中间分数动态减少真实评分次数的 sequential testing。
4. 使用小模型替代 Qwen 决策评分或 GPT 实验评分。
5. 把 reference answer、rubric、answer collection、judge scoring 合并进同一个大请求。
6. 为吞吐量引入完整 BFS、DFS、UCB 或复杂分布式任务系统。

其中第 2～4 项可能有效，但会改变实验统计口径或决策语义，应另立实验方案，不与本轮纯工程优化混测。

## 5. 推荐实施顺序

### 阶段 A：建立统一基线

先补齐以下指标，不改变运行逻辑：

- 每阶段逻辑请求数、实际远端请求数；
- 输入/输出 token，无法取得 token 时记录字符数估算；
- 排队时间、服务时间、重试次数和错误类型；
- 全局与分阶段在途请求峰值；
- `sample_id`、`candidate_id`、stage、model、trial/repeat 维度的调用追踪；
- 吞吐、P50/P95 延迟和每个有效候选的模型成本。

### 阶段 B：输入字段投影

先从 `profile_samples.py`、`question_evolution.py` 和两个 validator 开始，再覆盖 answer、rubric、scoring。该阶段风险最低，也为后续指纹和联合调用提供稳定输入格式。

### 阶段 C：全局调度

将各模块私有信号量或请求池接入统一调度器，首先只启用硬上限与公平队列；优先级、动态有效并发和 token 权重随后单独灰度。

### 阶段 D：幂等与精确恢复

在输入版本和调度接口稳定后加入逻辑请求 ID、请求账本和响应落盘点，避免恢复时重复计费。

### 阶段 E：验证小批量联合调用

最后只对验证阶段做 2 个候选的小批量试验。确认映射、解析和质量稳定后，再评估是否允许最大批次 3。

## 6. 总体验收指标

必须同时观察效率和质量，不能只看调用数。

### 6.1 正确性护栏

- 全局模型请求峰值始终不超过 20；
- Qwen 决策结果和 GPT 实验结果仍分开记录；
- trial/repeat 数量与基线一致；
- `hard_reject`、`main_chain_candidate`、`exploration_candidate`、`pass_through_candidate` 语义不变；
- `score_increased` 仍表示负收益，不进入成功终止态；
- 旧 JSONL 在缺少新增字段时仍可走 fallback；
- 中断恢复不丢失已经持久化的候选结果。

### 6.2 效率指标

- 分阶段输入 token/字符数下降；
- 实际远端请求数相对逻辑请求数的重复率下降；
- 全局并发槽利用率提升，同时 429/超时不恶化；
- 验证批量模式下单位候选的请求数和总输入 token 下降；
- 端到端 wall time 和每个有效候选成本下降。

### 6.3 质量指标

- 关键结构化字段解析成功率不下降；
- 候选分流和难度增益结论与基线保持可接受的一致性；
- 最终真实 score drop、有效边界命中率和候选多样性不劣化；
- 不因为调度顺序改变而污染同一 frontier 的 memory 视图。

## 7. 统一完成标准

本组方案只有在以下条件全部满足后才能标记为“已实施”：

1. 四个专项分别有实现开关、指标和回滚路径；
2. 全局并发 20 的约束有压力测试证明，而不是仅靠配置约定；
3. 新旧输入在固定样本集上完成语义等价或非劣验证；
4. 中断点恢复测试证明不会重复消费已持久化结果；
5. 联合验证的每个候选仍能单独解析、单独失败和单独回退；
6. `pytest -q` 通过，并完成 3～5 条样本的真实小规模试跑；
7. 端到端收益单独报告，不能用某一阶段的局部加速替代全链路结论。

## 8. 调研依据与项目取舍

本方案参考了以下一手资料，但只采用与当前项目约束相符的客户端工程措施：

- OpenAI API 会返回 request/token 两类限流信息，并支持服务端 `x-request-id` 和客户端 `X-Client-Request-Id`。因此调度指标同时保留请求数与 token 估算，账本同时记录逻辑 ID、客户端请求 ID 和服务端请求 ID；客户端请求 ID 只用于追踪，不能被当成服务端幂等保证。[OpenAI API reference](https://platform.openai.com/docs/api-reference/backward-compatibility)
- OpenAI Python SDK 默认会对连接错误、408、409、429 和 5xx 等错误自动重试。为了让 permit、退避和 attempt 全部由项目统一观测，全局调度模式下应显式关闭 SDK 内建重试，再由项目请求包装层执行已有重试策略。[OpenAI Python SDK](https://github.com/openai/openai-python#retries)
- 支持 JSON Schema 的模型可以使用 Structured Outputs 提高结构化解析稳定性；本项目仍保留严格 JSON 和本地解析 fallback，以兼容 OpenAI-compatible 服务。[OpenAI Structured Outputs reference](https://platform.openai.com/docs/api-reference/evals/deleteRun)
- OpenAI Batch API 使用每请求 `custom_id` 做输入输出映射，但当前完成窗口为异步 24 小时，适合离线任务而不适合树搜索关键路径。本方案只借鉴稳定 ID 和逐项映射思想，不接入该离线接口。[OpenAI Batch API](https://platform.openai.com/docs/api-reference/batch/object)
- HTTP 规范不保证普通 POST 天然幂等，并指出语义不明的非幂等请求不应被盲目自动重试。因此请求账本明确保留 `submitted` 后状态不明的窗口，不宣称客户端可实现严格 exactly-once。[RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)
