# 全链路模型输入裁剪与阶段字段投影方案

> 版本：v1.0  
> 日期：2026-07-26  
> 状态：方案已确定，尚未实施  
> 上位方案：[模型输入与调用效率后续优化总览](模型输入与调用效率后续优化总览.md)

## 1. 目标

在不改变题目、参考答案、rubric 和评分语义的前提下，为每个模型调用阶段定义最小、稳定、可测试的输入投影，减少重复字段、历史状态和阶段无关信息造成的输入 token 开销。

本方案解决的是“每个模型请求传什么”，不负责并发调度、请求幂等和多候选合并。

## 2. 当前问题

当前各阶段主要由调用点临时拼装 prompt。已有实现能够工作，但存在以下扩展性问题：

1. `profile_samples.py` 会把较完整的 `meta_info` 交给画像模型，后续新增搜索字段时可能被无意带入。
2. `question_evolution.py` 同时消费题目、答案、rubric、画像、诊断、进化状态和 operator route，缺少明确的字段白名单和历史截断边界。
3. validator、reference、rubric、answer、scoring 各自持有相似但未统一版本化的输入构造逻辑。
4. 完整试次结果、兄弟节点、搜索轨迹和调试信息可能随着 JSONL 结构扩展进入不需要它们的阶段。
5. 输入格式没有统一指纹，难以准确衡量字段投影收益，也不利于后续幂等恢复。

## 3. 非目标

- 不对题目正文、参考答案或 rubric 做 LLM 摘要。
- 不删除影响模型判断的事实、限定条件和评分标准。
- 不改变 operator 的能力轴和输出协议。
- 不减少评分 trial、repeat 或实验模型调用。
- 不依赖服务端 token cache 或 KV cache。
- 不把多个业务阶段拼成一个超大 prompt。

## 4. 核心设计

### 4.1 阶段字段投影器

新增统一的纯函数式投影层，例如：

```text
source JSONL record
  -> project_profile_input(...)
  -> project_evolution_input(...)
  -> project_question_validation_input(...)
  -> project_difficulty_validation_input(...)
  -> project_reference_answer_input(...)
  -> project_rubric_input(...)
  -> project_answer_collection_input(...)
  -> project_scoring_input(...)
```

投影器只做：

- 字段白名单选择；
- 已定义的空字段省略；
- 稳定排序和稳定序列化；
- 有明确上限的历史条目选择；
- 类型归一化；
- 输入版本和指纹生成。

投影器不做：

- 自由文本总结；
- 事实改写；
- 基于内容“猜测”字段是否重要；
- 调用模型补全缺失上下文。

### 4.2 公共信封

每个投影结果使用统一信封，但不要求写回主 JSONL 顶层：

```json
{
  "input_projection_version": "profile_v1",
  "stage": "profile",
  "sample_id": "sample-001",
  "candidate_id": null,
  "payload": {},
  "input_fingerprint": "sha256:..."
}
```

`input_fingerprint` 只对稳定序列化后的模型可见输入和协议版本求 hash。普通日志只记录 hash、长度和版本，不记录完整 prompt。

## 5. 各阶段字段边界

### 5.1 样本画像 `profile`

必需输入：

- `prompt`；
- 当前选定的 `reference_answer`；
- 当前代表性候选答案或代表性 round0 答案；
- 稳定后的 `score_rate` 和必要的评分摘要；
- 对画像确有影响的最小 `meta_info` 白名单。

禁止默认携带：

- 完整 `round0_score_trials`；
- 所有原始评分响应；
- 搜索分支、兄弟节点、operator memory；
- trace、checkpoint、manifest 和调试字段；
- 未列入白名单的整个 `meta_info`。

建议将画像需要的元信息显式列为 `PROFILE_META_FIELDS`，默认空集合或仅保留当前 prompt 明确使用的键。

### 5.2 问题进化 `evolution`

必需输入：

- 当前节点 `prompt`；
- 当前有效 `reference_answer`；
- 当前代表性候选答案；
- 当前有效 rubric；
- `sample_profile` 和 `overscore_diagnosis` 中 prompt 实际引用的字段；
- 当前 `operator_route`、当前 operator 和当前节点复杂度预算；
- 与当前 operator 直接相关的失败记忆或边界证据。

有界历史规则：

- 只保留当前父节点路径上最近且相关的失败证据；
- 默认按“同 operator + 同失败形态”选取最多 `K` 条，`K` 初始建议为 3；
- 不把完整 `evolution_state`、全部 operator memory、全部兄弟节点或历史模型原文直接注入；
- 若字段裁剪可能影响旧 prompt，先在 legacy/projected 双轨下验证，再切换默认值。

### 5.3 进化题合法性验证 `question_validation`

必需输入：

- 原题和进化题；
- 当前 operator 标识及验证规则所需的最小元数据；
- 当前结构化输出 schema 版本。

禁止默认携带：

- 候选答案、完整 rubric 和评分试次；
- 兄弟候选的内容和结论；
- 完整搜索轨迹、memory bank 和下游评分结果。

本地可确定的格式、空值和 hard-risk 检查应在模型调用前执行，但不得新增更严格的拒绝语义。

### 5.4 难度增益验证 `difficulty_validation`

必需输入：

- 原题和进化题；
- 当前难度增益判断协议；
- 与难度变化直接相关的最小 operator 元数据；
- 如现有 prompt 确实消费，则保留必要的画像或诊断摘要字段。

禁止默认携带完整历史评分、兄弟候选和无关元信息。弱探测属于独立逻辑调用，不与难度验证投影混合。

### 5.5 参考答案生成 `reference_answer`

只输入最终待作答题目、回答协议和必要领域约束。树路径、operator、候选选择原因、父节点分数和兄弟候选均不应进入。

### 5.6 Rubric 生成 `rubric`

只输入最终题目、当前参考答案和 rubric 生成规则。不得携带树搜索状态、候选排名、operator 成败记录或评分模型历史回答。

### 5.7 答案采集 `answer_collection`

只输入最终题目和回答约束。若模型接口需要 system prompt，则固定为版本化模板；不得把参考答案、rubric、树路径或候选结论泄漏给答题模型。

### 5.8 评分 `scoring`

只输入版本化 `score_prompt`、当前单次候选答案及现有评分协议明确要求的内容。

必须保持：

- 一次 trial/repeat 对应一个独立逻辑评分请求；
- Qwen 决策评分与 GPT 实验评分分别构造、分别记录；
- 不因字段投影合并不同候选答案或复用不同 trial 的结果。

## 6. 稳定序列化规则

为了让 token 统计、指纹和 A/B 可复现：

1. JSON 对象键按固定顺序输出；
2. 未提供字段与显式 `null` 的语义由 schema 固定，不能随调用点变化；
3. 空数组、空对象只有在 prompt 不区分时才省略；
4. 数值、布尔值不转成自然语言同义表达；
5. 模板说明、schema 和示例使用明确版本号；
6. 不在稳定输入中加入时间戳、随机 UUID 或本地绝对路径；
7. 记录 `input_chars`，能从响应取得 usage 时再记录 `input_tokens`。

## 7. 配置与兼容

建议配置：

```text
MODEL_INPUT_LAYOUT=legacy|projected_v1
PROFILE_INPUT_PROJECTION_ENABLED=false
EVOLUTION_INPUT_PROJECTION_ENABLED=false
VALIDATION_INPUT_PROJECTION_ENABLED=false
REFERENCE_INPUT_PROJECTION_ENABLED=false
RUBRIC_INPUT_PROJECTION_ENABLED=false
ANSWER_INPUT_PROJECTION_ENABLED=false
SCORING_INPUT_PROJECTION_ENABLED=false
EVOLUTION_RELEVANT_MEMORY_LIMIT=3
```

兼容规则：

- 新字段优先进入 trace/manifest 或现有阶段元数据，不要求历史数据迁移；
- 缺少投影版本时按 legacy 构造；
- 投影失败时允许按样本回退 legacy，但必须记录回退原因；
- 禁止静默删掉 schema 标记为 required 的字段。

## 8. 建议代码落点

- 新增 `model_input_projection.py`：阶段 schema、投影函数、稳定序列化和指纹。
- `profile_samples.py`：用 `project_profile_input` 替代直接传完整对象。
- `question_evolution.py`：复用现有共享上下文，增加有界历史投影。
- `validate_evolved_question.py`、`validate_difficulty_gain.py`：使用各自验证投影。
- `collect_answers.py`、`gen_rubric.py`、`scoring.py`：显式建立最小输入。
- `pipeline_runtime.py`：统一记录输入长度、版本和 fingerprint，不记录秘密内容。

实现时不改变这些文件的输出字段语义，也不调整 `run_loop.sh` 的阶段顺序。

## 9. 测试方案

### 9.1 单元测试

- 每个阶段 required 字段完整；
- 黑名单字段不会进入模型可见输入；
- 字段顺序变化不改变 fingerprint；
- prompt、reference、rubric 任一事实变化都会改变 fingerprint；
- legacy 数据缺字段时 fallback 正常；
- 不同 trial/repeat 的逻辑标识不会被投影层吞掉；
- 空值省略规则与 schema 一致；
- 普通日志中不存在完整 prompt 或 API key。

### 9.2 Golden 测试

为每个阶段准备 3～5 条固定样本，同时保存：

- legacy 模型可见输入；
- projected_v1 模型可见输入；
- 字段差异；
- 字符/token 差异；
- 结构化输出解析结果。

任何模板版本变化都必须显式更新 golden，不能自动覆盖。

### 9.3 真实 A/B

固定样本、模型、temperature、trial/repeat 和其他搜索配置，只切换输入投影开关，比较：

- 输入 token 中位数及 P95；
- 解析成功率；
- validator 标签一致率；
- 候选分流结果；
- 最终 score drop 和有效边界命中率；
- 端到端耗时与成本。

## 10. 验收标准

1. 所有模型阶段都有显式字段白名单和版本；
2. required 字段零遗漏，禁止字段零泄漏；
3. eligible 阶段的输入 token 中位数应有可测下降，建议以 15% 作为继续推广的观察目标，而非强制质量让步线；
4. 结构化解析成功率不低于基线；
5. 候选分流、真实评分和停止语义无系统性漂移；
6. 旧数据和 legacy 路径可运行；
7. 若某阶段节省不足以抵消维护复杂度，应保留 legacy，不强制启用投影。

## 11. 风险与回退

最大风险不是解析失败，而是删掉模型判断所需的隐含上下文。控制措施：

- 先建立字段读取清单，再实现白名单；
- 首轮只删明确的 trace、完整历史和阶段无关字段；
- 题目、参考答案、rubric 不做有损压缩；
- 按阶段灰度，发现质量漂移只回退对应阶段；
- 将输入版本写入实验 manifest，保证结果可追溯。
