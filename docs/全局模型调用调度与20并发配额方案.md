# 全局模型调用调度与 20 并发配额方案

> 版本：v1.0  
> 日期：2026-07-26  
> 状态：方案已确定，尚未实施  
> 上位方案：[模型输入与调用效率后续优化总览](模型输入与调用效率后续优化总览.md)

## 1. 目标

把当前分散在画像、进化、验证、答案、rubric 和评分模块中的请求并发控制，收敛为一个项目级模型调用调度器。在全局实际并发硬上限 20 内，通过公平队列、优先级借用、动态补位和可选的自适应有效并发，提高槽位利用率并降低关键搜索路径等待时间。

本方案只改变请求何时取得调用资格，不改变请求内容和业务结论。

## 2. 当前问题

现有实现已经有 `asyncio.Semaphore`、`FairRequestPool`、有界 worker/queue 和横向分支动态补位，但并发控制仍主要位于单个脚本或单次 runner 内：

- 某个模块配置 20，只能保证该模块不超过 20；
- Qwen、GPT 或多个阶段同时运行时，缺少统一的项目级峰值证明；
- 每个请求按一个槽计数，长 prompt 可能长期占用资源并造成短请求排队；
- 决策链请求与实验性请求缺少统一优先级和借用规则；
- 纵向搜索的样本/frontier 外层仍可能串行，不能充分利用空闲配额；
- 各模块指标难以汇总成一条全链路排队与利用率视图。

## 3. 硬约束与非目标

### 3.1 硬约束

```text
GLOBAL_MODEL_CONCURRENCY = 20
global_inflight_model_requests <= 20
```

- 20 是项目级实际远端调用上限，不是每个 stage、model 或 worker 的上限。
- 重试等待、JSON 解析、本地 validator、文件读写不占用调用槽。
- 每次实际 HTTP 模型请求开始前必须取得全局 permit，并在请求完成或抛错后释放。

### 3.2 非目标

- 不实现分布式集群调度器。
- 不改服务端 batching 或 KV cache。
- 不减少评分 trial/repeat。
- 不让低优先级任务永久饥饿。
- 不通过取消已经提交的有效请求来制造速度提升。

## 4. 调度对象

统一请求描述建议为：

```json
{
  "logical_request_id": "...",
  "stage": "difficulty_validation",
  "sample_id": "sample-001",
  "candidate_id": "candidate-002",
  "frontier_id": "frontier-003",
  "model_role": "qwen_decision",
  "quota_domain": "default",
  "priority_lane": "P0",
  "estimated_input_tokens": 3200,
  "estimated_output_tokens": 500,
  "attempt": 1
}
```

其中 `logical_request_id` 由幂等方案定义；调度器不能根据 prompt 文本自行合并请求。

## 5. 调度架构

### 5.1 两级限制

第一级是不可突破的请求数限制：

```text
hard_request_permits = 20
```

第二级是可选的软 token 在途窗口：

```text
estimated_tokens_inflight <= MODEL_TOKEN_INFLIGHT_LIMIT
```

初版只启用第一级。只有指标证明长短请求混跑存在明显队首阻塞后，才启用 token 窗口。token 估算误差不能导致突破 20 个请求的硬限制。

### 5.2 优先级通道

建议初始定义：

| 通道 | 任务 | 初始保留槽位 |
|---|---|---:|
| P0 搜索关键路径 | question evolution、题目验证、难度验证、Qwen 决策评分 | 12 |
| P1 主流程补全 | reference answer、rubric、answer collection、必要的普通评分 | 6 |
| P2 实验与后台 | GPT 实验评分、非阻塞分析 | 2 |

这不是固定分割，而是可借用的软保留：

- 某通道无任务时，空闲槽可被其他通道借用；
- 新的高优先级任务只等待现有请求自然完成，不强杀已提交请求；
- P2 通过 aging 获得逐步提升，避免长期饥饿；
- 槽位配置必须写入 manifest，不能隐藏在代码常量里。

### 5.3 同级公平性

同一优先级内采用分层轮询：

```text
priority lane
  -> sample_id round-robin
  -> frontier/parent round-robin
  -> stage FIFO
```

并设置单样本在途软上限，防止一个大树占满 20 个槽。初始建议 `MAX_INFLIGHT_PER_SAMPLE=4`，但它是可配置的公平性参数，不是业务分支预算。

### 5.4 动态补位

任何请求释放 permit 后，调度器立即从当前可运行队列选择下一项，不等待同一批次全部结束。现有横向分支动态补位应接入该接口；纵向搜索可把不同样本的可运行 frontier 放入全局任务队列，而不是在外层逐样本等待。

同一 frontier 的决策应冻结其 `memory_version` 和父节点输入视图。后完成的其他分支只能影响下一 frontier，避免并发完成顺序改变实验语义。

## 6. 自适应有效并发

硬上限始终为 20，但有效上限可以在 1～20 内变化：

```text
1 <= effective_concurrency <= 20
```

初始实现建议默认关闭。启用时采用保守的 AIMD：

- 连续成功且 P95 延迟稳定：每个观察窗口增加 1；
- 发生 429、明显超时或服务端过载错误：有效并发按比例下降；
- 鉴权、schema 或业务解析错误不触发并发下降；
- 恢复速度慢于下降速度；
- Qwen/GPT 如共享同一服务端配额，必须共用反馈；若证明确属独立配额域，可分别维护子反馈，但仍受全局 20 限制。

该机制优化的是服务稳定性，不得用“降低有效并发”掩盖错误配置。

## 7. 重试、取消与超时

### 7.1 重试

- 一次 HTTP 尝试占用 permit；
- 请求失败后先释放 permit，再执行退避；
- 到达重试时间后重新入队，不能在睡眠期间占槽；
- 重试保持同一 `logical_request_id`，但增加 `attempt`；
- 业务级新 trial/repeat 使用新的逻辑请求 ID。

当前使用的 OpenAI Python SDK 默认包含内部自动重试。启用全局调度器时，应把所有受管客户端统一设为 `max_retries=0`，再由项目级请求包装器执行重试；否则 SDK 内部退避会持续占用 permit，实际 attempt 也无法完整进入账本。关闭 SDK 重试不能减少现有重试次数，只是把重试控制权移到项目层。

### 7.2 取消

当样本已经达到终止条件或候选不再需要时：

- 尚未提交的 queued 请求可标记为 cancelled；
- 已提交请求默认等待完成并记录结果；
- 只有模型客户端明确支持安全取消且不会造成结果状态不明时，才允许取消在途请求；
- 已完成但不再消费的响应仍应写入 trace，避免恢复时重复调用。

### 7.3 超时

连接超时、读取超时和全任务 deadline 分开记录。超时后是否重试由现有重试策略决定，不由优先级决定。

## 8. 配置建议

```text
GLOBAL_MODEL_SCHEDULER_ENABLED=false
GLOBAL_MODEL_CONCURRENCY=20
GLOBAL_MODEL_EFFECTIVE_CONCURRENCY=20
GLOBAL_MODEL_ADAPTIVE_CONCURRENCY=false
GLOBAL_MODEL_MIN_EFFECTIVE_CONCURRENCY=1
GLOBAL_MODEL_MAX_INFLIGHT_PER_SAMPLE=4
GLOBAL_MODEL_P0_RESERVED=12
GLOBAL_MODEL_P1_RESERVED=6
GLOBAL_MODEL_P2_RESERVED=2
GLOBAL_MODEL_STARVATION_SECONDS=60
MODEL_TOKEN_INFLIGHT_LIMIT=0
```

启动时必须校验 `1 <= GLOBAL_MODEL_CONCURRENCY <= 20`。超过 20 应直接报错退出，不能静默接受；低于 20 允许用于灰度或适配更小的外部配额。

`PROFILE_CONCURRENCY`、`EVO_CONCURRENCY`、validator workers 和 scoring workers 继续表示本地 worker 数或阶段排队能力，不再直接代表实际远端并发上限。

## 9. 建议代码落点

- 在 `pipeline_runtime.py` 扩展 `FairRequestPool`，或新增 `model_call_scheduler.py`；优先保留现有上下文管理接口，降低迁移成本。
- 统一为模型客户端注入 scheduler，禁止模块内部再创建互不感知的 20 槽请求池。
- `profile_samples.py`、`question_evolution.py`、两个 validator、`collect_answers.py`、`gen_rubric.py`、`scoring.py` 的实际 API 调用前统一申请 permit。
- `multi_operator_search.py` 复用全局 scheduler，不分别创建互相独立的 GPT/Qwen 全局池。
- `vertical_operator_search.py` 增加跨样本可运行 frontier 队列，但保持单个 frontier 的输入视图冻结。
- `run_loop.sh` 统一传入全局配置并写入 manifest。
- 所有 `AsyncOpenAI` 客户端在 scheduler 模式下显式设置 `max_retries=0`；API key 切换也应释放 permit 后作为同一逻辑请求的新 attempt 重新排队。

若各阶段仍以独立进程由 shell 串行启动，进程内单例足够；若未来出现多个阶段进程重叠运行，则必须使用跨进程 semaphore/协调服务，不能继续声称进程内对象提供项目级上限。

## 10. 指标

必须记录：

- `global_inflight_current`、`global_inflight_peak`；
- 各 priority lane 的 queued/running/completed/cancelled；
- 排队时间、服务时间、端到端时间；
- 按 stage/model/sample 的 permit 占用；
- 槽位利用率和 work-conserving 借用次数；
- 429、timeout、retry 和 adaptive limit 变化；
- token 估算值与实际 usage 的偏差；
- 因终止条件取消的未提交请求数。

## 11. 测试方案

### 11.1 调度器单元测试

- 100 个混合请求压力下峰值永不超过 20；
- P0/P1/P2 空闲槽可以互借；
- P2 在持续 P0 流量下不会永久饥饿；
- 单个样本不能长期占满所有槽；
- permit 在成功、异常、取消和超时路径都被释放；
- 重试退避期间不占槽；
- adaptive limit 永远在 1～20；
- token 软窗口关闭时不改变现有行为。

### 11.2 集成测试

- 混合运行 evolution、validation 和 scoring，证明全局峰值不超过 20；
- Qwen 决策任务不会被大量 GPT 实验任务阻塞至饥饿；
- frontier memory 版本不受完成顺序影响；
- legacy scheduler 关闭时行为与当前实现一致；
- 中断恢复后 queued/running 状态能与请求账本正确衔接。

### 11.3 性能试跑

使用固定 3～5 条样本，比较：

- 端到端 wall time；
- 全局槽位平均利用率；
- P50/P95 排队时间；
- 429/timeout/retry；
- 各阶段完成顺序和最终结果一致性。

## 12. 验收标准

1. 压力测试和真实试跑中 `global_inflight_peak <= 20`；
2. 所有模型实际调用均经过统一 permit，代码审查中不存在旁路；
3. 重试等待不占槽，异常路径无 permit 泄漏；
4. 关键路径等待时间不高于基线，低优先级无永久饥饿；
5. 候选选择、评分次数、终止条件和 JSONL 字段语义不变；
6. 若自适应并发导致吞吐或稳定性变差，可单独关闭而不回退全局硬上限。

## 13. 风险与回退

- 优先级设计错误可能饿死后台任务，因此必须有 aging 和队列等待指标。
- 跨样本并行可能让 memory 更新顺序不稳定，因此必须冻结 frontier 视图。
- token 估算不准可能降低利用率，因此初版不启用 token 软窗口。
- 全局调度器故障影响面较大，必须保留 legacy 路径并分阶段接入。
- 若实际运行一直是严格串行阶段，全局调度的主要收益会来自搜索内部公平性而非跨阶段重叠；验收应如实报告。
