# 纵向算子叠加方案

文档状态：工程实现与自动化验收已完成（2026-07-26）；正式真实样本实验待准入数据
制定日期：2026-07-20
适用范围：Question Evolution 纵向搜索与算子叠加探索阶段
前置基础：基于父节点的多算子横向分支搜索
目标读者：负责流水线、搜索调度、数据结构、预算控制和实验验收的工程师

## 1. 方案摘要

本方案是在"以父节点为中心的多算子横向分支搜索"基础上的后续优化任务。横向搜索解决的是：同一个已评分父节点上，不再只选择一个算子候选进入完整闭环，而是让多个适合算子分别形成分支并接受完整评分。

纵向算子叠加进一步解决的是：当某个算子分支已经让题目分数下降时，不立即把该分支视为在线搜索终点，而是允许该降分子节点成为下一层父节点，继续叠加其他算子，探索多个算子连续作用后暴露出的模型能力边界。

核心变化如下：

横向搜索：

```text
父节点
  ├─ 算子 A -> 降分 -> 记录边界候选 -> 分支停止
  ├─ 算子 B -> 不降分 -> 分支停止
  └─ 算子 C -> 降分 -> 记录边界候选 -> 分支停止
```

纵向叠加：

```text
父节点
  ├─ 算子 A -> 降分 -> 记录边界候选 + 加入下一层 frontier
  │              ├─ 算子 B -> 继续降分 -> 记录叠加边界候选 + 加入下一层 frontier
  │              └─ 算子 C -> 不降分 -> 当前分支停止
  └─ 算子 D -> 不降分 -> 当前分支停止
```

纵向叠加的目的不是引入更严格的自动审核规则，也不是让搜索层判断"降分是否合理"。搜索层只负责扩大可观测的题目进化路径，记录单算子和多算子叠加后出现的降分证据。原有生成答案、生成 Rubric、生成或更新 Score Prompt、候选模型回答、Judge 评分、复杂度与可回答性校验、Memory 写入等机制均保持不变。

人工审核仍然是实验结束后的统一离线步骤。在线纵向搜索不等待人工审核结论，也不因为人工审核状态改变搜索调度。

## 2. 优化目的

### 2.1 从单算子边界扩展到组合边界

单个算子可以暴露模型在某一种进化方向上的能力边界，但模型真实弱点可能来自多个压力方向连续叠加。例如：

先通过一个算子改变题目的证据充分性竞争点，
再通过另一个算子引入反事实阈值变化，
最终形成单个算子难以直接生成的复合边界。

纵向叠加要发现的不是"任意复杂题目"，而是"在原题核心能力轴附近，多个算子连续施压后，模型在哪些组合判断上开始失稳"。

### 2.2 记录算子叠加路径，而不是只记录最终叶节点

纵向搜索必须保留完整路径：

```text
root -> O10 -> O15 -> O17
```

每一条边都需要记录：

- 当前父节点；
- 子节点；
- 使用的算子；
- 父子分数；
- 相对父节点的分数变化；
- 相对根节点的累计分数变化；
- 完整评价产物；
- 当前节点是否进入下一层 frontier。

这样后续人工审核和实验分析才能区分：

- 单个算子是否有效；
- 某个算子接在另一个算子之后是否有效；
- 某个有序算子序列是否形成了新的组合边界；
- 同一组算子在不同顺序下是否表现不同。

### 2.3 控制搜索范围，而不是枚举所有组合

搜索范围扩大必然带来资源消耗增加。纵向叠加不能直接枚举所有算子排列，否则会形成组合爆炸。

假设有 9 个可生成算子：

```text
深度 1：9
深度 2：9 * 8 = 72
深度 3：9 * 8 * 7 = 504
```

每个节点又都要执行完整答案、Rubric、Score Prompt、候选回答和 Judge 评分闭环，成本不可接受。

因此，本方案不再为根节点第一层额外设置"最多展开 N 个算子"的限制。根节点第一层仍沿用横向多算子分支搜索的全局规则：所有适合算子均已尝试，或已发现 5 个边界候选，则该样本停止。纵向方案只在此基础上增加最大深度约束，用来控制降分节点还能向下叠加多少层算子。

### 2.4 保持评测契约稳定

纵向算子叠加不能改变以下契约：

- 不改变候选模型回答方式；
- 不改变参考答案生成方式；
- 不改变 Rubric 生成与使用方式；
- 不改变 Score Prompt 生成与使用方式；
- 不改变 Judge 模型、重复次数和评分聚合方式；
- 不新增语义相似度判断；
- 不新增自动判断"降分是否合理"的规则；
- 不把任意降分自动标记为人工确认有效边界；
- 不改变原有复杂度、可回答性等候选校验；
- 不改变原有 Memory 的业务准入、写入时机和数据结构；
- 不使用人工审核状态控制在线搜索。

纵向搜索提升的是边界发现覆盖率，不是通过改变判别机制制造新的实验结论。

## 3. 非目标与设计边界

本方案明确不做以下事情：

1. 不实现全排列、全组合、无限深度搜索；
2. 不让搜索层判断降分是否合理；
3. 不新增题目语义相似度或边界语义去重模型；
4. 不改变原有 Judge 的决策地位；
5. 不根据路径深度改变原始样本权重；
6. 不根据算子叠加数量给题目额外加分或扣分；
7. 不因为路径更深就降低复杂度、可回答性或评分证据保存要求；
8. 不要求人工审核通过后才允许继续扩展；
9. 不把 review_status 用作搜索调度、Memory 写入或评分判断条件；
10. 不在第一阶段自动学习复杂的算子转移策略。

第一阶段优先建立可控、可恢复、可审计的纵向搜索数据。后续只有在积累足够实验记录后，才考虑基于历史命中率优化算子转移顺序。

## 4. 核心概念

### 4.1 根节点

根节点是样本进入纵向搜索前已经完成评分的原始父节点。它提供：

- 原题文本；
- 原题参考答案；
- 原题 Rubric 和 Score Prompt；
- 原题候选模型答案；
- 原题评分结果和 score_rate；
- 样本画像；
- 历史状态；
- 算子路由所需上下文。

根节点是整条纵向路径的起点。所有纵向节点都必须保留到根节点的可追溯关系。

### 4.2 当前父节点

当前父节点是某一层准备继续扩展的节点。它可能是根节点，也可能是上一层降分后形成的子节点。

纵向搜索中的每次分数比较都使用直接父节点：

```text
child_score_rate < direct_parent_score_rate
```

直接父子比较用于判断当前算子是否带来新的边际降分。根节点比较只用于实验分析，不用于在线扩展判定。

### 4.3 Frontier 节点

Frontier 节点是已经完成评分、通过原有校验、且相对直接父节点分数下降的节点。它同时具有两个身份：

boundary_candidate：待人工审核的边界候选
frontier_node：可继续向下一层叠加算子的在线搜索节点

一个节点进入 frontier 不代表它已经是确认有效边界，只代表它满足在线扩展条件：

```text
原有校验通过
且 child_score_rate < direct_parent_score_rate
且 child depth 未超过 max_depth
且 未触发请求、评分、超时或致命错误保护
```

### 4.4 算子叠加路径

算子叠加路径表示从根节点到当前节点经过的有序算子序列。例如：

```json
{
  "operator_stack": ["O10_evidence_sufficiency_ladder", "O15_counterfactual_threshold_shift"],
  "depth": 2
}
```

有序路径用于判断具体叠加效果。O10 -> O15 和 O15 -> O10 必须视为不同路径，因为第二个算子作用的父题不同，生成上下文、Rubric、候选答案和评分结果都可能不同。

同时，为了后续聚合分析，可以额外记录无序组合键：

```json
{
  "operator_set": [
    "O10_evidence_sufficiency_ladder",
    "O15_counterfactual_threshold_shift"
  ]
}
```

无序组合键只用于统计"这组算子整体是否值得研究"，不用于替代有序路径。

### 4.5 边界边与边界路径

纵向搜索需要区分两类结果：

边界边

边界边是某一次父子扩展中出现的降分关系：

```text
parent_node --operator--> child_node
且 child_score_rate < parent_score_rate
```

边界边用于在线搜索调度和局部效果分析。

边界路径

边界路径是从根节点出发，经过一条或多条边界边形成的完整路径：

```text
root -> O10 -> O15 -> O17
```

边界路径用于人工审核和实验总结。路径越深，不代表越有效；它只说明多个算子连续作用后仍然观察到分数下降。

## 5. 搜索模式

建议新增搜索模式：

```text
single_branch
multi_operator_branch
multi_operator_vertical_stack
```

- single_branch：保持当前单候选主链行为；
- multi_operator_branch：启用横向多算子分支搜索；
- multi_operator_vertical_stack：启用纵向算子叠加搜索。

三种模式共享相同的生成、回答、Rubric、Score Prompt、评分和原有校验模块。差异只在搜索协调层：

```text
single_branch：
  每轮选择一个候选进入闭环。

multi_operator_branch：
  同一父节点上多个适合算子分别形成一层分支。

multi_operator_vertical_stack：
  降分分支继续成为下一层父节点，在预算内叠加其他算子。
```

## 7. 每层候选算子选择

### 7.1 每个 frontier 节点重新路由

每一层都必须基于当前 frontier 节点重新建立 operator_plan，不能简单继承根节点的算子计划。

原因是纵向叠加后，当前节点的题面、预期失分点、候选答案和评分结果已经发生变化。下一层适合的算子可能与上一层不同。

### 7.2 候选算子来源

每个 frontier 节点的候选算子集合按以下来源构建：

```text
当前节点 router primary / backup operators
→ 其他启用且具备题目生成功能的算子
→ avoid_operators（只降低优先级，不等于排除）
```

候选算子必须满足：

- 当前启用；
- 具备题目生成功能；
- 未被静态禁用；
- 未在当前节点返回结构化 not_applicable；
- 默认未在当前有序路径中出现过。

### 7.3 同一路径默认禁止重复算子

第一阶段建议禁止同一路径重复使用同一算子：

```text
允许：O10 -> O15 -> O17
默认不允许：O10 -> O15 -> O10
默认不允许：O10 -> O10
```

原因：

- 更容易解释叠加效果；
- 避免把同一算子的重复强化误认为组合边界；
- 减少搜索空间；
- 方便后续统计不同算子之间的转移效果。

如果未来要研究同一算子的连续强化，可以单独开启实验参数：

```text
allow_operator_repeat_in_path = true
```

该实验应与默认纵向叠加实验分开统计。

### 7.4 算子排序策略

第一阶段建议使用规则排序，不引入学习型转移模型。

排序优先级如下：

1. 当前节点 router primary operator；
2. 当前节点 router backup operators；
3. 与上一层算子方向互补的算子；
4. 当前路径未使用过的算子；
5. 历史 failure memory 或 avoid 信息只降权，不直接排除；
6. 其他具备生成功能的启用算子；
7. avoid_operators 中的算子放在末尾。

互补关系第一阶段不需要做复杂语义模型判断，可先由固定规则维护。例如：

```text
证据充分性方向后，可优先尝试反事实阈值、动作事实门槛、基线口径方向；
不可见状态归因方向后，可优先尝试正常替代解释、反事实阈值、动作事实门槛方向；
信息闭包方向后，可优先尝试证据充分性、多条件共同必要方向。
```

这些只是排序偏好，不是硬规则。只要预算允许，其他适合算子仍可被尝试。

### 7.5 运行时不适用

如果题目生成模块结构化返回 not_applicable，必须同时保存非空原因，并将该算子标记为当前节点不可用。

not_applicable 只对当前节点生效，不应自动扩散到同一样本的其他节点。原因是同一个算子可能不适用于某个中间题面，但适用于另一条路径上的题面。

## 8. 深度控制与全局终止条件

### 8.1 不限制根节点第一层算子覆盖

纵向方案不能把根节点第一层限制为"最多展开 3 个算子"或其他固定宽度。根节点第一层已经由横向多算子分支搜索负责，目标是覆盖所有适合算子，直到满足原有全局终止条件。

因此，纵向模式下：

```text
root 第一层：
  沿用横向方案的 operator_plan
  不额外设置第一层分支数量上限
  不额外设置每层 frontier 保留上限
```

如果第一层因为找到 5 个边界候选而停止，则样本按原全局终止条件结束，不再为了纵向叠加强行继续调度未尝试算子。

### 8.2 只新增最大深度约束

纵向方案新增的核心控制参数只有最大深度：

```json
{
  "max_depth": 3
}
```

本方案采用节点层级定义深度：

root 节点：depth = 1
root 的第一层算子子节点：depth = 2
第一层降分节点继续叠加一个算子后：depth = 3

因此，当 max_depth = 3 时，含义是：

允许 root 先按横向方案展开所有适合算子；
如果某个第一层子节点降分，则允许在该节点基础上再叠加 1 个算子；
第二次叠加生成的 depth=3 节点完成评分后，不再继续向 depth=4 扩展。

换句话说，max_depth = 3 对应的是"最多允许一个纵向叠加算子"，而不是"根节点第一层最多展开 3 个算子"。

### 8.3 全局终止条件保持不变

纵向模式沿用横向方案的两个业务终止条件：

1. 所有适合算子均已完成尝试；
2. 已发现的边界候选数量达到 5 个。

差异只在于"所有适合算子"的作用范围从单一父节点扩展为搜索过程中所有允许扩展的父节点：

```text
如果某个节点有资格继续扩展，
则该节点也拥有自己的 operator_plan；
该 operator_plan 仍按横向方案尝试适合算子；
直到该节点算子耗尽，或样本级边界候选达到 5 个。
```

系统硬保护仍然保留：

- 请求预算；
- 评分预算；
- 超时；
- 致命错误；
- 断点恢复失败。

这些保护只防止任务失控，不属于业务判别依据。

### 8.4 第一阶段建议深度

第一阶段建议：

```json
{
  "max_depth": 3
}
```

不建议第一阶段超过 depth=3，原因：

- 深度越大，题目越可能偏离原始能力轴；
- Rubric 漂移和参考答案扩展压力增加；
- 复杂度与可回答性失败概率上升；
- 人工审核路径更难解释；
- 资源消耗和恢复复杂度显著上升。

depth=3 已经能验证核心假设：

在单算子已经产生降分后，再叠加一个算子是否能继续发现新的边际能力边界。

如果 depth=3 的实验显示叠加路径明显有价值，再考虑扩大到 depth=4。

## 9. 有序组合与反向顺序

### 9.1 执行层必须区分顺序

纵向算子叠加中的算子不是可交换运算。以下两条路径必须视为不同实验对象：

```text
O10 -> O15
O15 -> O10
```

原因：

- 第二个算子作用的父题不同；
- 第一层改写会改变第二层生成上下文；
- Rubric 和 Score Prompt 会基于不同子题生成；
- 候选模型答案可能暴露不同错误方向；
- 评分下降可能来自不同判断点。

因此，执行记录、节点 ID、分支 ID 和恢复键都必须包含有序路径。

### 9.2 分析层可以同时记录无序组合

为了后续统计，可以同时记录无序组合：

```text
operator_stack = [O10, O15]
operator_set = {O10, O15}
```

这样可以分别回答：

```text
O10 -> O15 是否有效？
O15 -> O10 是否有效？
{O10, O15} 这组算子整体是否值得继续研究？
```

### 9.3 第一阶段不强制补测反向顺序

第一阶段不建议自动跑所有反向组合。默认策略：

```text
先按路由和预算执行有序路径；
如果某组算子在一个顺序上表现出高价值；
再在后续实验中补测反向顺序。
```

这样能把预算集中在更有可能发现边界的路径上，而不是平均消耗在所有排列上。

## 10. 分数比较与扩展规则

### 10.1 直接父子比较

每个子节点只与直接父节点比较：

```text
edge_delta_score_rate = child_score_rate - parent_score_rate
```

如果：

```text
child_score_rate < parent_score_rate
即 edge_delta_score_rate < 0
```

则该节点：

- 标记为 boundary_candidate；
- review_status = pending；
- 记录完整评价产物；
- 如果 child_depth < max_depth，则成为可继续叠加算子的父节点；
- 如果 child_depth >= max_depth，则只保留为边界候选，不继续向下扩展。

### 10.2 根节点累计比较

同时记录相对根节点的累计变化：

```text
root_delta_score_rate = child_score_rate - root_score_rate
```

root_delta_score_rate 只用于实验分析，不用于在线扩展判断。

### 10.3 分数不变

如果：

```text
child_score_rate == parent_score_rate
```

则当前节点标记为：

```text
branch_status = no_score_change
```

该节点不进入下一层 frontier，也没有必要在其基础上继续叠加算子。原因是该算子没有在当前父节点上形成新的边际降分，继续向下扩展会把后续结果建立在一个未证明有效的进化节点上，容易放大噪声。

### 10.4 分数上升

如果：

```text
child_score_rate > parent_score_rate
```

则当前节点标记为：

```text
branch_status = score_increased
```

该节点不进入下一层 frontier，也不能成为后续评分基线。

分数上升节点仍然要保存完整产物，用于分析该算子在当前路径上为什么削弱了题目区分度。

### 10.5 无效分支不继续纵向叠加

以下分支终态不能成为下一层父节点：

- no_score_change；
- score_increased；
- duplicate_exhausted；
- validation_failed；
- not_applicable；
- branch_error。

第一层某个算子未形成有效边界边时，没有必要在该节点基础上继续叠加算子。这里的"无效"仅指该次分支未通过原有校验，或相对直接父节点未产生降分；它不等同于该算子在其他题目或其他路径上永远不适用。纵向叠加的目标是观察"已经形成降分的进化之后再施加另一个算子"是否能发现新的能力边界；把未形成降分的节点继续向下展开会将后续结果建立在未经证实的压力路径上，并显著扩大组合搜索空间。

若后续研究的目标改为发现"两个单独不降分、组合后才降分"的协同效应，应作为独立的组合探索实验设计，并另行设置预算、对照组和终止条件；它不属于本方案的默认纵向边界搜索。

无效分支仍需保留完整轨迹，用于分析算子覆盖、失败原因和后续路由改进，但它只回到当前父节点继续尝试其他适合算子，不进入纵向路径。

### 10.6 不使用轻量命中标签作为扩展条件

纵向扩展条件不应依赖 effective_boundary_probe、needs_manual_review 或其他带有置信度判断的效果标签。

在线扩展只看：

```text
原有校验通过
且 child_score_rate < direct_parent_score_rate
且 child_depth < max_depth
且 未触发样本级全局终止条件
```

原因是纵向搜索不是为了提前确认有效边界，而是为了扩大边界候选发现范围。人工审核仍在实验结束后统一进行。

## 11. 重复题目判定

### 11.1 继续使用精确重复

纵向搜索继续使用简单、可解释的精确重复检查，不引入语义相似度模型。

题目比较前只做以下规范化：

1. 去除首尾空白；
2. 将连续空格、换行和制表符合并为一个空格。

规范化后的题目文本完全相同时，视为重复。

### 11.2 纵向重复检查范围

纵向搜索的重复检查范围应扩展为：

- 当前直接父节点；
- 当前路径上的所有祖先节点；
- 当前父节点下已经接受的兄弟节点；
- 同一样本内已经登记的其他纵向节点。

这样可以避免路径绕回已经生成过的题目。

### 11.3 重复重试规则

同一父节点、同一算子分支首次生成重复时，允许同算子重试一次。

第二次仍重复时：

- 当前算子分支标记为 duplicate_exhausted；
- 保存两次生成轨迹；
- 不创建子节点；
- 不进入答案、Rubric、Score Prompt 和评分闭环；
- 回到当前父节点，尝试下一个候选算子。

精确重复重试不消耗原有复杂度或可回答性校验重试次数。

## 13. 终止条件

### 13.1 正常业务终止

纵向模式保持横向多算子分支搜索的全局业务终止条件不变：

条件一：所有可扩展父节点的适合算子均已尝试

当搜索过程中不存在仍可扩展的父节点，或所有可扩展父节点的 operator_plan 都已结束时，样本终止：

```text
termination_reason = operator_space_exhausted
```

这里的"可扩展父节点"包括：

- root 节点；
- 已经降分、通过原有校验、且 depth < max_depth 的子节点。

如果某个节点已经达到 max_depth，它不再继续向下扩展，但这只是节点级扩展限制，不是样本级终止原因。

条件二：边界候选数量达到 5 个

当该样本累计发现 5 个降分分支时，立即停止，不再调度新的算子分支：

```text
termination_reason = boundary_target_reached

boundary_target = 5
```

边界数量仍按降分分支计数。由于合理性将在后续人工审核，本阶段不进行语义去重或有效性扣减。样本因 boundary_target_reached 终止时，boundary_candidate_count 等于 5；样本因 operator_space_exhausted 终止时，输出实际发现数量，该数量可以小于 5。

### 13.2 最大深度不是全局终止条件

max_depth 只决定一个降分节点能否继续成为下一层父节点。例如：

```text
max_depth = 3
root depth = 1
root -> O10 depth = 2
root -> O10 -> O15 depth = 3
```

当 depth=3 的节点继续降分时，它仍然记录为 boundary_candidate，但不再加入可扩展父节点集合。搜索协调器应回到其他仍可扩展父节点或其他未尝试算子，而不是把样本终止原因写成 max_depth_reached。

### 13.3 系统保护终止

系统仍需保留以下硬保护：

- 单样本最大 API 请求数；
- 单样本最大评分次数；
- 单样本最大运行时间；
- 全局并发限制；
- 阶段产物损坏保护；
- 不可恢复错误终止；
- 断点恢复和幂等写入。

系统保护触发时使用独立终止原因：

- request_budget_exhausted；
- evaluation_budget_exhausted；
- timeout；
- fatal_error；
- state_recovery_failed。

这些原因表示搜索未按业务目标自然完成，不能伪装成 operator_space_exhausted 或 boundary_target_reached。

## 14. Frontier 扩展资格

纵向模式不使用额外的宽度裁剪策略。Frontier 只由扩展资格决定。

### 14.1 可扩展节点

节点必须同时满足以下条件，才能成为下一层父节点：

1. 子题通过原有校验；
2. 子节点已完成答案、Rubric、Score Prompt、候选回答和 Judge 评分闭环；
3. child_score_rate < direct_parent_score_rate；
4. child_depth < max_depth；
5. 样本尚未触发 boundary_target_reached；
6. 未触发系统硬保护。

### 14.2 不可扩展节点

以下节点不得继续纵向叠加：

- 分数不变节点；
- 分数上升节点；
- 原有校验失败节点；
- 重复耗尽节点；
- 算子不适用节点；
- 阶段错误节点；
- 已达到 max_depth 的节点。

这些节点仍保留完整记录，但只作为失败探索、边界候选或审计证据，不再成为下一层父节点。

### 14.3 调度顺序

当多个节点同时具备扩展资格时，建议使用确定性顺序调度，而不是按额外宽度规则丢弃节点：

1. 深度较浅的节点优先；
2. 同一深度下，按父节点生成顺序优先；
3. 同一父节点下，按 operator_plan 顺序优先；
4. 达到 5 个边界候选后立即停止。

确定性顺序只影响执行先后，不改变哪些节点具备扩展资格，也不增加新的有效性判断。

## 15. 输出产物

纵向模式已新增以下规范化产物：

```text
vertical_search_checkpoint.jsonl  轻量搜索状态和恢复入口
vertical_nodes.jsonl              根节点与完成完整评分闭环的节点
operator_attempts.jsonl           每个 frontier 的逐算子尝试
boundary_edges.jsonl              直接父子降分边
boundary_paths.jsonl              有序算子路径与累计分数变化
vertical_search_summary.json      样本、算子、组合、终止和预算指标
parents/                          各 frontier 复用横向完整闭环的阶段产物
```

边界路径集合不能只保存题目和分数，必须保留完整分支产物，否则人工审核无法判断：

- 是否存在 Rubric 漂移；
- 是否存在 Score Prompt 漂移；
- Judge 是否稳定；
- 候选模型失分是否来自题目能力边界；
- 多算子叠加是否偏离原题核心能力轴。

## 16. 与原有 Memory 机制的关系

纵向搜索不改变原有 Memory 的业务准入、内容和触发时机。

每个完成原有闭环的节点继续按照原有机制处理 Memory。搜索层不得增加以下约束：

- 不得要求人工审核通过后才允许写入 Memory；
- 不得因为节点属于纵向路径而改变 Memory 准入条件；
- 不得使用 review_status 控制 Memory 写入；
- 不得用路径深度替代原有 Memory 判断依据。

为支持断点恢复，Memory 写入层可以使用以下技术幂等键：

```text
node_id + memory_type
```

该幂等键只用于避免恢复时重复追加，不改变 Memory 的业务字段、准入条件或触发时机。

需要注意：同一样本内纵向搜索按确定顺序执行时，前面节点写入的 Memory 可能影响后续节点的路由。这是保留原有 Memory 机制后的顺序效应。实验必须记录：

- 节点执行顺序；
- 算子计划；
- Memory 版本；
- 搜索配置。

这样才能保证结果可复现。

## 17. 并发与调度

### 17.1 样本间并发

不同样本之间可以并发执行。并发上限继续由全局请求、评分和 API 限流预算控制。

### 17.2 样本内调度

同一样本内建议按层串行推进：

```text
完成当前层所有已调度节点
→ 收集下一层 frontier
→ 过滤已达 max_depth 或无效节点
→ 再进入下一层
```

不建议同一样本内同时展开不同深度的节点。否则会增加以下复杂度：

- frontier 抢占；
- 预算并发扣减；
- 重复题登记竞态；
- 断点恢复顺序不稳定；
- 边界路径输出不确定。

### 17.3 同一 frontier 下的算子分支

第一阶段建议同一 frontier 下的算子分支按路由顺序串行执行。这样可以复用横向方案中的去重和边界数量控制思路，避免兄弟分支同时登记相同题目的竞态。

如果后续为了吞吐并行化同一 frontier 下的算子，必须先实现原子化的题目哈希登记和幂等写入。

## 18. 断点恢复与幂等

纵向模式的恢复键必须稳定，不能依赖执行批次。

推荐 ID 规则：

```text
root_node_id = sample_id::root
node_id = root_node_id::operator_stack_hash_or_joined_operator_ids
attempt_id = parent_node_id::try::operator_id
path_id = sample_id::path::operator_stack
```

实际实现可以使用可读 ID 或哈希 ID，但必须满足：

- 同一输入、同一配置、同一路径生成相同 ID；
- 重启后不会重复执行已完成节点；
- 已完成评分的节点不会被覆盖；
- 已记录的生成尝试轨迹不会丢失；
- 系统保护中断后可以从未完成 frontier 继续。

恢复时应按以下顺序判断：

1. 搜索状态是否存在且 manifest 有效；
2. 节点记录是否完整；
3. 算子尝试记录是否完整；
4. 已完成节点的答案、Rubric、Score Prompt、候选答案和 Judge 结果是否完整；
5. Memory 幂等提交是否完成；
6. 未完成节点应从哪个阶段继续。

## 19. 人工审核方式

人工审核仍在全部实验运行完成后统一进行。

审核对象包括：

- 单算子降分边界候选；
- 两算子叠加边界候选；
- 三算子叠加边界候选；
- 已达到 max_depth 但继续降分的节点；
- 所有达到审核条件的边界路径。

审核内容包括：

- 题目变化是否仍围绕原始能力轴；
- 多算子叠加是否形成合理的新判断压力；
- 参考答案是否足以支撑新题；
- Rubric 是否稳定；
- Score Prompt 是否稳定；
- 候选模型失分是否确实体现目标能力边界；
- Judge 结果是否可信；
- 是否应进入正式有效边界集合。

审核结论只写回审核状态和实验总结，不改变在线搜索期间已经产生的评分、Memory 和路径记录。

## 20. 搜索摘要指标

每次纵向实验应输出以下指标：

### 20.1 样本级指标

- 输入样本数；
- 进入纵向搜索样本数；
- 样本平均完成深度；
- 样本平均评分节点数；
- 样本平均边界边数量；
- 样本平均边界路径数量；
- 正常终止样本数；
- 系统保护终止样本数；
- 各终止原因分布。

### 20.2 算子级指标

- 单算子调用次数；
- 单算子校验通过率；
- 单算子评分完成率；
- 单算子边界边命中率；
- 单算子导致 score_increased 的比例；
- 单算子 not_applicable 比例；
- 单算子 duplicate_exhausted 比例。

### 20.3 组合级指标

- 有序二元组合出现次数；
- 有序二元组合边界命中率；
- 有序三元组合出现次数；
- 有序三元组合边界命中率；
- 无序组合整体表现；
- 反向顺序对比表现；
- 平均 edge_delta_score_rate；
- 平均 root_delta_score_rate。

### 20.4 预算指标

- API 请求数；
- 评分次数；
- 平均每样本运行时间；
- 平均每条边界路径成本；
- 因 max_depth 未继续扩展的降分节点数量；
- 因系统硬保护中止的样本和节点数量。

## 21. 兼容策略

### 21.1 与横向多分支模式兼容

纵向模式应复用横向模式已经定义的能力：

- 父节点和分支节点；
- 每个算子最多生成一个有效候选；
- 精确重复检查与一次重复重试；
- not_applicable 结构化记录；
- API 重试、原有校验重试、精确重复重试分离；
- 分支级完整产物保存；
- candidate_group_id 和 candidate_id 的稳定映射；
- 搜索摘要和断点恢复。

纵向模式在此基础上新增：

- 节点可成为下一层父节点；
- 有序 operator_stack；
- 最大深度扩展限制；
- 可扩展父节点调度；
- 边界路径输出；
- 组合级指标。

### 21.2 与单分支模式兼容

纵向模式不得改变单分支模式的数据含义和输出字段。

建议所有纵向字段都挂在独立结构下，例如：

vertical_search_state
vertical_node
operator_stack
frontier_status
boundary_path

单分支模式不需要填充这些字段。

### 21.3 与现有轮次概念兼容

纵向模式下，round 可以继续作为执行批次和日志字段，但不作为业务终止条件。

业务终止由以下字段决定：

- operator_space_exhausted；
- boundary_target_reached；
- 系统保护终止原因。

## 22. 建议实施顺序

1. 定义纵向节点、边、路径、frontier 和搜索状态数据结构；
2. 定义稳定 ID、路径 ID 和恢复键；
3. 在搜索协调层支持 multi_operator_vertical_stack 模式；
4. 将横向模式的父节点算子计划扩展为"每个 frontier 节点独立算子计划"；
5. 实现同一路径默认禁止重复算子的过滤；
6. 实现 max_depth 节点扩展限制；
7. 实现直接父子分数比较与根节点累计分数记录；
8. 实现降分节点进入下一层 frontier；
9. 实现无效节点不进入下一层 frontier；
10. 扩展精确重复检查范围到祖先节点和同一样本已登记节点；
11. 接入原有答案、Rubric、Score Prompt、候选回答和 Judge 评分闭环；
12. 接入原有 Memory 写入机制，并使用节点级幂等键防止重复追加；
13. 实现边界边、边界路径和搜索摘要输出；
14. 增加单分支、横向多分支、纵向叠加三种模式的兼容回归测试；
15. 用小样本和低深度配置验证断点恢复、最大深度限制和全局终止条件；
16. 再扩大到推荐默认参数进行正式实验。

## 23. 验收标准

### 23.1 功能验收

1. multi_operator_vertical_stack 模式可以独立开启，不影响单分支和横向多分支模式；
2. 只有原流程判定需要进化的样本进入纵向搜索；
3. 根节点和每个纵向子节点均有稳定 ID；
4. 每个 frontier 节点都会重新建立自己的 operator_plan；
5. 同一路径默认不会重复使用同一算子；
6. 每个候选算子最多生成一个有效候选，首次精确重复时允许同算子重试一次；
7. 每个不重复且通过原有校验的节点都执行完整答案、Rubric、Score Prompt、候选回答和 Judge 评分闭环；
8. 每个子节点都与直接父节点比较分数；
9. 分数下降节点标记为 boundary_candidate，且仅在 depth < max_depth 时加入下一层 frontier；
10. 分数不变或上升节点不会进入下一层 frontier；
11. 样本只因 operator_space_exhausted 或 boundary_target_reached 正常终止；
12. 系统保护触发时使用独立终止原因，不伪装成业务完成。

### 23.2 判别一致性验收

1. 纵向模式不修改候选模型回答方式；
2. 纵向模式不修改参考答案生成方式；
3. 纵向模式不修改 Rubric 和 Score Prompt 生成方式；
4. 纵向模式不修改 Judge 输出；
5. 纵向模式不新增复杂边界判定规则；
6. 纵向模式不使用人工审核状态控制在线搜索；
7. 降分节点只能自动标记为边界候选，不能自动标记为确认有效边界；
8. 原有 Memory 的准入条件、写入时机和数据结构保持不变。

### 23.3 数据与恢复验收

1. 每个节点、边、算子尝试和路径均可追踪；
2. 每条路径保留有序 operator_stack；
3. O10 -> O15 和 O15 -> O10 可以被区分；
4. 同一样本内重复题不会被重复登记；
5. 断点恢复不会重复执行已完成评分节点；
6. Memory 写入通过节点级幂等键避免重复追加；
7. 达到 max_depth 的降分节点仍保留边界候选状态和完整产物；
8. 搜索摘要能区分业务终止和系统保护终止。

### 23.4 实验分析验收

1. 可以统计单算子边界命中；
2. 可以统计有序二元算子组合边界命中；
3. 可以统计有序三元算子组合边界命中；
4. 可以比较同一组算子的不同顺序；
5. 可以计算每条边的 edge_delta_score_rate；
6. 可以计算每条路径的 root_delta_score_rate；
7. 可以输出代表性边界路径供人工审核；
8. 可以复现每条路径的完整生成和评分证据。

## 24. 第一阶段推荐实验配置

建议第一阶段只新增纵向最大深度配置：

```json
{
  "search_mode": "multi_operator_vertical_stack",
  "max_depth": 3,
  "allow_operator_repeat_in_path": false
}
```

该配置含义：

- root 节点仍按横向多算子分支搜索覆盖全部适合算子；
- root 的第一层子节点为 depth=2；
- 只有第一层降分节点可以继续叠加一个算子，形成 depth=3 节点；
- depth=3 节点即使继续降分，也只记录为边界候选，不再向 depth=4 扩展；
- 样本级全局终止条件仍为适合算子耗尽或边界候选达到 5 个。

推荐先用更小深度做工程验证：

```json
{
  "search_mode": "multi_operator_vertical_stack",
  "max_depth": 2,
  "allow_operator_repeat_in_path": false
}
```

max_depth=2 只验证 root 到第一层分支的兼容性，不启用真正的纵向叠加。

小配置用于验证：

- 节点 ID 是否稳定；
- 路径记录是否正确；
- 重复检查是否覆盖祖先节点；
- 分数比较是否始终使用直接父节点；
- 降分节点是否进入下一层 frontier；
- 断点恢复是否幂等；
- 原有生成、答案、Rubric、Score Prompt 和评分闭环是否保持不变。

验证通过后，再使用 max_depth=3 进行正式纵向叠加实验。

## 25. 最终原则

纵向算子叠加只改变搜索形态，不改变评测契约。

横向多分支：
  在同一个父节点上覆盖多个算子方向。

纵向算子叠加：
  在降分节点上继续叠加其他算子，搜索多算子连续作用后的能力边界。

搜索层负责：

- 选择可扩展 frontier；
- 为每个 frontier 建立候选算子计划；
- 管理最大深度和全局终止条件；
- 处理精确重复和一次重复重试；
- 调用原有完整闭环；
- 根据直接父子分数关系决定是否继续扩展；
- 记录节点、边、路径和搜索摘要。

原有模块继续负责：

- 生成题目；
- 生成答案；
- 生成 Rubric；
- 生成或更新 Score Prompt；
- 候选模型回答；
- Judge 评分；
- 原有候选校验；
- 保存完整实验证据；
- 按原机制写入 Memory。

人工审核负责：

- 在实验结束后统一判断降分是否合理；
- 判断单算子或多算子叠加是否形成有效能力边界；
- 标记边界候选是否进入正式有效边界集合；
- 总结哪些有序算子路径值得继续扩大实验。

只有保持"搜索扩展"和"有效性审核"分离，纵向算子叠加才能真正用于发现模型更多能力边界，而不是把在线流程变成新的严格审核系统。
