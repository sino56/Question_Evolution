# 树搜索效率优化方案

- 文档版本：v1.0
- 制定日期：2026-07-24
- 文档状态：代码实施完成；真实小批量与三次性能验收待执行（2026-07-25）
- 适用范围：Question Evolution 基于父节点的多算子横向分支搜索
- 目标读者：负责搜索调度、模型服务、运行状态、实验编排和验收的内部工程师
- 读后可执行的动作：按阶段改造搜索调度，在不改变边界判定和评分口径的前提下，提高分支吞吐并完成等价性、恢复性和性能验收。

本方案建立在 基于父节点的多算子分支搜索方案 和 实验迭代速度优化方案 之上。前者定义搜索业务语义，后者定义阶段并发、请求池、检查点和正式产物发布机制；本文只补充树搜索调度效率设计。

## 1 方案摘要

当前树搜索实际是"以一个已评分题目为父节点，对多个算子进行一层横向探索"。它不是向下递归的多层树。当前实现对同一样本一次只调度一个算子分支，必须等待该分支完成生成、校验、参考答案、Rubric、Qwen 回答、双 Judge 评分和状态更新后，才会调度下一个算子。

这种宽度为 1 的批次式执行保证了控制逻辑简单，但存在四个直接问题：

1. 同一样本的独立算子分支无法共享模型服务并发能力；
2. 每个搜索步都存在完整的阶段屏障，快分支必须等待慢分支；
3. 活跃样本逐渐减少后，全局请求池长期无法达到安全并发上限。
4. 当前计划会将大量注册且静态可执行的算子补入 operator_plan，即使它们不在当前题目的候选列表中，也会被逐一建立分支并进入完整闭环。

本方案采用以下优化顺序：

1. 修复终止搜索状态可能丢失并导致样本重新进入搜索的问题；
2. 将调度范围限定为当前样本候选列表中的算子，不再自动遍历全部注册算子；
3. 将每个样本的分支调度从宽度 1 改为动态有界窗口，初始建议窗口为 3；
4. 将只承担实验记录职责的 GPT Judge 从搜索决策关键路径中移出；
5. 将逐步批处理改造成按分支推进的阶段流水线；
6. 根据历史边界产出率和耗时优化候选算子的尝试顺序；
7. 将完整分支产物与轻量搜索状态分离，控制长期运行的状态体积。

前三项是优先实施范围。它们不改变 Qwen 决策分数、父子比较、边界候选定义、算子单次尝试预算或 Memory 写入规则。

## 2 当前结构与性能基线

### 2.1 当前执行结构

当前每个活跃样本的执行顺序为：

```text
父节点
  |
  +--> 算子 1
  |      -> 题目生成
  |      -> 候选校验
  |      -> 参考答案
  |      -> Rubric
  |      -> Qwen 回答与 Qwen/GPT Judge
  |      -> 父子分数比较
  |      -> 状态更新
  |
  +--> 算子 2
  |      -> 重复同一完整闭环
  |
  +--> ...
```

不同样本之间可以并发，同一样本的算子分支串行。搜索编排每步只取一个待处理算子，然后依次启动题目进化、校验、选择、答案采集、Rubric、评分、归并和 Memory 更新阶段。

当前注册 O10-O33 共 24 个算子。其中静态禁用或仅承担校验职责的算子不进入生成闭环，单个样本最多仍可能需要完成 22 个生成算子分支。业务停止条件为：

- 边界候选达到目标数量，默认 5；
- 可执行算子空间耗尽。

## 3 根因分析

### 3.1 每个样本的分支窗口固定为 1

即使全局模型服务允许更多并发，同一样本也只能有一个分支进入完整评价。输入样本较少或部分样本提前结束后，题目进化、参考答案、Rubric 和评分 worker 都会出现空闲。

### 3.2 搜索步之间存在全量阶段屏障

当前编排要求一个步骤中的所有候选完成当前阶段，才能进入下一阶段。一个慢生成会阻塞同批其他分支进入参考答案阶段，一个慢 GPT Judge 会阻塞已经完成 Qwen 决策的分支更新搜索状态。

### 3.3 实验 GPT Judge 位于搜索决策关键路径

当前评分协议以 Qwen Judge 聚合结果计算 score_rate。GPT Judge 明确标记为 experimental_only，但实现仍等待 Qwen 和 GPT 两组结果全部返回后才发布分支评分。因此，GPT 延迟会直接推迟下一个算子的调度。

### 3.4 调度集合默认填充全部静态可执行算子

当前 operator_plan 会在优先算子之后补入其余静态可执行算子。这样即使某个算子不在当前题目的候选列表中，也会在前序分支无效或未命中边界后进入 pending 队列，并触发题目生成、答案、Rubric 和评分闭环。

注册表用于定义系统可识别的算子范围，不能直接等同于当前样本的调度范围。当前样本应只调度候选列表中通过规则校验的算子；未进入候选列表的注册算子不创建分支、不计为已尝试，也不因候选耗尽而被自动追加。

### 3.5 算子排序没有直接优化"单位时间边界产出率"

当前路由能够把 primary、backup 和 avoid 算子放到不同优先级，但其余可执行算子主要按固定顺序补齐。搜索在达到 5 个边界后停止，因此前几个算子的边界命中率对总耗时影响很大。

### 3.6 终止状态存在重新初始化风险

当某个父节点在当前搜索步没有候选记录时，归并逻辑会将其搜索状态置空。若该父节点此前已经完成，而其他样本仍需继续搜索，下一步可能依据原有进化动作重新初始化算子计划，从而重复执行已经完成的算子。

终止状态丢失不仅影响速度，也破坏"同一父节点、同一算子最多一条分支"的业务约束，必须在并发优化前修复。

### 3.7 搜索状态携带完整历史产物

搜索状态内嵌完整分支结果，候选记录又携带搜索状态进入下游阶段。随着分支数增加，单条记录不断膨胀，后续每个阶段都会重复解析、复制和序列化历史数据。当前小样本下该成本不占主导，但会限制更大规模实验和更宽分支窗口。

## 4 优化目标与不变量

### 4.1 优化目标

本方案的首要目标是提高单位墙钟时间内完成完整评价的分支数，并缩短每个样本达到终止条件的时间。

具体目标为：

1. 已完成样本永不重新进入算子调度；
2. 在模型服务额度允许时，同一样本可同时推进多个独立算子分支；
3. 边界目标为 5 时，任何调度波次都不能产生超过目标所需数量的新在途分支；
4. Qwen 决策完成后即可更新搜索状态，不被实验 GPT Judge 阻塞；
5. 阶段吞吐受全局请求池控制，不因窗口扩大突破服务安全并发；
6. 中断恢复后不重复已经确认完成的真实模型调用；
7. 性能指标能够区分排队、模型等待、重试、本地处理和状态发布耗时。

### 4.2 必须保持的业务不变量

以下规则不得因提速而改变：

- 同一父节点下的所有子分支都与该父节点比较，不与兄弟节点比较；
- child_score_rate < parent_score_rate 仍是边界候选的唯一自动分数条件；
- Qwen Judge 仍是在线决策 Judge，回答 trial、Qwen Judge repeat 和聚合规则不变；
- GPT Judge 结果仍需完整保留，只调整执行时机；
- 每个父节点与算子组合最多形成一个有效分支；
- 精确重复重试、候选校验重试和 API 重试继续使用独立计数器；
- not_applicable 只能来自具备非空原因的结构化生成结果；
- Memory 的准入、内容、幂等键和写入规则不变；
- 正式产物继续使用 partial、checkpoint、manifest 和原子发布机制；
- 边界候选达到目标后，不再为该样本启动新的算子分支。

### 4.3 非目标

本方案不包含以下策略：

- 不减少 Qwen 回答 trial 或 Qwen Judge repeat；
- 不使用低成本模型替换现有题目生成、参考答案、Rubric 或决策 Judge；
- 不新增近似评分、置信度剪枝或推测性边界判断；
- 不修改边界目标数量；
- 不把一层横向搜索扩展为多层递归树；
- 不把 GPT 实验 Judge 的缺失视为正式实验完成；
- 不通过无限增大 worker 数绕过模型服务请求池。

上述策略可能进一步降低成本，但会改变实验协议或结果完整性，需要单独立项。

## 5 目标调度架构

### 5.1 总体结构

目标架构以"分支"为最小推进单位，以"模型服务"为全局限流边界：

```text
每样本搜索调度器
  |
  +--> 从 operator_plan 领取有界分支窗口
  |
  v
题目生成队列
  |
  v
候选校验与重复控制
  |
  v
参考答案队列
  |
  v
Rubric 队列
  |
  v
Qwen 回答与决策 Judge 队列
  |
  +--> 立即完成父子比较并更新搜索状态
  |
  +--> GPT 实验 Judge 队列异步补齐
  |
  v
正式分支产物齐备后发布
```

各队列只负责阶段依赖，不自行扩大真实请求并发。Qwen 回答和 Qwen Judge 继续共享 Qwen 公平请求池；GPT 题目生成、参考答案、Rubric 和实验 Judge 应按实际服务端点配置共享或独立请求池。

### 5.2 动态分支窗口

#### 5.2.1 候选列表限定调度

每个父节点在进入搜索前必须持久化一份冻结的 selected_operator_ids。该列表表示本次搜索允许创建分支的候选算子集合，必须满足以下规则：

- 只保留当前样本候选列表中通过 ID、启用状态、模式资格、avoid 和历史终态校验的算子；
- 按候选列表既有优先顺序去重；
- operator_plan 只为 selected_operator_ids 创建 entry，不能把其余注册算子或静态可执行算子自动追加到队尾；
- 每个 entry 仍使用稳定的 branch_id = parent_node_id + operator_id，并保留 generation、validation、scoring 和失败状态；
- 候选算子运行时返回 not_applicable、validation_failed、duplicate_exhausted、branch_error、no_score_change 或 score_increased 后，只从同一 selected_operator_ids 中领取下一个 pending 算子；
- 专项全覆盖实验如需遍历全部算子，必须显式构造包含全部目标算子的候选列表，不能复用自然搜索的默认调度行为。

搜索状态同时保存以下审计字段：

```text
selected_operator_ids
selected_operator_count
attempted_selected_operator_ids
omitted_registered_operator_ids
coverage_status = complete | partial
```

当 selected_operator_ids 中所有算子到达终态且未达到边界目标时，终止原因为 candidate_list_exhausted。只有显式全覆盖运行中，所有预注册目标算子都到达终态时，才可以使用 operator_space_exhausted。若调度受到窗口、请求或评分预算截断，则使用 partial_coverage 或对应预算终止原因，不能把未被选入候选列表的注册算子写成"已穷尽"。

每次为一个样本领取分支时，使用以下规则：

```text
remaining_boundary_slots = boundary_target - boundary_candidate_count
available_in_flight_slots = branch_window - in_flight_branch_count

dispatch_count = min(
    remaining_boundary_slots,
    available_in_flight_slots,
    pending_selected_operator_count
)
```

初始建议：

```text
branch_window = 3
```

窗口为 3 时：

- 候选列表含 N 个算子时，全部候选耗尽的搜索波次上限约为 ceil(N / 3)；
- 最快获得 5 个边界所需波次可从 5 降至 2；
- 对只有 1 个剩余边界名额的样本，只允许再启动 1 个分支；
- 已经在途的分支必须完成并保留结果，不能因其他兄弟先完成而丢弃。

第一阶段可以继续在同一样本内顺序生成窗口中的候选，以保持精确重复判定顺序稳定；候选通过校验后，参考答案、Rubric 和评分可跨兄弟分支并行。只有在第一阶段验收后，才考虑将同一样本的题目生成也并行化。

### 5.3 分支领取与幂等

分支调度必须使用稳定身份：

```text
branch_id = parent_node_id + operator_id
```

领取分支时应原子完成：

1. 确认算子状态为 pending；
2. 确认当前窗口仍有容量；
3. 将算子状态改为 running；
4. 将 branch_id 加入在途集合；
5. 持久化轻量搜索状态；
6. 才允许发送第一次真实模型请求。

恢复时，系统根据 checkpoint 判断 running 分支处于哪一阶段。已经发布阶段产物的分支从下一阶段继续；没有任何已确认产物的分支可以恢复为 pending。不得仅因进程中断就把一个已产生正式候选的分支重新从题目生成开始执行。

### 5.4 终止状态保留

当某个样本在当前波次没有候选时，应区分以下情况：

> 暂时无法在飞书文档外展示此内容

题目进化入口和搜索归并入口都应执行该判断，形成双重保护。状态归并不得用"本步没有候选"推断"该样本从未进入搜索"。

候选列表耗尽的 candidate_list_exhausted 是完成状态，应与 boundary_target_reached、partial_coverage 和 aborted 一样被原样保留并透传；不得因后续搜索步没有候选而重新从注册表初始化完整 operator_plan。

### 5.5 GPT 实验 Judge 异步补齐

Qwen Judge 结果齐备后，系统可以立即：

1. 计算 Qwen 聚合分数；
2. 与父节点分数比较；
3. 更新分支业务状态；
4. 更新边界候选计数；
5. 决定是否领取下一批算子。

GPT Judge 继续对相同 answer trial 和相同 Rubric 执行既定重复次数，但进入独立实验评测队列。分支可以具有两个相互独立的完成标志：

```json
{
  "decision_evaluation_status": "completed",
  "experimental_evaluation_status": "pending"
}
```

搜索调度只依赖 decision_evaluation_status。正式完整实验产物发布仍要求两者都完成，或按照现有容错规则明确记录 GPT 调用失败。这样只缩短搜索控制路径，不减少实验请求或丢失 GPT 结果。

实现时应增加内部的决策评测检查点。该检查点只保存搜索归并所需的稳定分支 ID、Qwen trial/repeat 结果、聚合分数和决策状态，搜索归并消费该检查点。现有完整 scored 产物继续等待 GPT 实验结果后再正式发布，不能把缺少 GPT 结果的中间记录伪装成完整评分产物。

## 6 分阶段实施方案

### 6.1 阶段 A：终止状态与幂等修复

改造内容：

- 无候选时保留已有搜索状态；
- 题目进化入口跳过 completed 和 aborted 样本；
- 搜索步结束时校验已完成算子不会重新变成 pending；
- 增加"一个样本已完成、另一个样本仍运行"的回归测试；
- 增加跨两次恢复运行的分支 ID 和调用次数断言。

退出条件：混合状态输入连续推进多个搜索步后，已完成样本的算子调用计数不再增加，终止原因保持不变。

### 6.2 阶段 B：动态分支窗口

改造内容：

- 增加冻结的 selected_operator_ids、候选覆盖状态和候选列表耗尽终止原因；
- operator_plan 仅从候选列表构造，禁止默认追加其余注册算子；
- 增加 SEARCH_BRANCH_WINDOW 配置，默认先设为 1，实验启用值为 3；
- 每条样本按剩余边界名额动态截取候选列表中的待处理算子；
- 搜索状态记录在途分支 ID；
- 归并逻辑支持同一父节点一个波次返回多个分支；
- 保持同一样本的题目生成顺序，先只并行下游评价；
- 在所有服务请求入口继续使用全局公平请求池。

退出条件：固定模拟响应下，窗口 1 和窗口 3 的最终分支分类、边界集合、终止原因和 Memory 条目完全一致；非候选注册算子不产生任何分支或模型调用；窗口 3 不产生边界计数溢出。

### 6.3 阶段 C：GPT 实验 Judge 解耦

改造内容：

- 将评分状态拆成决策评测和实验评测；
- Qwen 决策完成后立即返回搜索归并所需的轻量结果；
- GPT Judge 任务使用独立可恢复队列；
- 完整 scored 分支产物在 GPT 结果补齐后发布；
- 运行摘要分别报告搜索完成时间和完整实验完成时间。

退出条件：解耦前后 Qwen score_rate、分支状态和边界集合完全一致；GPT trial/repeat 数量、顺序、模型和结果字段保持一致。

### 6.4 阶段 D：按分支推进的阶段流水线

改造内容：

- 用长期存活的阶段 worker 和有界队列替代每个搜索步重复启动完整子流程；
- 分支完成一个阶段后立即进入下一队列；
- 每个阶段按 branch_id 发布可恢复检查点；
- 搜索调度器只消费轻量决策结果，不加载完整实验产物；
- Memory 仍按原有准入规则写入，并保证同一分支和类型幂等。

退出条件：任意阶段中断后可从最后一个正式检查点恢复；不存在重复模型请求、漏分支或跨父节点归并。

### 6.5 阶段 E：算子收益排序

改造内容：

- 从历史分支结果统计每个算子的边界候选率、校验通过率、平均耗时和错误率；
- 按样本画像、场景和算子建立分组统计；
- primary 和 backup 仍保持路由优先；
- 候选列表中除 primary 和 backup 外的算子按"预期边界概率 / 预期耗时"排序；
- 保留固定探索比例，避免历史样本不足时永久压低新算子。

退出条件：排序只改变候选列表内部的算子领取顺序，不改变候选列表成员；在固定预算下，前 N 个候选算子的边界候选产出率高于固定顺序基线。

### 6.6 阶段 F：搜索状态瘦身

改造内容：

- 搜索状态只保存调度所需字段、分支 ID、状态和轻量分数；
- 完整候选、回答、Rubric 和 Judge 结果保存到追加式分支产物；
- 搜索状态通过 branch_id 引用完整产物；
- 聚合产物改为流式发布，避免在内存中累计全部步骤记录；
- 保留旧结构读取兼容，禁止在同一实验目录混写两种状态版本。

退出条件：分支数量增加时，单条搜索状态大小只随轻量索引增长；最终业务投影与旧结构等价。

## 9 测试与验收

### 9.1 单元测试

必须覆盖：

1. completed 样本与 running 样本混合时，完成状态不会被清空；
2. 边界计数为 4、目标为 5、窗口为 3 时，只领取 1 个新分支；
3. 窗口容量扣除现有在途分支后正确计算；
4. 同一 parent_node_id + operator_id 不能被领取两次；
5. 一个窗口内出现精确重复时，重试和兄弟去重仍按确定顺序执行；
6. Qwen 决策完成可推进搜索，GPT 状态仍保持待补齐；
7. GPT 补齐后 trial/repeat 顺序与旧评分结果一致；
8. 搜索状态升级和旧状态恢复具有明确兼容行为。

### 9.2 集成测试

使用固定模拟模型响应，对同一输入分别运行：

- 基线：branch_window=1，step 模式，GPT 同步
- 候选：branch_window=3，目标调度模式，GPT 异步

必须比较：

- 每个父节点的算子尝试集合；
- 每个分支的候选文本和稳定 ID；
- 校验结果；
- Qwen answer trial 和 Judge repeat；
- Qwen 聚合分数；
- 分支状态和边界候选集合；
- 样本终止原因；
- Memory 写入内容与幂等键；
- GPT 实验结果完整性；
- 中断恢复后的最终业务投影。

允许不同的字段仅限于运行时间、队列顺序、trace ID 和新增调度诊断字段。

### 9.3 故障恢复测试

在以下位置主动中断并恢复：

- 分支已领取但未发送生成请求；
- 题目已生成但未完成校验；
- 参考答案已发布但 Rubric 未生成；
- Qwen 决策已完成但 GPT 实验评测未完成；
- 一个窗口内部分分支完成、部分分支仍在途；
- 样本刚达到边界目标但搜索状态尚未正式发布。

每次恢复必须证明：

- 已完成阶段不重复调用；
- 在途分支不丢失；
- 边界计数不重复增加；
- Memory 不重复追加；
- 最终产物可通过 manifest 校验。

## 10 灰度发布与回滚

### 10.1 发布顺序

1. 先合入终止状态修复，保持窗口为 1；
2. 使用固定模拟响应完成等价性测试；
3. 在 3 至 5 条真实样本上启用窗口 2；
4. 确认请求池、错误率和边界结果正常后启用窗口 3；
5. 单独启用 GPT Judge 异步补齐；
6. 稳定后再启用流式阶段调度；
7. 算子收益排序和状态瘦身最后独立灰度。

每个阶段只改变一个主要变量，避免无法归因性能变化或结果差异。

### 10.2 回滚策略

所有结构性优化必须保留兼容开关：

- 将 SEARCH_BRANCH_WINDOW 设为 1，恢复单分支波次；
- 将 SEARCH_PIPELINE_MODE 设为 step，恢复现有阶段编排；
- 关闭 GPT 延后评测，恢复同步双 Judge；
- 将算子排序设为 route，恢复现有顺序；
- 状态版本不兼容时拒绝在原实验目录继续运行，不自动降级或混写。

回滚不得删除已发布分支产物。恢复旧调度前应从稳定分支 ID 和 operator 状态重建待处理集合。

## 12 建议实施优先级

建议按以下优先级推进：

```text
P0 终止状态与幂等修复
  -> 防止重复搜索，先保证正确性

P1 动态分支窗口，默认灰度值 3
  -> 直接减少搜索波次，提高现有阶段并发利用率

P1 GPT 实验 Judge 解耦
  -> 不改变在线决策，缩短搜索关键路径

P2 按分支推进的阶段流水线
  -> 消除跨样本和跨阶段的批次屏障

P2 算子单位时间收益排序
  -> 更早达到边界目标，减少实际算子尝试数

P3 搜索状态瘦身与流式聚合
  -> 支撑更大样本量和更宽窗口
```

完成 P0 和 P1 后，应先用真实运行数据重新测量各阶段墙钟时间、请求池利用率和每小时完整分支数，再决定是否进入更复杂的流式编排。这样可以优先获得主要收益，同时控制一次性架构改造范围。

## 15 实验产物存储收敛（2026-07-26）

为避免完整记录在每个阶段和 checkpoint 中按固定倍数长期保留，新增
`SEARCH_ARTIFACT_RETENTION=compact|full`，默认使用 `compact`：

- 主阶段的新 checkpoint 原子落盘后立即删除更早的主阶段快照；
- `decision_consumed` 只保存稳定 `branch_id` 标记，不再复制完整评分记录；
- 成功分支只保留 `final.json`，失败分支只保留 `branch_error.json`；
- stream 分支形成追加式正式结果或失败结果后，删除其阶段工作目录；
- step 模式仅在最终搜索状态、分支 sidecar 和 manifest 成功发布后删除 `wave_*`；
- `branch_results.jsonl`、轻量搜索状态、终态 checkpoint、性能事件和汇总继续保留。

该策略把已完成 stream 分支的中间存储从“分支数乘阶段数份完整记录”收敛为每分支
一份正式结果加一份终态恢复记录。运行中的峰值由有界分支窗口控制。`full` 作为诊断
回滚开关，保留旧版全部中间文件；两种模式不改变评分、边界判定、Memory 或 JSONL
业务字段。
