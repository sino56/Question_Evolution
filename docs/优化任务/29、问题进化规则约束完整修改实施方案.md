- 历史兼容：保留现有 JSONL 字段，不强制迁移历史数据；新增信息优先写入既有嵌套结构，旧记录继续走兼容 fallback；

## 0. 文档关系与优先级

本方案是第 28 号 v2.2 规则约束方案的工程实施计划。三份文档的层级固定为：第 28 号是唯一上位规则规范，第 27 号是题面职责隔离与全算子语义泄漏专项治理方案，本方案负责代码、Schema、Pipeline、测试、发布与回滚。若本方案与第 27 号存在语义冲突，以第 28 号为最终基准；若本方案尚未覆盖第 28 号中的规则，不得将该规则视为已经实施。

第 27 号方案中以下内容继续保留：

1. 父题解析、隐藏规划、盲题面编写和独立校验的职责隔离；
2. O14 作为全局信息闭包原则，不生成独立题面；
3. O10–O33 全量治理，而不是只修复少数已暴露算子；
4. 语义泄漏、竞争存活、消融和表面交换检查；
5. 新校验器先 shadow，再逐步 enforce；
6. weak risk 保留 exploration 机会；
7. `score_increased` 始终表示负收益。

第 28 号方案新增或修正以下关键约束，本方案必须完整落实：

1. 显式区分 `source_case_world` 与 `hypothetical_training_world`；
2. 显式支持 `source_faithful`、`controlled_synthesis`、`hypothetical_adaptation_from_source` 和 `pass_through` 四种模式；
3. 在任务显式授权且样本资格通过后，允许受控合成观察事实，但不允许自由编造真实规则、专业阈值和答案结论；
4. 每项事实必须具有 `world_id`、来源类型和设计职责；
5. 旧参考答案、Rubric、Score Prompt 和旧分数在题目实质变化后必须隔离并重建；
6. 结构校验通过只能表示可进入实验，不能表示已经有效变难；
7. 弱竞争、算子重叠和潜在收益不确定应进入重试或有预算的模型探索，不应自动 hard reject 或默认转人工复核；
8. 真实有效进化必须由多次回答、重新评分、目标错误命中和强答案稳定性共同确认。
9. `controlled_synthesis` 和 `hypothetical_adaptation_from_source` 默认关闭，必须同时通过任务显式授权与样本资格门禁；
10. 来源事实必须具有稳定 locator 与 `global_fact_key`，真实规则必须具有来源、版本、适用范围和时效状态；
11. 每个候选必须声明 `conclusion_contract`，唯一答案要求必须具有公开事实与有效规则依据；
12. 适用的语义校验统一使用 `passed/failed/unresolved`，不适用时使用 `not_applicable`；低风险不确定项进入有预算的模型实验，高风险不确定项才转人工复核或透传；
13. 统一扩展泄漏标签、定向重试、统计与回放夹具；
14. 每次运行必须受 `execution_scope` 限制；正式迭代必须显式跑完整闭环，离线结构优化只作为开发、调试和回放配置。

### 0.1 工程术语与产物边界

本方案使用的若干工程术语含义如下：

| 术语 | 含义 | 例子 |
|---|---|---|
| contract | 跨模块必须共同遵守的语义和字段约束 | Mode contract规定授权与资格必须同时满足 |
| schema | 对字段类型、必填项和枚举的机器可验证描述 | JSON Schema验证`validity_status`枚举 |
| artifact | 某个Pipeline阶段产生、可恢复和校验版本的正式产物 | 新reference、Rubric、answers、scoring result |
| sidecar | 与主JSONL分离、按candidate identity受限读取的隐藏产物 | hidden plan文件 |
| trace | 一次调用的可审计身份和输入版本信息 | `writer_input_trace_id` |
| gate | 阶段执行前的确定性准入检查 | authorization gate、scope gate、slot gate |
| shadow | 只记录新判断，不改变正式分流 | 新泄漏标签先观察误报率 |
| enforce | 新判断开始影响重试、拒绝或流程停止 | 未授权合成被阻止 |
| fallback | 新字段缺失时采用的兼容路径 | 历史记录继续legacy处理 |

contract 与 schema 不能互相替代。Schema 可以证明字段存在且类型正确，但不能证明“任务授权确实来自可信配置”或“规则真的适用于当前对象”；这些语义仍需要 gate 和 Validator 检查。

文中的不同 Judge/Verifier 也不能混用：

| 角色 | 检查对象 | 输出用途 |
|---|---|---|
| Semantic Validator | 最终题面与hidden control | 判断来源、泄漏、竞争和控制检查 |
| Reference Verifier | 新题、新reference与公开事实账本 | 判断答案是否可由题面推出、是否偷用hidden fact |
| Scoring Judge | 最终题面、弱模型答案与新Rubric | 产生新题分数 |
| Effect Analyzer | 多次评分、错误证据与替代原因 | 判断降分是否命中目标能力 |

同一个底层模型可以承担不同角色，但请求、输入白名单、输出Schema和trace必须独立。Semantic Validator给出的“题面可答”不能替代Reference Verifier，Scoring Judge给出的低分也不能替代Effect Analyzer的归因。

### 0.2 一个候选的端到端身份

同一个候选在不同阶段必须由以下身份共同绑定：

```text
sample_id
+ round
+ candidate_group_id
+ candidate_id
+ world_id
+ contract/schema/prompt revision
```

例如，`candidate_id=C03` 的 hidden plan、public projection、新reference和Rubric必须全部指向同一组身份与版本。只比较 prompt 文本不够，因为两个样本可能具有相同题面但不同来源、world或参考答案。任何 sidecar 或artifact身份不匹配都属于L0失败，不能“就近复用”。

## 1. 摘要

当前项目已经具备多算子路由、候选生成、轻量校验、难度收益校验、探索候选分流、真实回答与评分、效果分析和 Memory 收敛，但问题进化的事实来源和信息职责仍未形成统一闭环。

现有实现同时存在两种相反倾向：

1. Rule Router 可能根据诊断关键词强制选择算子，即使题面没有满足构题槽位；
2. Hybrid Router 又要求所有槽位必须已由题面给出，因此无法执行合法的受控合成。

生成侧虽然已经尝试隔离参考答案和 Rubric，但仍把未经拆分的原题全文作为可观察事实，并可能从旧参考答案中启发式抽取所谓观察事实。题面 Writer 还被要求同时输出 `expected_qwen_failure` 等隐藏结构信息，职责隔离并不彻底。

评分侧存在更严重的污染风险：弱模型回答阶段会收到旧答案边界和旧 Rubric 意图；题目变化后，旧参考答案没有真正重建，Rubric 仍可能基于旧 `meta_info.references` 生成；旧 `score_rate` 也缺少明确的 `not_evaluated` 状态。

因此，本方案不以追加禁词为核心，而是建立以下完整闭环：

```text
任务授权与执行范围
-> 来源世界识别
-> 原始输入拆分
-> 进化模式选择
-> 模式感知算子路由
-> 隐藏结构规划与事实账本
-> Writer 可见事实投影
-> 盲题面编写
-> 独立来源/可答性/泄漏/控制校验
-> 定向重试或候选分流
-> 新参考答案重建与核验
-> 新 Rubric / Score Prompt 重建
-> 弱模型仅看题面作答
-> 重新评分与效果归因
-> Memory 更新
-> 下一轮机器决策
-> 继续同算子 / 换算子 / 返回父题 / 停止分支
```

### 1.1 本方案中常见工程术语的含义

为避免把不同层次的机制混为一谈，本文统一使用以下含义：

| 术语 | 含义 | 不等于 |
|---|---|---|
| 规则 `rule` | 第28号规定的语义要求 | 某个Python条件分支 |
| 数据契约 `contract` | 阶段之间约定字段、枚举、权限和状态迁移 | 仅有一个JSON示例 |
| Schema | 对字段类型、必填项和枚举做机器校验 | 完整业务语义校验 |
| Runtime policy | operator当前是否enabled、suspended或仅forced | operator的题型定义 |
| Artifact | 某阶段产生并供下游消费的版本化文件或记录 | 任意临时变量 |
| Sidecar | 与主JSONL分离、通过trace ID关联的受限工件 | 可以被所有下游读取的隐藏顶层字段 |
| Shadow | 计算并记录新结果，但不改变正式分流 | 校验已可信或已发布 |
| Enforce | 新契约正式参与门禁和分流 | 所有不确定结果都hard reject |

例如，Schema可以验证 `world_id` 是字符串，却不能判断两条事实是否真的属于同一案例；后者需要事实来源和语义校验。又例如，operator prompt写得正确，也不表示该operator已获得自然路由资格，仍需runtime policy和forced qualification共同控制。

## 2. 当前实现基线与差距

### 2.1 已有能力

当前实现中以下部分应尽量保留：

1. `prompts/operators/` 已注册 O10–O33；
2. O14 已设置为 `generates_question=False`；
3. 公共 operator prompt 已包含单一自然判断、反显式脚手架、反格式复杂化和语义经济约束；
4. Hybrid Router 已有 required slots、相邻算子边界和严格响应契约；
5. `candidate_selection.py` 已有四类候选分流；
6. 现有兼容逻辑会让 `weak_gain` 和旧 `needs_manual_review` 在无 hard risk 时进入 exploration；新契约必须把两者拆开：`weak_gain` 仍可探索，新的高风险 `needs_manual_review` 不得直接评分；
7. `score_increased` 已按负收益处理；
8. 正式阶段失败会写入 `*.failed` 并以非零状态退出；
9. 现有主流程已支持多候选、候选选优、真实回答、多次评分和效果分析。

### 2.2 当前核心差距

#### 2.2.1 缺少来源世界和进化模式

当前记录没有统一、稳定地表达：

```text
source_world_status
evolution_mode
world_id
mode_reason
synthesis_eligibility
```

因此系统无法区分：

- 真实案件事实不能改变；
- 抽象方法题可以构造新假设案例；
- 来源原理可以改编为独立假设案例；
- 无法安全进化时应该透传。

#### 2.2.2 当前 observable ledger 不是真正事实账本

`semantic_budget.py` 当前把完整父题作为单一 observable entry，并可能从参考答案中按关键词抽取观察事实。这不能可靠区分：

- `source_observation`；
- `source_claim`；
- `task_presupposition`；
- `comparative_direction`；
- `derived_summary`；
- `answer_direction`；
- `provided_rule_primitive`。

#### 2.2.3 Router 存在规则路由与 Hybrid 路由语义分裂

当前 Rule Router 更偏向“诊断关键词命中即选择算子”，并存在默认 O10 fallback；Hybrid Router 则要求所有 hard slots 已在题面中出现且不能补造事实。

第 28 号方案要求的正确语义是：

- source-faithful：槽位必须由来源事实满足；
- controlled-synthesis：观察级槽位可以合法合成；
- adaptation：在新 world 中合法合成；
- 真实规则、专业阈值等不可合成槽位缺失时透传。

#### 2.2.4 Writer 信息权限仍过宽

当前 Writer 仍能看到完整 `original_question`，并被要求输出：

```text
evolution_strategy
target_subclaim
boundary_hypothesis
expected_qwen_failure
expected_evaluation_focus
```

这些字段属于隐藏规划和评测意图，不应由盲题面 Writer 同时生成。

#### 2.2.5 factual validator 不支持受控合成

当前 `light_factual_check.py` 会把新增数字、时间、比例和金额直接视为高置信致命风险。这对 source-faithful 是合理的，但会错误拒绝已获任务授权且已登记的 controlled synthesis 和 hypothetical adaptation。

#### 2.2.6 校验器缺少完整控制检查

当前校验主要集中在：

- 主轴数；
- 输出任务数；
- 候选项数；
- 反事实数；
- 外部知识词面；
- 格式复杂度词面；
- 已知泄漏短语；
- LLM 语义风险判断。

尚未形成以下闭环：

- 逐句事实来源映射；
- 单 world 一致性；
- mode compliance；
- 决定性事实消融；
- 无关事实消融；
- 名称交换；
- 顺序交换；
- 信息量平衡；
- 竞争解释存活；
- 新参考答案只依据新题事实可推出。

#### 2.2.7 旧评分材料污染

当前进化记录会保存旧参考答案、旧 Rubric、旧评分结果和旧分数，但缺少统一状态机。更关键的是：

1. `collect_answers.py` 会把旧 answer boundary 和 Rubric intent 拼入模型回答上下文；
2. `gen_rubric.py` 仍从 `meta_info.references` 读取参考答案；
3. 题目变化后没有独立的新参考答案重建阶段；
4. 新题正式评分前，旧 `score_rate` 可能仍然存在于活动记录中。

这会导致旧答案被当作新答案、新题分数被旧分数污染、弱模型获得额外提示，最终破坏难度归因。

#### 2.2.8 结构收益与真实有效进化混用

当前 difficulty validator 使用 `clear_gain`、`probable_gain` 等标签。若没有明确限定，这些名称容易被误认为已经证明题目有效变难。

第 28 号方案要求：真实回答和重新评分前，只能表示结构通过、潜在收益或需要探索。

#### 2.2.9 授权、追溯、结论与执行边界仍未闭合

现有设计尚未统一表达：

- 任务是否显式授权 `controlled_synthesis` 或来源改编；
- 来源事实的逐字 span、JSON Pointer、记录 ID、页码/行号和内容哈希；
- 真实规则的版本、适用对象、适用场景与当前有效状态；
- 题目允许的结论类型以及唯一答案的保证依据；
- 语义校验无法可靠判断时的 `unresolved`；
- `hypothesis_status_disclosure` 等完整泄漏标签；
- 本次任务允许执行到参考答案、模型回答、Judge 还是效果确认。

如果不补齐这些契约，Source Analyzer 可能把资格当授权，Validator 可能把未知当通过，运行器也可能越过离线任务边界继续调用模型与评分。

### 2.3 必须补齐的三个受控合成闭环

当前方案虽然已经定义了 `controlled_synthesis`，但仅有模式名称、Schema 或 Prompt 说明并不代表该能力已经可用。受控合成必须同时完成下面三个闭环；缺少任意一个，都不能声明“支持通过新增人物、时间和行为构造假设案例”。

#### 2.3.1 受控合成必须真正进入主流程

需要打通的不是单个生成 Prompt，而是完整链路：

```text
任务授权
-> Mode Decider 选择 controlled_synthesis
-> Router 将观察级缺失槽位标记为可合法合成
-> Hidden Planner 登记新增人物、时间、地点、动作和题内参数
-> Writer 只使用已登记公开事实生成题面
-> factual validator 按 mode 和 fact ledger 校验
-> 新参考答案与新 Rubric 重建
```

Validator 必须区分两类新增内容：

- 已授权、已登记、属于当前假设 world 的观察事实：允许；
- 未授权、未登记、混入其他 world，或伪造真实规则/专业阈值的内容：拒绝或透传。

不能继续使用“只要新增人物、时间、动作或数值就统一拒绝”的规则；也不能因为处于合成模式，就放行所有新增内容。判断依据必须是 `mode + authorization + world_id + fact_id + origin_type`，而不是只比较新旧题面字符串。

完成标准：至少有一条抽象原题能够在显式授权后生成包含新增实体和事件链的合法候选；同一输入在未授权时必须透传；已授权但出现未登记事实时必须被拦截。

#### 2.3.2 受控合成必须由任务配置显式开启

受控合成默认关闭。样本“适合合成”、Router“希望补槽位”或算子“支持合成”都不能自动授予权限。

正式入口必须先读取任务级配置：

```json
{
  "allowed_evolution_modes": ["source_faithful", "controlled_synthesis"],
  "controlled_synthesis_authorized": true,
  "authorization_source": "task_config",
  "authorization_id": "可审计的任务授权编号"
}
```

只有同时满足以下条件才能进入受控合成：

```text
模式在 allowed_evolution_modes 中
AND controlled_synthesis_authorized = true
AND 样本具备合成资格
```

配置缺失、字段解析失败、授权来源不可审计或样本资格不成立时，不得静默开启合成，应转为 `source_faithful` 或 `pass_through`，并记录具体原因。

#### 2.3.3 必须先构造隐藏完整场景，再生成公开题面

受控合成不能让 Writer 一边编故事、一边决定正确答案。系统应先在隐藏层确定同一个假设 world 中的：

- 实体及其真实关系；
- 完整事件时间线和状态变化；
- 每条观察事实对应的 `fact_id`；
- 竞争解释及其可存活范围；
- 正确答案或允许的结论上限；
- 保证答案唯一、或保证“证据不足”确实成立的依据。

隐藏场景先通过一致性检查，再编译为公开事实。Public Fact Compiler 只能输出可观察行为、记录和明确声明的题内参数，并删除真实关系、角色标签、事实重要性、正确解释、答案轮廓和推理链。Writer 只能看到这份公开投影，不能看到 hidden plan、旧答案、Rubric 或预期模型错误。

这里的“先确定正确答案”不是要求题面必须具有武断的唯一结论。如果任务目标是判断证据是否充分，隐藏层可以把正确答案设为“现有观察只支持到某一程度，无法排除竞争解释”；但这个答案边界必须由隐藏 world 和公开事实共同保证，不能在题面生成完成后临时猜测。

若隐藏场景存在事实矛盾、答案无法由拟公开事实推出，或公开事实已经直接写出真实关系和答案，候选不得交给 Writer，应返回 Hidden Planner 定向修正或结束当前候选。

#### 2.3.4 三项能力必须作为同一个功能切片验收

不允许按以下方式分别宣布完成：

- 只增加 mode 字段，但 Router 和 Validator 仍按旧规则运行；
- 只增加授权配置，但正式入口没有读取和执行；
- 只增加 hidden plan 字段，但 Writer 仍能看到正确答案；
- Writer 已隔离，但新参考答案仍沿用原题答案；
- Validator 放行新增事实，但没有 fact ledger 和 world 约束。

三项闭环的联合验收必须证明：默认不合成；显式授权后可以合法新增观察事实；未登记新增内容仍被拦截；Writer 请求中没有隐藏答案信息；新题使用与新场景一致的新参考答案和 Rubric。

## 3. 目标、非目标与不可破坏约束

### 3.1 目标

本方案必须实现：

1. 每个候选在生成前都具有明确的来源世界判断；
2. 每个候选显式选择四种进化模式之一；
3. 每个可见事实都能追溯到 source observation、controlled hypothetical observation、provided rule primitive 或 task-local parameter；
4. 一个候选中的全部可见事实属于同一 world；
5. 每项新增事实都具有明确设计职责；
6. 隐藏规划器与盲题面 Writer 使用不同输入白名单；
7. O10–O33 均具有 mode-aware slots、禁止合成项和专属控制测试；
8. O14 成为全局信息闭包和来源校验原则；
9. hard reject、定向重试、exploration 和 pass-through 的语义严格分开；
10. 题目变化后旧参考答案、Rubric、Score Prompt 和评分结果进入 stale 状态；
11. 新参考答案和 Rubric 只依据新题与新事实账本重建；
12. 弱模型回答只看到最终题面，不看到旧答案、Rubric、隐藏计划和 Judge 意图；
13. 真实效果确认依赖多次回答、稳定评分、目标错误命中和强答案正确性；
14. 历史 JSONL 不强制迁移，旧记录仍能运行；
15. 保持 `score_increased` 的负收益语义。
16. 任务授权与样本资格分离，合成和来源改编缺省关闭；
17. 来源事实与真实规则具有可验证、稳定且版本化的追溯信息；
18. 每个候选具有明确 `conclusion_contract`；
19. 适用的语义检查统一使用 `passed/failed/unresolved`，不适用时使用 `not_applicable`；低风险未知状态进入模型探索，高风险未知状态才进入人工复核或透传；
20. 完整泄漏标签在 Validator、重试、统计、Memory 和回放测试中保持一致；
21. `execution_scope` 阻止任何未授权阶段，但不改变完整 Pipeline 的目标；正式入口缺少完整配置时必须在启动前失败。

### 3.2 非目标

本方案不做：

- 不引入完整树搜索、BFS、DFS、UCB 或深层 parent stack；
- 不实现 boundary bank 或 fork task，除非另有明确任务；
- 不重写 `gen_rubric.py` 和 `scoring.py` 的核心评分 Prompt；
- 不删除或重命名现有稳定 JSONL 字段；
- 不强制迁移历史实验产物；
- 不把所有结构不确定候选 hard reject；
- 不用题长、格式和任务数替代真实推理难度；
- 不允许 Memory 或 Global Judge 自动修改正式 operator prompt；
- 不把结构校验分数当成最终效果分数。

### 3.3 不可破坏约束

实施过程中必须保持：

1. 每个 candidate group 最多选择一个 exploration candidate；
2. 每轮 exploration 总预算继续生效；
3. hard label、hard risk 和模板化简化信号覆盖 exploration；
4. `score_increased` 不进入成功终止态，不写 operator success memory；
5. 相同 prompt 的不同样本继续按 `sample_id` 保留；
6. 正式阶段失败继续 fail-fast；
7. 不提交真实 API key、base URL 和本地配置；
8. 不把大型 `experiments/` 产物纳入常规提交。

## 4. 目标架构

### 4.1 主流程目标形态

调整后的推荐主流程为：

```text
admitted_seed_samples.jsonl
-> load_task_authorization_and_execution_scope
-> execution scope gate for round0 answer/Judge calls
-> round0_stability_probe.py
-> profile_samples.py
-> select_evolution_candidates.py
-> operator_router.py
-> question_evolution.py
   -> source analysis
   -> mode decision
   -> hidden planner
   -> public fact projection
   -> blind surface writer
-> validate_evolved_question.py
-> light_factual_check.py
-> validate_difficulty_gain.py        # 只判断结构潜力，不确认有效进化
-> candidate_selection.py
-> execution scope gate
-> rebuild_reference_answer.py        # 新增
-> gen_rubric.py                       # 使用新参考答案
-> collect_answers.py                  # 弱模型只看题面
-> scoring.py
-> analyze_evolution_effect.py
-> update_sample_state.py
-> build_next_round_decision           # 可在 update_sample_state.py 内实现
-> 下一轮输入 / 分支终止
```

与当前主流程相比，主要变化是：

1. `question_evolution.py` 内部增加职责隔离子阶段；
2. 新增参考答案重建阶段；
3. `gen_rubric.py` 移到 `collect_answers.py` 之前；
4. `collect_answers.py` 不再注入答案侧边界材料；
5. `validate_difficulty_gain.py` 只输出预测性结构收益，不确认有效进化；
6. 真实成功仍由 `analyze_evolution_effect.py` 和 `update_sample_state.py` 决定。
7. Mode Decider 在样本资格之外必须检查任务级模式授权；
8. 每个下游阶段必须先通过 `execution_scope`；开发工具未授权时在允许的最大阶段正常停止，正式迭代入口缺少完整授权时应在启动前报告配置错误。
9. 效果分析和 Memory 更新后必须产出下一轮机器决策，使流程能够自动继续、换算子、返回直接父题或终止分支。

这里的“调整顺序”只发生在候选选中后的评分准备子流程。以下问题进化前半段保持主体结构：

```text
路由 -> 题目生成 -> 题面校验 -> 候选选择
```

因此，第 27 号方案所说的“主链保持”与本方案并不要求推翻整个 Pipeline；本方案只是为新题版本的评分材料隔离，增量调整后半段依赖关系。

一个正式运行候选的典型生命周期如下：

```text
sample S01
-> Source Analyzer：判定为abstract_method_question
-> Authorization Gate：任务允许controlled_synthesis
-> Mode Decider：选择controlled_synthesis并创建world hyp_S01_01
-> Router：O22的观察槽位可合成，真实规则槽位不缺失
-> Planner：建立事实账本、竞争解释和结论契约
-> Public Compiler：去除answer_role等隐藏字段
-> Writer：只根据公开事实写题面
-> Validator：结构通过，但竞争存活检查unresolved
-> Candidate Selection：低风险unresolved，进入exploration_candidate
-> Reference Rebuilder与强模型：重建并核验新答案，确认题目可答
-> Rubric Builder：按新题生成评分标准
-> Weak Answer Model：多次回答新题
-> Scoring Judge：多次评分
-> Effect Analyzer：确认是否命中目标错误
-> Memory：写入成功或失败经验
-> Next Round Decision：继续O22、换算子、返回父题或停止当前分支
```

例如，两个 Validator 对竞争车辆是否足够有迷惑性意见不一，但题面来源、规则和答案都安全，这种不确定更适合用真实模型回答解决，不应把候选默认停在人工复核。若无法确认通行规则是否有效，则会改变正确答案，才应停止当前候选并复核或透传。

`structure_debug` 可以在 Candidate Selection 后停止，用于调试上述前半段；它不是这里的典型生产路径，也不能产生有效进化结论。

### 4.2 信息权限矩阵

| 阶段 | 可以看到 | 不可以看到 |
|---|---|---|
| Source Analyzer | 原题、来源材料、旧答案和 Rubric 的存在状态 | 不把旧答案当事实来源 |
| Mode Decider | source analysis、来源性质、显式任务授权 | 不依据主题词直接选择模式，不得把 eligibility 当 authorization |
| Operator Router | source analysis、mode、slot 状态、目标 failure | 不编写题目，不补造事实 |
| Hidden Planner | operator 完整契约、事实池、目标错误、竞争结构、旧材料仅供审计 | 不直接输出自然题面 |
| Public Fact Compiler | 完整 ledger、mode policy | 不输出 answer role、正确解释和决定性标签 |
| Surface Writer | public facts、中性任务意图、表面要求 | 正确答案、旧答案、Rubric、目标错误、answer role、Judge 逻辑 |
| Structural Validator | 候选题、完整 ledger、hidden plan、source analysis | 不参与生成 |
| Reference Rebuilder | 新题、完整 ledger、hidden plan | 旧答案不得作为新答案正文来源 |
| Reference Verifier / 强模型 | 新题、新参考答案、公开事实和有效规则 | 不使用隐藏事实补齐答案，不代替弱模型实测 |
| Rubric Builder | 新题、已核验的新参考答案 | 旧 Rubric 只能审计，不能复制为活动 Rubric |
| Weak Answer Model | 最终题面 | 任何 reference、Rubric、hidden plan、validator feedback |
| Scoring Judge | 最终题面、弱答案、新 Rubric | 旧 Rubric、旧分数不得参与新题评分 |
| Effect Analyzer | 新旧评分、目标错误证据、强模型与 Judge 稳定性 | 不只凭分数下降宣布成功 |
| Next Round Decider | 效果结果、当前算子、父候选和有限 Memory | 不绕过授权、事实和安全门禁 |
| Execution Scope Gate | 已校验的执行范围、当前 stage、artifact status | 不得因脚本存在或模型可用而扩大本次任务权限 |

### 4.3 同一次模型调用的职责边界

以下职责不得由同一次调用同时完成：

```text
hidden plan + evolved_prompt
new reference answer + weak model answer
candidate generation + independent semantic validation
old-answer audit + new-answer正文生成
```

即使使用同一模型名称，也必须采用独立请求、独立输入白名单和独立 trace。

“独立 trace”至少应能证明：使用了哪个prompt/schema版本、输入中有哪些字段、输出对应哪个candidate、调用是否成功。审计日志可以记录字段名和哈希，不应记录会泄漏答案或敏感材料的完整正文。

独立请求不是把同一个大字典传入两个函数后在prompt模板中“提醒模型忽略某些字段”。真正的白名单应在序列化请求之前构造。例如：

```python
writer_input = {
    "public_facts": public_projection["public_facts"],
    "neutral_task_intent": public_projection["neutral_task_intent"],
    "surface_requirements": public_projection["surface_requirements"],
}
```

不得使用 `writer_input = sample.copy()` 后再删除若干已知字段，因为未来新增隐藏字段时容易遗漏。

### 4.4 贯穿示例的数据流

以“20:10车辆A离开东门、20:17同型号车辆进入北门、最快通行8分钟、存在另一辆同型号车辆”为例：

```text
Source Analyzer
-> 把时间、地点、车型和可见性拆成source observations
-> 不把“属于同一车辆”当观察事实

Mode Decider
-> 检查任务授权和样本资格
-> 若事实来自固定案例则选择source_faithful

Hidden Planner
-> 记录可能结论、竞争车辆、决定性组合和目标错误

Public Fact Compiler
-> 仅投影原子事实、题内参数和中性任务

Surface Writer
-> 写成自然题面，不出现“时间不可达”“另一车辆更合理”等解释

Validator
-> 检查来源、可答性、泄漏、竞争存活和交换控制

Reference Rebuilder
-> 只引用公开fact keys与有效规则生成新答案

Rubric Builder / Weak Model / Scoring Judge
-> 分别按白名单读取同一题目版本的产物
```

该例子的重点是，同一条“最快8分钟”在 ledger 中可以具有隐藏的决定性角色，但 Writer 只能看到参数文本；Reference Rebuilder可以用它推理，弱模型只能从最终题面自行发现它的重要性。

## 5. 统一数据契约

### 5.0 Task Authorization 契约

任务级授权必须在任何 mode decision 之前加载。默认关闭合成与来源改编：

```json
{
  "evolution_authorization": {
    "allowed_evolution_modes": ["source_faithful"],
    "controlled_synthesis_authorized": false,
    "hypothetical_adaptation_authorized": false,
    "authorization_source": "task_config",
    "authorization_id": "task_policy_001"
  }
}
```

强制要求：

- Source Analyzer 只输出样本 `eligibility`，不得授予模式权限；
- Mode Decider 同时检查 `allowed_evolution_modes`、对应布尔授权和样本资格；`pass_through` 作为安全退出始终允许，不要求列入生成模式白名单；
- 任一授权字段缺失、解析失败或来源不可审计时按 `false` 处理；
- 未授权时只能选择 `source_faithful` 或 `pass_through`；
- Router、Memory、operator qualification 和 slot completeness 均不能绕过该 gate；
- 授权允许某个模式，不代表允许合成真实规则、专业阈值或答案结论。

实现时建议把授权和资格分别保存，避免只保留一个模糊的 `allowed=true`：

```json
{
  "controlled_synthesis": {
    "authorized": true,
    "eligible": false,
    "decision": "not_selected",
    "reason": "样本依赖不可合成的真实专业阈值"
  }
}
```

最终可选择条件是 `authorized && eligible && mode_in_allowlist`。`pass_through` 是安全退出，不参与该布尔合取。

Mode Decider 的实现应近似以下逻辑，而不是让 LLM自由解释“允许”：

```text
if requested_mode == pass_through:
    allow
else if requested_mode not in allowed_evolution_modes:
    deny
else if requested_mode == controlled_synthesis:
    require controlled_synthesis_authorized and sample_eligible
else if requested_mode == hypothetical_adaptation_from_source:
    require hypothetical_adaptation_authorized and sample_eligible
else if requested_mode == source_faithful:
    require source_world and source_satisfied_slots
```

这里的伪代码只说明判定次序，不要求采用特定编程语言。拒绝原因要区分 `mode_not_whitelisted`、`mode_not_authorized` 和 `sample_not_eligible`，否则后续统计无法判断是配置问题还是样本问题。

### 5.1 Source Analysis 契约

建议新增可选嵌套结构：

```json
{
  "source_analysis": {
    "contract_version": "source_analysis_v1",
    "source_world_status": "source_case_world | abstract_method_question | training_question | source_principle_only | unknown",
    "source_observations": [],
    "source_claims": [],
    "design_only_principles": [],
    "provided_rule_primitives": [],
    "answer_directions": [],
    "derived_summaries": [],
    "manual_review_reasons": []
  }
}
```

建议写入：

```text
meta_info.question_evolution_metadata.source_analysis
```

每个拆分项至少包含：

```json
{
  "item_id": "S03",
  "type": "source_observation",
  "surface_text": "人员P于20时10分进入东门",
  "source_ref": "prompt:sentence_2",
  "source_locator": {
    "source_file": "...",
    "source_record_id": "record_018",
    "json_pointer": "/prompt",
    "source_span": "人员P于20时10分进入东门",
    "page_index": null,
    "line_start": null,
    "line_end": null,
    "source_hash": "sha256:..."
  },
  "confidence": 0.96
}
```

低置信度拆分不得自动升级为来源事实，应进入 manual review 或 pass-through。

每个来源事实至少必须具有一个可验证 locator。`source_ref` 仅作为兼容提示保留，不能成为新记录唯一的稳定定位依据。

不同介质的推荐定位方式：

| 来源介质 | 推荐 locator | 说明 |
|---|---|---|
| JSON / JSONL | `source_file + source_record_id + json_pointer + source_hash` | 记录顺序变化后仍可通过ID和pointer定位 |
| Markdown / 纯文本 | `source_file + line_start/line_end + source_span + source_hash` | 行号用于快速定位，span/hash用于检测漂移 |
| PDF | `source_file + page_index + source_span + source_hash` | 页码通常按程序内部0-based约定，UI展示时需明确转换 |
| 当前prompt | `json_pointer=/prompt + source_span + source_hash` | `prompt:sentence_2`只作人类提示，不作唯一键 |

`source_hash` 应基于规范化后的来源片段计算，规范化规则必须版本化，例如只统一换行和Unicode形式，不能删除会改变事实含义的数字、否定词或单位。hash不匹配表示来源可能漂移，应重新分析，而不是静默沿用旧fact ledger。

### 5.2 Evolution Mode 契约

```json
{
  "evolution_mode": {
    "mode": "source_faithful | controlled_synthesis | hypothetical_adaptation_from_source | pass_through",
    "mode_reason": "...",
    "world_id": "source_case_001 | hyp_case_001",
    "synthesis_eligibility": "not_needed | eligible | ineligible | needs_manual_review",
    "authorization_checked": true,
    "authorization_id": "task_policy_001"
  }
}
```

模式决策必须遵循：

1. 真实且不可修改的来源世界：优先 source-faithful；槽位不足则 pass-through；
2. 抽象方法题或训练题：可构造自包含案例时 controlled-synthesis；
3. 来源只提供方法原理：可用 adaptation，新建 world；
4. 需要真实法规、专业阈值或来源性质不明：pass-through/manual review；
5. 不能只根据文件字段、主题词或是否来自文档决定模式。
6. `eligible` 只说明样本适合合成；只有任务授权同时通过时才能选择合成模式。

### 5.3 完整事实账本契约

完整 ledger 仅供 planner、validator 和 reference rebuilder 使用：

```json
{
  "fact_id": "F07",
  "world_id": "hyp_case_003",
  "global_fact_key": "hyp_case_003::F07",
  "origin_type": "source_observation | controlled_hypothetical_observation | provided_rule_primitive | task_local_parameter",
  "surface_text": "车辆V在18时22分驶出园区西门",
  "source_ref": null,
  "source_locator": {
    "source_file": null,
    "source_record_id": null,
    "json_pointer": null,
    "source_span": null,
    "page_index": null,
    "line_start": null,
    "line_end": null,
    "source_hash": null
  },
  "entity_refs": ["vehicle_v"],
  "time_scope": "18:22",
  "slot_role": ["path_continuity"],
  "answer_role": "decisive_fact | competitor_support | relevant_distractor | answerability_support | natural_context",
  "design_basis": ["O22.required_slot.exit_observation"],
  "prompt_visible": true
}
```

强制要求：

- 一个候选中的全部事实必须使用同一个 `world_id`；
- `fact_id` 只在单个 world 内唯一，跨阶段稳定引用使用 `global_fact_key = world_id::fact_id`；
- 来源事实至少具有一个可验证 locator；受控假设观察和题内参数 locator 可为空，但必须保留授权、`origin_type` 和 design basis；
- source-faithful 只允许 source observation 和来源提供的规则；
- controlled/adaptation 新事实必须具有设计职责；
- 任何真实规则和专业阈值不得伪装成 task-local parameter；
- `answer_role`、`design_basis` 和正确竞争解释不得进入 Writer 输入。

真实规则另进入 `rule_ledger`：

```json
{
  "rule_id": "R01",
  "rule_text": "...",
  "source_locator": {
    "source_file": "...",
    "source_record_id": "record_018",
    "json_pointer": "/rules/0",
    "source_span": "...",
    "page_index": null,
    "line_start": null,
    "line_end": null,
    "source_hash": "sha256:..."
  },
  "applicable_subjects": [],
  "applicable_scenarios": [],
  "version": "2026-01",
  "effective_at": "2026-01-01",
  "expires_at": null,
  "validity_status": "current | expired | superseded | unresolved"
}
```

无来源、版本、适用范围或当前有效性无法确认的规则不能作为真实规则进入题面；只有明确声明为当前假设题内部条件时才可作为 `task_local_parameter`，且不得冒充真实法律、行业或专业规范。

实现 `source_hash` 时必须固定规范化算法并版本化，例如：

```text
source_hash_algorithm = sha256
source_normalization_version = text-normalization-v1
```

`text-normalization-v1` 可以约定统一为LF换行、去除行尾空格、保留正文标点与大小写。若 locator仍能找到记录但哈希不一致，表示来源内容可能发生变化，应将事实或规则状态置为 `unresolved` 并重新分析，不能静默复用旧缓存。

`global_fact_key` 用于稳定引用，不应依赖数组下标。例如事实排序后，`facts[2]` 可能指向不同内容，而 `hyp_case_003::F07` 仍指向同一账本项。删除或重建事实时不得把旧key复用于不同语义内容。

规则处理分为两个不同阶段：

```text
Rule Registry检查：规则来源、版本、时效是否有效
-> Hidden Planner / 回答者判断：有效规则是否适用于当前对象和事实
```

例如，规则R3在2026年有效且适用于园区车辆身份判断，因此可以作为题面输入；但当前记录是否满足R3的时间、路径和排他条件仍是待推理问题。工程实现不得因为 `validity_status=current` 就预填 `rule_applies=true`。后者属于隐藏答案或回答结果。

若规则版本未知，正确状态是 `unresolved` 并进入 manual review/pass-through；若任务明确写“本题仅规定：两点最快通行时间为8分钟”，它是 `task_local_parameter`，无需伪造外部版本号，但必须在题面中明确其局部性质。

### 5.4 Writer Public Projection 契约

Writer 只能看到：

```json
{
  "world_disclosure": "以下为假设训练案例",
  "public_facts": [
    {
      "fact_id": "F07",
      "surface_text": "车辆V在18时22分驶出园区西门",
      "origin_type": "controlled_hypothetical_observation"
    }
  ],
  "neutral_task_intent": "根据全部记录作出判断，并说明最关键的依据",
  "surface_requirements": {
    "single_primary_axis": true,
    "single_core_output": true
  }
}
```

Writer projection 中禁止出现：

```text
answer_role
design_basis
correct_answer
decisive_fact_ids
wrong_competitor_id
target_failure_mode
expected_qwen_failure
expected_evaluation_focus
rubric
reference_answer
old_score
```

`prompt_visible=true` 只表示该账本项具备进入题面的资格，不表示 Writer 必须使用它。Public Compiler还应根据事实预算、重复性和题目可答性选择最小公开集合。反过来，`prompt_visible=false` 是硬禁止，不能因为Writer认为该事实“有助于说明”而加入。

Public Projection应是新对象，不应与完整ledger共享可变引用。否则后续代码给公开事实追加说明时，可能反向污染隐藏账本或把 `answer_role` 一并序列化。

`fact_id` 出现在 Writer 输入中只用于生成后核对 `used_fact_ids`，不应自然语言化为“根据事实F07”。若担心模型把内部编号写入题面，可以在调用边界把事实映射为临时无语义序号，并在返回后恢复到正式 fact key。无论采用哪种方式，映射必须确定、可审计，不能靠文本相似度猜测 Writer 使用了哪条事实。

Public Fact Compiler 的职责是过滤与投影，不是第二个生成器。它可以：

* 删除 `answer_role`、`design_basis` 和 hidden-only facts；
* 将规则账本投影为题目求解所需的原始规则文本；
* 附加“以下为假设案例”等 world disclosure。

它不能：

* 为了让题目更顺畅而补写新事件；
* 把多个原子事实总结成因果句；
* 根据正确答案选择更有暗示性的表述。

### 5.5 Hidden Plan 契约

```json
{
  "hidden_plan_version": "hidden_plan_v1",
  "operator_id": "O22_path_topology_reachability",
  "primary_axis": "path_topology_joint_reachability",
  "auxiliary_axis": "time_reachability",
  "target_claim": "...",
  "correct_answer_outline": "...",
  "conclusion_contract": {
    "admissible_outcomes": ["supports_h1", "supports_h2", "insufficient_evidence", "cannot_distinguish", "candidate_set_expanded"],
    "unique_answer_required": false,
    "uniqueness_basis": []
  },
  "competing_interpretations": [],
  "decisive_fact_ids": [],
  "relevant_distractor_fact_ids": [],
  "required_inference_obligations": [],
  "expected_weak_model_failure": "...",
  "forbidden_surface_propositions": [],
  "control_plan": {
    "decisive_ablation": [],
    "distractor_ablation": [],
    "name_swap": [],
    "order_swap": []
  }
}
```

完整 hidden plan 优先写入已注册的压缩 sidecar，并在记录中只保存 trace ID：

```text
meta_info.question_evolution_metadata.hidden_plan_trace_id
```

不得把完整正确答案结构长期放入所有下游阶段都能读取的普通顶层字段。

`conclusion_contract` 是每个候选必填的隐藏契约。`unique_answer_required=true` 时，`uniqueness_basis` 必须引用公开 `global_fact_key` 和当前有效 `rule_id`；否则 Reference Rebuilder、Rubric Builder 和 Validator 不得强制唯一答案。Writer 只接收中性任务意图，不接收正确 outcome 或唯一性依据。

Sidecar 至少应绑定：

```text
sample_id
candidate_id
round
hidden_plan_version
content_hash
created_at
```

加载时必须同时校验身份和哈希，不能只凭文件名读取。candidate重试产生新题面后，应生成新的sidecar版本或明确父子关系，避免旧hidden plan被错误用于验证新题。

“压缩sidecar”是减少主记录暴露面，不是省略关键审计信息。若压缩后无法还原决定性事实、结论契约或控制计划，Validator和Reference Rebuilder将无法可靠工作。

### 5.6 评分材料状态契约

题目发生实质变化后写入：

```json
{
  "artifact_status": {
    "reference_answer_status": "pending_rebuild",
    "rubric_status": "pending_rebuild",
    "score_prompt_status": "pending_rebuild",
    "scoring_status": "not_evaluated"
  }
}
```

状态迁移：

```text
pending_rebuild
-> rebuilt
-> independently_verified

rubric pending_rebuild
-> rebuilt

scoring not_evaluated
-> answers_collected
-> scored
```

旧材料只允许保存在：

```text
meta_info.parent_snapshot
meta_info.stale_references
meta_info.stale_rubric
meta_info.stale_score_prompt
meta_info.stale_scoring_result
```

新题评分前，活动 `score_rate` 必须为 `null` 或被 `scoring_status=not_evaluated` 明确屏蔽；任何消费者不得把旧值解释为新题结果。

“stale”表示材料可能仍有审计价值，但不再属于当前题目版本。例如只把题面中的时间从20:17改成20:25，也可能改变可达性结论，因此旧参考答案和Rubric必须进入stale状态，不能仅因为大部分文字相同就继续复用。

建议每个活动评分工件绑定同一版本指纹：

```text
question_version_id
reference_version_id
rubric_version_id
score_prompt_version_id
```

Scoring启动前检查引用链：Rubric必须声明基于哪个question/reference版本，弱答案必须声明回答哪个question版本。任一版本不一致都应停止并标记artifact mismatch，而不是尝试“尽量评分”。

典型状态序列：

| 时点 | reference | rubric / score prompt | scoring | 允许动作 |
|---|---|---|---|---|
| 候选刚发生实质变化 | `pending_rebuild` | `pending_rebuild` | `not_evaluated` | 结构校验、候选选择 |
| 新答案已生成但未核验 | `rebuilt` | `pending_rebuild` | `not_evaluated` | 只能运行reference verifier |
| 新答案核验通过 | `independently_verified` | `pending_rebuild` | `not_evaluated` | 可以生成新Rubric |
| Rubric与Score Prompt完成 | `independently_verified` | `rebuilt` | `not_evaluated` | execution scope允许时收集回答 |
| 回答已收集 | `independently_verified` | `rebuilt` | `answers_collected` | 可以评分，不能宣称效果 |
| 评分完成 | `independently_verified` | `rebuilt` | `scored` | 可以进入效果归因 |

“题目实质变化”指答案条件、任务目标、事实集合或规则适用发生变化；只修正标点或等价排版通常不要求重建全部材料，但必须由版本判定逻辑明确认定为非实质变化，不能由下游脚本自行猜测。

### 5.7 Validation Disposition 契约

保留既有 `passed` 字段用于兼容，同时增加更明确的嵌套判定：

```json
{
  "validation_disposition": {
    "status": "structurally_ready | retry_same_operator | hard_reject | exploration_candidate | pass_through_candidate | needs_manual_review",
    "hard_labels": [],
    "retry_labels": [],
    "soft_labels": [],
    "retry_instruction": null
  }
}
```

不在未同步 schema、prompt、parser 和 candidate selection 的情况下单独扩展现有 difficulty label enum。

每项适用的语义校验必须使用统一三态；检查不适用时使用 `not_applicable`：

```json
{
  "semantic_validation": {
    "competition_survival": {
      "status": "passed | failed | unresolved",
      "reason": "...",
      "evidence": []
    }
  }
}
```

每项检查还必须说明是否适用和风险等级，避免所有算子共用同一套硬门槛：

```json
{
  "semantic_validation": {
    "competition_survival": {
      "applicable": false,
      "applicability_reason": "O26依靠计算和阈值判断，不依靠竞争解释",
      "risk_level": "soft",
      "status": "not_applicable",
      "reason": "该检查不适用于当前算子",
      "evidence": []
    }
  }
}
```

`not_applicable` 表示不需要检查，不能换算成失败或低分。只有 operator execution contract 明确声明为必做的检查，才参与当前候选的最终处置。

只有校验器经过对应夹具校准且证据充分时才能输出 `passed`。调用失败、Judge 不一致、证据不足、控制变体无法执行或当前能力未达门禁时必须输出 `unresolved`。`unresolved` 不得折算为通过，也不得在没有 hard evidence 时直接 hard reject。后续去向由风险等级决定：竞争强度、轻微信息差、算子轻微重叠和预测难度等低风险项进入有预算的模型实验；来源、规则版本、答案矛盾和隐藏事实使用等高风险项进入人工复核、透传或停止当前候选。

三态检查与候选处置是两层状态机：

| 检查集合 | 示例 | 建议 disposition |
|---|---|---|
| 存在确定性 hard `failed` | mixed worlds、无来源规则、明确答案泄漏 | `hard_reject`或一次定向重试 |
| 只有可修复 `failed` | 题面写出“关键事实”但原子事实本身合法 | `retry_same_operator` |
| 无failed且只有低风险 `unresolved` | Judge无法确定竞争解释是否够强 | 预算内 `exploration_candidate` |
| 存在高风险 `unresolved` | 规则版本或答案唯一性无法确认 | `needs_manual_review` / `pass_through_candidate` |
| 全部必要检查 `passed` | 来源、可答、泄漏和控制均有可靠证据 | `structurally_ready` |

基础设施失败要在 reason 中单独编码，例如 `validator_timeout` 或 `sidecar_unavailable`。它会使检查 unresolved，但不能写成 `model_reasoning_failure`，也不能进入算子 failure memory。

### 5.8 Execution Scope 契约

`execution_scope` 是单次运行开关，不是系统功能清单。正式生产和正式实验的目标都是完整跑完模型调用、评分、效果分析和下一轮决策。

正式入口使用：

```json
{
  "execution_profile": "full_iteration",
  "require_full_pipeline": true,
  "on_missing_scope": "fail_configuration",
  "execution_scope": {
    "max_stage": "effect_claim",
    "allow_reference_rebuild": true,
    "allow_model_answering": true,
    "allow_judge_scoring": true,
    "allow_effect_claim": true
  }
}
```

开发、Shadow 或局部回放可以使用：

```json
{
  "execution_profile": "structure_debug",
  "execution_scope": {
    "max_stage": "manual_review_preparation",
    "allow_reference_rebuild": false,
    "allow_model_answering": false,
    "allow_judge_scoring": false,
    "allow_effect_claim": false
  }
}
```

缺失配置时必须看入口。单独开发工具可以采用上述 `structure_debug` 默认并记录 `scope_blocked`；正式 `run_loop.sh` 或正式实验入口必须要求 `full_iteration`。缺少模型、Judge、reference rebuild、Rubric rebuild 或完整 scope 时，应在启动前返回 `configuration_error`，不能静默降级后仍把运行标为成功。`max_stage` 是总上限，布尔值不能绕过它。每个阶段启动前必须同时检查 scope 与 artifact 前置状态。只有真实回答、重新评分与效果归因完成且 `allow_effect_claim=true` 时，才允许产生 provisional/confirmed effect。

`allow_model_answering` 管理弱模型、Probe 与其他被测模型作答，不限制 `max_stage` 范围内的 Source Analyzer、Planner、Writer 和 Validator 调用。若 round0 阶段需要新建模型答案或 Judge 分数，也必须分别检查 `allow_model_answering` 和 `allow_judge_scoring`；开关关闭时只允许复用版本匹配的既有产物，不得发起新调用。

`max_stage` 的固定顺序为：

```text
structure_validation
-> manual_review_preparation
-> reference_rebuild
-> model_answering
-> judge_scoring
-> effect_attribution
-> effect_claim
```

scope gate 应返回结构化结果，而不是简单退出：

```json
{
  "scope_gate": {
    "requested_stage": "model_answering",
    "max_stage": "manual_review_preparation",
    "allowed": false,
    "reason": "stage_exceeds_max_stage",
    "next_action": "stop_debug_run"
  }
}
```

`stop_debug_run` 表示一次开发或回放任务已到声明边界，不应产生 `*.failed`。正式 `full_iteration` 若出现同样结果，必须视为配置错误；配置格式损坏、声明相互矛盾或完整主流程所需服务未配置时应 fail-fast。

## 6. 算子契约改造

### 6.1 总体策略

保留现有 O10–O33 名称和主要能力轴。不要把 mode、来源策略、slot policy、控制测试全部塞进题面生成 prompt。

各算子的通俗含义和简化例子见第 27 号方案 9.7 节。本节重点解释如何把这些语义落成执行契约，不重复把例子当成可直接复制的题面模板。

建议新增独立模块：

```text
operator_execution_contracts.py
```

每个算子契约至少包含：

```json
{
  "operator_id": "...",
  "supported_modes": [],
  "primary_axis": "...",
  "allowed_auxiliary_axes": [],
  "required_slots": [],
  "synthesizable_slots": [],
  "non_synthesizable_slots": [],
  "rule_source_policy": "...",
  "single_core_output": "...",
  "neutral_task_intent": "...",
  "fact_budget_policy": "...",
  "required_checks": [],
  "optional_checks": [],
  "not_applicable_checks": [],
  "requires_live_competitor": false,
  "control_spec": {}
}
```

`OperatorPromptSpec` 继续负责内容描述；execution contract 负责模式、槽位、来源和控制策略；runtime policy 继续负责 enabled/suspended 等执行资格。

三个对象分别回答不同问题：

* `OperatorPromptSpec`：这个算子在语义上要制造哪种推理负担；
* `operator_execution_contract`：在当前mode和来源条件下，哪些槽位可用、哪些可合成、哪些绝不能合成；
* runtime policy：该算子目前是否通过资格、是否可进入自然路由。

例如O22需要端点、方向边和通行时间：Prompt Spec解释“测试联合可达性”；execution contract规定在 `source_faithful` 下通行时间必须来自来源、在授权合成模式下可作为明确题内参数；runtime policy则可能因为O22尚未通过forced qualification而将其设为`suspended`。三者不能合并成一个布尔“operator可用”。

### 6.2 O10–O18

#### O10 最小充分事实集

- source-faithful：只有来源已包含多个互不蕴含事实时可用；
- controlled/adaptation：允许补齐有职责的观察事实；
- 最小集合成员和决定性角色只在 hidden plan；
- 专属控制：必要成员消融使结论减弱，干扰事实消融不改变答案；
- 禁止把“最小充分集合”写进任务。

#### O11 端点时序一致性

- source-faithful：端点、时间窗、路径或速度范围必须来源已给；
- controlled/adaptation：可合成端点观察和 task-local 路径参数；
- 禁止合成盲区内真实发生事件；
- 专属控制：联合约束而非单一显眼数字决定答案。

#### O12 独立性与共同必要性

- X/Y/X+Y 只属于 hidden plan；
- 普通任务优先生成关联样本，而不是把多个反事实版本塞进一道题；
- 每个题仍只有一个核心判断；
- 专属控制：交换 X/Y 不改变语义，单条件均不足且各自有独立贡献。

#### O13 必要连接破坏

- source-faithful 只能使用已有复核事实和冲突；
- controlled/adaptation 可新增登记后的复核观察；
- “断点”“必要连接”“整体翻转”不得进入题面；
- 专属控制：局部连接失效不自动等于整体翻转。

#### O14 信息闭包

- 保持 `generates_question=False`；
- 从 Router 可执行候选中永久排除；
- 升级为全局 source/world/mode 合规校验原则；
- 输出精确无来源事实、世界混合和非法规则证据。

#### O15 单变量门槛变化

- 事实变化与阈值变化必须区分；
- 阈值只能来自 provided rule 或明确 task-local parameter；
- 反事实组普通默认一组，最多两组，优先作为关联样本；
- 专属控制：除一个决定性变量外其余事实、规则和目标命题完全不变。

#### O16 相近解释覆盖与残差

- 只引入一个真实竞争的相近解释；
- 竞争解释在决定性事实出现前必须存活；
- 不允许一句话直接排除错误解释；
- 专属控制：删除区分事实后两个解释重新接近。

#### O17 双规则边界映射

- 两套规则必须来源明确或显式声明为题内局部规则；
- 不得合成真实法律、行业规则和专业处置阈值；
- 只提出一个整体业务判断；
- 不拆成“事实层/行动层”两个作答任务。

#### O18 基线纳入口径

- 基线标准和统计摘要必须来源明确或属于假设案例局部参数；
- 不得把合成统计冒充真实行业基线；
- 正确基线不能独占权威来源、更长描述或更多数字；
- 专属控制：交换基线名称和顺序不改变答案。

### 6.3 O19–O27

#### O19 多实体角色绑定

- 只描述局部行为，不预绑定实施者、运输者、接收者等角色；
- 要求至少两个真实竞争实体和跨节点绑定线索；
- 专属控制：名称交换、行为归属单变量变化。

#### O20 多阶段事件链断点

- 阶段和状态变化是观察事实，断点是 hidden role；
- 单阶段必要转移失败优先 O20，不升级为 O28；
- 专属控制：修复真正断点后整体结论才改变。

#### O21 对象来源与同一性

- 转移、遮挡、重现和对象特征必须是观察事实；
- 同一性结论不得写入题面；
- 必须保留至少一个竞争来源；
- 禁止使用唯一编号直接给答案。

#### O22 路径拓扑联合可达

- 节点、边、方向、封闭和时间窗必须来源明确或是 task-local parameter；
- 不得靠常识补真实通行时间；
- 专属控制：决定性边/窗口变化改变答案，旁支变化不改变答案。

#### O23 观测可靠性冲突

- 提供可见性、清晰度、遮挡、来源冲突等观察条件；
- 不得直接写“来源不可靠”；
- 来源名称和权威性不能代替质量事实；
- 同源复制不得自动增强结论。

#### O24 多假设残差排序

- 三个以上解释仍服务于一个主轴和一个核心输出；
- 每个解释都必须解释部分核心事实；
- 明显荒谬候选触发定向重试；
- 做名称、顺序、描述长度和信息量平衡检查。

#### O25 程序不变量与参照系

- 程序、单位、映射和参照系必须来源明确或题内声明；
- 不得自由编造真实业务程序；
- 不标记错误步骤和不变量答案；
- 只问一个结果有效性判断。

#### O26 定量阈值与误差传播

- 公式、单位、误差关系和阈值必须全部题内明示；
- 合成内容只能作为局部参数，不能冒充专业标准；
- 不给中间计算和阈值比较结果；
- 覆盖跨阈值、不跨阈值和接触阈值控制样本。

#### O27 跨层结论校准

- 删除“说明其边界”“最高支持”等答案方向问法；
- 改为中性的整体业务判断；
- 原题无规则时不得补造结论层级；
- 观察、事实、表述和行动层映射只存在于 hidden plan。

### 6.4 O28–O33

#### O28 多跳链路闭合

- 只呈现各跳原子事实，不呈现完整链总结；
- 负例允许必要跳转缺失；
- 单阶段断点仍使用 O20；
- 专属控制：必要跳消融影响整体，旁支变化不影响整体。

#### O29 实体同一性冲突消解

- 支持和冲突线索都必须是观察事实；
- 不标记排他冲突；
- 正确身份不得拥有更多细节；
- 必须执行名称交换和事实顺序交换。

#### O30 主动判别观测选择

- 给出竞争解释、可执行观察和资源边界；
- 哪项观察真正判别属于 hidden plan；
- 输出保持“选择下一观察并说明理由”一个任务；
- 不把成本最低或信息最多直接等同最佳。

#### O31 观测累积校准

- 提供来源和生成关系，不直接标注独立、同源或重复；
- 删除“支持到什么程度”等答案边界提示；
- 真正独立新增信息才允许增强；
- 同源转录、截取和重复不得当成多份独立证据。

#### O32 角色关系图关键边

- 只描述方向性行为，不画图、不标关键边和角色答案；
- 加强与 O19、O20、O28 的相邻边界；
- 必要边变化影响答案，冗余边变化不影响答案。

#### O33 跨模态支持边界

- 多源材料必须属于同一 world，并对齐时间、实体和适用范围；
- 删除“共同支持边界”式问法；
- 采用中性融合判断；
- 不能用来源数量和技术名称暗示证据更强。

## 8. 路由机制改造计划

### 8.1 路由分层

Router 拆成：

```text
Layer 0: task authorization gate
Layer 1: evolution mode eligibility gate
Layer 2: operator slot gate
Layer 3: adjacent-operator resolution
Layer 4: memory ranking
```

Memory 只能参与 Layer 4，不能绕过前面的 authorization、mode 和 slot gate。

### 8.2 Rule Router 修改

当前关键词规则保留为诊断候选召回提示，但不能直接成为执行资格。

修改为：

1. 关键词规则产生 tentative operators；
2. tentative operators 必须通过 mode-aware slot gate；
3. 默认 O10 fallback 删除；
4. 无安全算子返回 `no_safe_operator`；
5. 上层将其转换为 `pass_through_candidate`，不是 generation failure；
6. legacy fallback 仅在兼容开关下保留，并写明 route revision。

### 8.3 Hybrid Router 修改

因为 controlled synthesis 下合法新增观察事实不应被判定为非法补造。

### 8.4 Router Contract 版本

## 9. 校验器改造计划

### 9.1 校验层次

每一层先做适用性判断，再做结果判断。公共校验器不得默认所有算子都需要竞争解释、角色绑定、路径交换或唯一答案。

处理顺序固定为：

```text
明确且致命的问题 -> hard reject
明确但可局部修复的问题 -> retry_same_operator
没有致命问题且只是结构判断不稳 -> exploration
来源、规则或正确答案存在高风险不确定 -> needs_manual_review / pass_through
检查不适用 -> not_applicable，继续后续检查
无法安全进化 -> pass_through
```

顶层 `passed` 只用于历史兼容，不能再作为候选是否 hard reject 的唯一依据。`candidate_selection.py` 必须优先读取 `validation_disposition.status`；否则一个“候选项略多”或“Judge超时”仍会被错误当成致命失败。

校验按成本和确定性从低到高执行：

```text
L0 schema / identity / artifact status
L1 task authorization / fact source / rule validity / world / mode compliance
L2 answerability / contradiction / external knowledge
L3 surface leakage / single-sentence direct answer
L4 complexity budget / competition survival / information balance
L5 ablation / name swap / order swap controls
L6 predicted structural gain
```

只有前一层通过后才运行更昂贵的 LLM 或控制变体检查。

### 9.2 L0：Schema、身份与旧评分状态

检查：

- `sample_id/index/round/candidate_group_id/candidate_id` 未被破坏；
- hidden sidecar trace 可解析且属于当前 candidate；
- evolved candidate 的 active scoring status 为 `not_evaluated`；
- 旧 `score_rate/scoring_result/rubric/score_prompt` 未被当作活动结果；
- pass-through 样本保持原有可复用评分材料。
- 当前阶段没有越过 `execution_scope.max_stage`，对应 allow 开关已经显式开启。

### 9.3 L1：事实来源、世界与模式

hard reject：

- 题面存在无法映射到 ledger 的事实；
- 同一候选混合多个 world；
- controlled synthesis/adaptation 未获得任务显式授权；
- source-faithful 新增人物、时间、地点、规则或结果；
- 假设事实冒充来源事实；
- 编造真实法律、行业规则或专业阈值；
- task-local parameter 未明确标注局部适用范围；
- Writer 使用了 `prompt_visible=false` 的事实。
- 真实规则缺少来源、版本、适用对象、适用场景或当前有效状态；
- expired/superseded/unresolved 规则被当作当前有效规则使用。

来源定位暂时不可用与事实确定无来源要分开处理：

* 题面事实在ledger中不存在，或确认来自另一个world：hard reject；
* ledger有对应事实，但文件移动、hash漂移或定位服务暂时失败：`unresolved`，进入人工复核或透传；
* 跨阶段身份明显错配、sidecar属于另一个candidate：L0/L1 hard reject。

例如，`F03`能在原记录中找到，但缓存hash因换行格式变化而不一致，应重新分析；不能立即断言F03是虚构事实。

### 9.4 L2：可答性和冲突

L2 只做候选选择前的结构可答性检查，不生成新参考答案，也不调用强模型。检查：

- 必要条件是否完整；
- 是否存在事实冲突；
- 是否依赖题外知识；
- 唯一答案任务是否实际存在多个合理答案；
- `conclusion_contract` 是否覆盖真实可能结果；唯一答案要求是否有公开事实与当前有效规则保证。

不可回答和事实矛盾属于 hard reject。

“新参考答案是否只依据题面事实”“强模型是否稳定正确作答”“是否偷用隐藏事实”“是否存在多个冲突答案”移到候选选中后的 Reference Verification。这样不会在 Candidate Selection 之前依赖尚未生成的新答案，也不会为所有未选候选提前调用强模型。

### 9.5 L3：答案泄漏

检查标签：

```text
direct_answer_leakage
derived_summary_leak
target_chain_disclosure
rule_ceiling_disclosure
role_binding_disclosure
competitor_elimination
answer_direction_disclosure
answer_template_disclosure
hypothesis_status_disclosure
fact_role_disclosure
rule_application_disclosure
missing_link_disclosure
uniqueness_disclosure
forced_conclusion_type
counterfactual_result_disclosure
control_role_disclosure
authority_bias
position_or_naming_bias
metadata_leakage
```

明确标准答案泄漏属于 hard reject；可通过删除总结和模板修复的候选先定向重试一次。

标签必须在 Validator 输出、retry map、统计、Memory 和测试夹具中使用同一名称。一个命题可命中多个标签，但必须保留最具体标签与证据句；“假设A成立，再分析B为何不成立”必须命中 `hypothesis_status_disclosure`。

L2–L5 中适用的语义判断输出 `passed/failed/unresolved`，不适用的检查输出 `not_applicable`。只有校准达标且证据充分时才是 `passed`；无法可靠判断时为 `unresolved`，不能在 shadow 或 enforce 模式中默认当作通过。低风险结构项的 `unresolved` 进入有预算的模型实验；涉及来源、有效规则、答案矛盾或隐藏事实的高风险项才进入人工复核或透传。

### 9.6 L4：竞争、复杂度与信息量

规则调整：

- 普通题一个 primary axis，最多一个 auxiliary axis；
- 默认一个核心输出目标；
- “判断并说明依据”算一个任务；
- 候选项数量根据任务类型动态判断，不再固定 hard limit 3；
- 普通反事实默认一组，最多两组，优先拆成关联样本；
- 每项新增事实必须有职责；
- 竞争解释必须解释部分核心事实；
- 正确项不得独占长度、数字、因果解释和谨慎措辞。

弱竞争、轻度显著性不平衡和 operator overlap 属于 retry/soft risk，不直接 hard reject。

主轴、输出任务、候选项和反事实数量是默认设计范围，不是统一硬上限。超过默认值时：

1. 先判断能否定向精简；
2. 若任务明确要求组合压测或路径结构确有需要，记录 `approved_exception`；
3. 只有多项独立任务导致不可答或难度主要来自任务堆叠时，才 hard reject。

例如，路径题有6个候选节点但每个节点都参与可达性判断，可以保留；一道题同时要求身份判断、最短路径、设备评价和处置建议，则应拆题。

竞争存活检查只在 `requires_live_competitor=true` 时执行。O16、O24通常需要；O26定量题可设为false，并改查计算完整性、单位和阈值接触状态。

### 9.7 L5：控制测试

#### 决定性事实消融

删除决定性事实后允许：

- 答案翻转；
- 结论强度下降；
- 无法区分；
- 证据不足；
- 可行候选增加。

不要求机械 A->B 翻转。

#### 无关事实消融

删除 `relevant_distractor` 后答案必须保持不变。

#### 名称交换

交换人物、车辆、路径、规则或解释名称后，语义答案必须不变。

#### 顺序交换

调整事实和候选呈现顺序后，答案不得因位置变化。

#### 信息量平衡

正确项不得系统性拥有：

- 更长描述；
- 更多数字；
- 更完整因果解释；
- 更谨慎措辞；
- 更权威来源名称。

控制检查结果放入：

```text
validation_result.counterfactual_controls
```

控制失败必须进一步区分：

```text
candidate_failed             候选本身未满足控制关系
control_variant_invalid      控制变体生成错误
judge_unresolved             Judge无法稳定判断
control_not_applicable       当前算子不需要该控制
```

例如，名称交换只替换“车辆A”为“车辆B”，却没有同步交换全部记录和答案映射，应记为 `control_variant_invalid`，不能 hard reject 原候选。顺序交换只能调整材料展示顺序，不能改动事件真实时间。

### 9.8 L6：预测性结构收益

`validate_difficulty_gain.py` 在正式评分前只判断：

- 是否保持目标轴；
- 是否没有泄漏；
- 对要求竞争结构的算子，是否有真实竞争判断；
- 是否避免教学式脚手架；
- 是否可回答；
- 是否非格式复杂度主导；
- 是否可能命中目标 failure。

以上检查也必须服从算子适用性。非竞争型算子不得因为 `competitive_judgment_score` 低于统一阈值而失败。连续分数只用于排序和观察；hard reject 必须来自明确 hard label 和可定位证据，不能只来自“0.59低于0.60”。

它不能宣称：

- 已有效变难；
- operator 已成功；
- 已命中模型边界；
- 弱模型一定降分。

为兼容现有 enum，`clear_gain/probable_gain` 在过渡期必须被文档化为 `predicted structural potential`。推荐在嵌套字段增加：

```text
difficulty_gain_validation.confirmation_status = not_evaluated
```

### 9.9 Hard、Retry、Explore、Pass-through 分流

本节的默认严重程度必须直接复用第 28 号方案“13.7 统一风险和默认处理”，Validator、Candidate Selection、重试器和 Memory 不得各自维护含义不同的副本。工程侧至少固定以下映射：

| 问题类型 | 默认处理 |
|---|---|
| 直接金标、真实敏感 metadata 泄漏 | 立即 hard reject |
| 假设状态、角色绑定、规则应用、链条总结 | 在预算内定向重试一次 |
| 权威偏置、位置或命名偏置、轻微信息量失衡 | 软风险或定向重试 |
| 竞争偏弱、预测难度不确定 | exploration candidate |
| 来源、规则版本、答案唯一性、隐藏事实使用不明 | needs manual review 或 pass-through，不得直接评分 |

#### Hard reject

- 无来源事实；
- world 混合；
- 编造真实规则或专业阈值；
- 无法通过删除局部总结安全修复的标准答案或规则应用结果泄漏；
- 不可回答；
- 事实矛盾；
- 旧评分结果被当成新题结果；
- 数据身份破坏；
- 密钥或内部配置泄漏。

#### 定向重试

- 竞争解释太弱；
- 正确项信息量过多；
- 题面总结完整链；
- 输出任务过多；
- 反事实改变多个变量；
- 候选项明显荒谬；
- 题面过度提示步骤；
- 可修复的派生总结和角色称谓泄漏。
- 可修复的规则应用措辞、结论方向和竞争解释淘汰。

直接金标、真实敏感metadata暴露、无来源事实和事实矛盾可以立即拒绝；其余泄漏先做一次最小修复，保留合法原子事实。重试后仍有同类确定性问题时再 hard reject。

重试器必须同时检查单标签和单候选总预算：

```json
{
  "retry_budget": {
    "max_retries_per_label": 1,
    "max_total_retries_per_candidate": 2
  }
}
```

例如候选已经分别修复过角色称谓和命名偏置，即使用完两次总预算；之后再发现轻微信息量偏差时，不再第三次调用改写模型，而是按当前风险进入 exploration、透传或拒绝。

#### Exploration

- 难度增益偏弱；
- 竞争解释基本成立但强度不足；
- operator 边界不清；
- primary/auxiliary axis 可能重叠；
- 结构合理但效果只能由真实模型实验判断。

#### Needs manual review

- 来源是否真实无法确认；
- 规则版本或适用范围无法确认；
- 答案唯一性存在高风险不确定；
- 新参考答案可能使用隐藏事实。

这类候选不能直接进入 Reference Rebuild、弱模型回答或评分。复核后若能排除高风险，可重新进入候选选择；否则透传或放弃当前候选。

#### Pass-through

- 缺少不可安全合成的规则或阈值；
- 来源世界不明；
- source-faithful 槽位不足；
- 无安全适配算子；
- 清理泄漏后无法保持可答性。

## 10. 参考答案、Rubric 与评分隔离

### 10.1 立即修复项

`collect_answers.py` 必须停止调用会注入 `answer_boundary_ledger` 和 `rubric_intent_ledger` 的答案侧上下文构造逻辑。

弱模型请求体必须只有：

```text
最终 evolved prompt
```

如果开启专门的标准答案生成模式，应使用独立脚本和独立配置，不能复用弱模型回答流程。

### 10.2 候选选中后的参考答案重建与核验

该阶段只对 `candidate_selection.py` 已选中的主链或 exploration 候选运行。未选候选不会生成正式新答案，也不会调用强模型核验。

Reference Rebuilder 先完成：

1. 为选中候选生成新参考答案；
2. 引用公开 fact IDs 和规则 IDs；
3. 将旧答案保留在 `stale_references`；
4. 将状态更新为 `rebuilt`，等待独立核验。

随后由独立 Reference Verifier 或强模型检查：

1. 新参考答案是否只使用题面公开事实和当前有效规则；
2. 强模型是否能够稳定正确作答；
3. 新参考答案或强模型答案是否使用了 hidden-only facts；
4. 是否存在多个互相冲突但都合理的答案；
5. `conclusion_contract` 是否与实际可得结论一致。

全部通过后，才把新答案写入活动 `meta_info.references` 并将状态更新为 `independently_verified`。核验失败或高风险 unresolved 时不能进入 Rubric 重建和正式评分。

### 10.3 Rubric 重建

`gen_rubric.py` 核心 Prompt 语义保持不变，但输入必须是：

- 最终新题；
- 已独立核验的新参考答案。

不得继续使用旧 references。重建完成后：

```text
rubric_status = rebuilt
score_prompt_status = rebuilt
```

### 10.4 运行顺序调整

前半段保持：

```text
operator routing
-> question evolution
-> surface validation
-> candidate selection
```

只调整候选选中后的评分准备子流程。

当前：

```text
candidate_selection
-> collect_answers
-> gen_rubric
-> scoring
```

调整为：

```text
candidate_selection
-> rebuild_reference_answer
-> gen_rubric
-> collect_answers
-> scoring
```

这样弱模型不会影响参考答案和 Rubric 构建，评分也只使用新材料。

理论上也可采用：

```text
candidate_selection
-> rebuild_reference_answer
-> collect_answers
-> 独立生成新Rubric
-> scoring
```

但该架构必须证明 Rubric Builder 绝对看不到弱模型答案，并使用独立输入白名单、独立请求或进程与可审计 trace，且不得根据弱模型答案动态调整标准。考虑到当前项目已有隐式上下文耦合，本方案选择“先新 Rubric、后弱模型回答”作为默认实现，使评分标准预注册关系更明确、可测试。

无论采用哪一种理论可行顺序，新参考答案都必须在弱模型正式回答前完成独立核验；本项目实施与验收只认默认推荐顺序。

这里所说的“评分标准预注册”不是要求把Rubric公开给弱模型，而是指Rubric在看到被测答案之前已经固定并版本化。弱模型仍然只能看到最终题面；Scoring Judge在回答产生后读取题面、弱答案和已固定的新Rubric。这样可以区分：

* 题目本身让模型犯错；
* Rubric在看到错误后临时增加了针对性扣分项。

后者会污染实验归因，因此即使模型调用完全独立，也不能允许Rubric Builder读取弱答案摘要、错误标签或validator对弱答案的反馈。

各阶段还必须通过 `execution_scope`。`structure_debug` 可以在结构校验、候选分流和复核材料准备后停止；正式 `full_iteration` 必须继续进入 reference rebuild、强模型核验、model answering、scoring、效果归因和下一轮决策，缺少任一必要配置都应在启动前报错。

### 10.5 Weak Probe 调整

当前 weak probe 位于正式参考答案重建之前，容易使用旧答案或不完整答案判断候选。

在 enforce 模式下建议：

1. pre-selection difficulty validation 只做结构潜力判断；
2. weak probe 移到候选选中且新参考答案/Rubric 可用之后；
3. weak probe 结果作为真实效果证据，不作为无条件 hard gate；
4. exploration 候选可以在预算内运行 probe；
5. 不能用单次 probe 直接确认 effective evolution。

## 11. Candidate Selection、效果分析和 Memory

### 11.1 Candidate Selection

保留现有四类 flow 和预算机制。

需要调整：

1. factual validation 必须 mode-aware；
2. `format_complexity_only`、`competition_weak`、`operator_overlap` 优先定向重试或 soft flow，不应一律当成不可恢复 hard risk；
3. 真正的 direct answer leakage、unanswerable、external dependency 等继续覆盖 exploration；
4. `not_applicable` 和 `no_safe_operator` 转正常 pass-through；
5. 每组仍最多一个 exploration candidate；
6. 每轮总 exploration 预算不变；
7. 语义检查为 `unresolved` 且无确定性 hard evidence 时继续看 `risk_level`：soft 进入有预算的 exploration，hard/safety 才进入 `needs_manual_review` 或 pass-through；不得统一阻塞，也不得默认 structurally ready 或 hard reject。

这里的 `not_applicable` 是算子级结果，表示当前算子不适合；`no_safe_operator` 是路由聚合结果，表示没有任何候选算子通过门禁；`pass_through_candidate` 才是最终候选流。单个算子 `not_applicable` 时仍可继续检查其他算子，不能过早透传整道题。

历史兼容必须与新契约分开处理：旧 JSONL 中只有 `needs_manual_review` 标签、但没有来源、规则版本、答案唯一性、隐藏事实或其他高风险证据时，兼容层将其重新映射为 `exploration_candidate`。新契约生成的 `needs_manual_review` 已明确表示高风险不确定，Candidate Selection 不得把它直接送入 Reference Rebuild、弱模型回答或正式评分。

### 11.2 Effect Analysis

确认有效进化至少需要：

1. 弱模型多次回答后稳定降分；
2. 错误命中目标能力轴；
3. 新参考答案或强模型保持正确；
4. Judge 评分稳定；
5. 题面无来源、泄漏、不可答和冲突问题；
6. 降分不是由于多任务、格式或 Rubric 失效；
7. 至少在多个独立样本上复现后，才升级为 operator 稳定成功证据。

建议新增可选嵌套字段：

```json
{
  "effect_confirmation": {
    "status": "not_evaluated | ambiguous_effect | provisional_effect | confirmed_effect",
    "target_failure_match": true,
    "strong_answer_valid": true,
    "judge_stable": true,
    "alternative_causes_excluded": []
  }
}
```

不立即修改现有主效果 enum，避免破坏历史消费者。

只有 `execution_scope.allow_effect_claim=true` 且真实回答、重新评分和效果归因均完成时，才允许状态升级为 `provisional_effect` 或 `confirmed_effect`；否则保持 `not_evaluated`，不得因结构校验结果产生效果声明。

### 11.3 Memory 写入

这里的 `Memory` 指流水线保存的可审计历史经验记录，不是模型参数更新，也不是把完整历史Prompt重新塞给Router。Memory应提供具体、有限的排序信号，例如“某算子在某类来源结构上反复产生角色泄漏”，但不能授予模式权限、补齐缺失事实或覆盖当前样本门禁。

operator success memory 只有在 confirmed/provisionally verified effect 满足现有成功门禁时写入。

必须继续保证：

```text
score_increased
-> failure memory
-> no success memory
-> continue with new operator or strategy
```

Memory 应记录具体失败形态，例如：

```text
role_binding_disclosure
mixed_worlds
unregistered_task_local_threshold
competitor_elimination
multi_output_overload
```

不要因为一次题面失败惩罚整个 operator。

### 11.4 下一轮决策

`update_sample_state.py` 完成 Memory 更新后，还必须给出下一轮可直接执行的动作。建议放入现有 `evolution_state`，避免增加容易在中间脚本中丢失的临时顶层字段：

```json
{
  "evolution_state": {
    "next_round_decision": {
      "action": "continue_same_operator",
      "reason": "score_decreased_and_target_failure_hit",
      "next_operator_policy": "retain_primary_operator",
      "difficulty_adjustment": "increase_one_level",
      "parent_candidate_id": "C03",
      "retain_as_boundary": true
    }
  }
}
```

`action` 允许：

```text
continue_same_operator
switch_operator
retry_generation_strategy
backtrack_to_parent
retain_as_boundary
stop_branch_success
stop_branch_no_gain
pass_through
manual_review
```

动作规则用直接例子说明：

* 弱模型稳定降分、目标错误命中、强模型正确、Judge 稳定：`retain_as_boundary`，再按难度预算决定 `continue_same_operator` 或 `stop_branch_success`；
* 分数下降但目标错误没有确认：`retry_generation_strategy`，状态保持 `ambiguous_effect`，不写 success memory；
* `score_increased`：写 failure memory，`backtrack_to_parent` 后 `switch_operator`；若字段只能放一个动作，则主动作写 `backtrack_to_parent`，并在 `next_operator_policy` 写 `switch_operator`；
* 同类题面泄漏定向重试后仍存在：停止当前候选，返回父题尝试其他算子，不写算子成功经验；
* 没有安全进化方式：`pass_through`，继续处理其他样本，不暂停整轮实验。

这里的 `backtrack_to_parent` 只支持返回当前候选的直接父题，不引入完整树搜索、全局分支队列或复杂路径调度。

目标：在任何行为修改前固定现有失败和正确行为。

实施内容：

2. 题目变化后写 artifact status；

实施内容：

5. 新字段只写 metadata/report；

退出条件：每条测试样本均有可审计 task authorization、source world、mode、locator/rule validity 和原因；未授权合成不会发生，无法判断的样本不会被强制分类。

### 阶段 3：Mode-aware Router

目标：消除 Rule/Hybrid 路由语义分裂。

实施内容：

1. 新增 execution contracts；
2. Rule tentative route 必须通过 slot gate；
3. Hybrid input/contract 升级；
4. 删除默认 O10 执行 fallback；
5. no-safe-operator 正常 pass-through；
6. O14 永久排除；
7. 更新 route cache revision。

退出条件：source-faithful 不补事实，获得任务授权的 controlled synthesis 可合法补观察槽位，未授权合成和缺真实规则时透传。

### 阶段 4：Hidden Planner 与 Blind Writer

目标：从调用结构上实现题面信息职责隔离。

实施内容：

1. 新增 hidden planner；
2. hidden plan 必须先确定实体、真实关系、完整事件过程、竞争解释和正确答案轮廓；
3. 生成完整 ledger 和 control plan；
4. 为每个候选生成 conclusion contract，以及唯一答案或“证据不足”的成立依据；
5. 在 Writer 调用前检查 hidden world 内部一致性、答案可推出性和公开事实是否只包含观察级内容；
6. 编译 public projection，删除 answer role、正确解释、事实重要性和推理链；
7. Writer 只看到白名单，并且只能使用投影中的 `fact_id`；
8. Writer 输出缩减；
9. hidden plan 写 sidecar；
10. 生成失败继续 fail-fast。

退出条件：hidden plan 能稳定表达完整场景和答案依据；实际 Writer request snapshot 不含任何 hidden/answer/rubric 字段；题面不存在未登记事实，也没有把真实关系或答案直接写入观察描述。

### 阶段 5：O10–O33 全量修订

目标：让每个算子服从统一 mode、事实和输出契约。

实施顺序：

1. O10–O18，确认 O14 全局化；
2. O19–O27；
3. O28–O33；
4. 全量相邻算子边界审查；
5. 全量中性问法和单核心输出审查。

退出条件：所有生成算子都有 execution contract、正例、mode 反例和控制测试；任何未覆盖算子阻止阶段完成。

### 阶段 6：新校验器 Shadow

目标：测量召回、误报和成本，不立即扩大硬拒绝。

实施内容：

1. 接入 L0–L5；
2. factual validator 改为 mode-aware：source-faithful 继续禁止新增事实，受控合成只放行同 world、已授权且已登记的观察事实；
3. 输出 hard/retry/soft 标签；
4. 执行消融、交换和信息量控制；
5. 先按 operator contract 判断检查是否适用，不适用时记录 `not_applicable`；
6. 记录 shadow disposition；
7. 每项语义检查输出 `passed/failed/unresolved/not_applicable`，并覆盖完整泄漏标签；
8. 与当前 candidate flow 对比；
9. 校准哪些风险进入重试、exploration、manual review 或 hard reject。

退出条件：所有硬风险夹具被命中；干净题误报均可定位到具体句子、global fact key 或控制结果；低风险 unresolved 进入预算内探索，高风险 unresolved 进入人工复核或透传。

### 阶段 7：定向重试与 Enforce

目标：阻止确定性错误进入主链，同时保留探索价值。

实施内容：

1. 每类可修复错误最多一次定向重试；
2. 每个候选总计最多重试两次，达到总预算后不得因新标签继续调用改写模型；
3. 重试仍存在确定性 hard risk 才 hard reject；
4. competition weak/operator overlap 进入 soft flow；
5. exploration 预算保持不变；
6. pass-through 成为正常风险控制结果。

退出条件：主链无已知硬风险，weak/manual review 未被全量拒绝。

### 阶段 8：参考答案与 Rubric 重建

目标：完成新题评分材料闭环。

实施内容：

1. 新增 reference rebuild 和 verifier；新答案必须只依据最终题面中的公开事实和有效规则，不能直接使用未公开 hidden truth 补齐推理；
2. gen_rubric 只使用新 reference；
3. 调整 run_loop 顺序；
4. scoring 拒绝 stale artifact；
5. weak probe 移到新 reference 可用之后；
6. 更新 resume/manifest 和 Windows 集成测试；
7. 在每个阶段前执行 execution scope gate，structure_debug 能在复核材料准备后正常停止，full_iteration 必须继续完整实验。

退出条件：任何 evolved candidate 在评分前都具有 independently verified reference 和 rebuilt rubric/score prompt。

### 阶段 9：效果确认、Memory、下一轮决策和资格发布

目标：只把真实能力边界命中记录为成功。

实施内容：

1. 增加 effect confirmation；
2. 要求目标 failure match、强答案正确和 Judge 稳定；
3. score_increased 继续写 failure memory；
4. 对每个 operator 做 forced qualification；
5. 未通过资格的 operator 标记 suspended 或只允许 forced run；
6. 正式启用 enforce 默认值；
7. 只有 `allow_effect_claim=true` 才允许写 provisional/confirmed effect 与 success memory。
8. 根据效果证据生成 `next_round_decision`，由 run_loop 继续同算子、换算子、返回父题或停止分支。

退出条件：泄漏、不可答、格式性降分和旧 Rubric 污染均不能写 operator success memory；每个完成归因的候选都有合法下一轮动作，正式 full_iteration 能自动进入下一轮或明确终止。

## 16. 兼容、迁移与回滚

### 16.1 历史兼容

历史记录缺少新字段时：

- 不强制迁移；
- legacy 模式继续使用旧 route/generation；
- shadow 模式只添加审计，不改变候选结果；
- enforce 模式只用于新 experiment；
- 不允许在同一 experiment 中混合 route revision 和 generation contract revision。

三种兼容模式的含义：

| 模式 | 新契约是否计算 | 是否改变正式分流 | 适用场景 |
|---|---:|---:|---|
| `legacy` | 否或仅最小兼容解析 | 否 | 重放历史实验、紧急回滚 |
| `shadow` | 是 | 否 | 校准新字段、误报率和成本 |
| `enforce` | 是 | 是 | 新实验正式执行v2.2门禁 |

`shadow` 不是“部分 enforce”。即使新Validator发现hard label，正式候选流仍按旧逻辑运行，但报告必须清楚记录如果enforce会采取什么处置。反过来，enforce模式不能在缺少新契约字段时静默回退legacy；应按明确的兼容策略停止、透传或要求新实验。

### 16.2 统一开关

避免引入过多长期环境变量，建议使用：

```text
QUESTION_EVOLUTION_CONTRACT_MODE=legacy|shadow|enforce
```

任务级 `evolution_authorization`、`execution_profile` 与 `execution_scope` 必须来自可审计配置对象或任务清单，不得仅依赖散落的环境变量。开发工具缺失 scope 时可使用 `structure_debug` 的保守默认；正式入口必须显式声明 `full_iteration`，缺失或不完整时返回配置错误。

过渡期可保留两个临时开关：

```text
ALLOW_LEGACY_RULE_ROUTE_FALLBACK=0|1
REBUILD_REFERENCE_BEFORE_SCORING=0|1
```

正式发布后应删除临时开关，避免永久双轨。

### 16.3 回滚

1. shadow 阶段可直接关闭新审计，不修改历史输出；
2. enforce 阶段回滚只能在新 experiment 中切回 legacy，不能混写同一 round；
3. 单个 operator 质量下降时只暂停该 operator；
4. 回滚不删除 sidecar、报告和失败记录；
5. 不修改或重写历史 experiments。

## 17. 风险与缓解

### 17.1 Source Analyzer 误分类

风险：把来源主张误当观察事实，或把真实案例误判为可合成题。

缓解：

- 低置信度进入 manual/pass-through；
- source-faithful 默认保守；
- source analysis 先 shadow；
- 参考答案不得作为事实真实性证明。

### 17.2 Controlled Synthesis 变成自由编造

风险：借“假设案例”补真实规则、行业阈值和答案结论。

缓解：

- 每项事实必须登记 world/`origin_type`/design basis；
- 只允许观察事实和局部参数；
- O14 逐项审核；
- 真实规则和专业阈值是 non-synthesizable slots。

### 17.3 Validator 过严

风险：系统重新变成 candidate rejection system。

缓解：

- hard/retry/soft/pass-through 分层；
- competition weak 和 operator overlap 不硬拒绝；
- shadow 校准；
- 保留 exploration 预算；
- 真实评分优先于预测性结构分。

### 17.4 清理泄漏后不可回答

风险：删除总结句时同时删除必要事实。

缓解：

- retry 只删除派生命题；
- 允许补回合法原子事实；
- 清理后重新运行 answerability 和 reference verifier；
- 无法修复时 pass-through。

### 17.5 调用成本增加

风险：source analyzer、planner、writer、validator 和 reference verifier 增加调用。

缓解：

- 缓存父题解析；
- cheap gates 先行；
- control Judge 只运行在结构通过候选；
- reference rebuild 只对选中候选；
- 未资格 operator 不自然路由。

### 17.6 主流程顺序调整风险

风险：gen_rubric/collect_answers 顺序变化影响 artifact resume 和现有脚本。

缓解：

- 新 experiment 启用；
- 更新 manifest input hash 和 stage config；
- 增加 Windows/tiny pipeline 集成测试；
- pass-through 继续复用旧材料；
- 不在已有 experiment 中途切换。

### 17.7 Hidden Plan 泄漏

风险：完整答案结构通过 metadata、日志或异常信息进入 Writer/weak model。

缓解：

- sidecar 存储；
- 每个模型请求显式字段白名单；
- prompt snapshot 测试；
- 日志只记录 trace ID；
- 禁止把完整 sample dict 直接传给 Writer。

### 17.8 授权或执行范围配置缺失

风险：配置缺失时系统沿用宽松历史行为，自动启用合成；或者正式实验静默退化成只做结构检查，却仍输出看似成功的结果。

缓解：

- 开发工具缺失或解析 scope 失败时采用 `structure_debug` 保守停止；
- 正式入口缺失或解析失败时返回 `configuration_error`，不启动残缺实验；
- authorization 与 execution scope 均记录审计 ID；
- 每个阶段入口重复验证，不只依赖启动时检查；
- 越权停止记录 `scope_blocked`，不写失败 Memory。

### 17.9 来源与规则元数据陈旧

风险：来源内容变化但 locator/hash 未更新，或过期规则继续作为当前规则。

缓解：

- 校验内容 hash 与记录定位；
- cache key 包含来源与规则版本；
- `expired/superseded/unresolved` 不进入当前规则集；
- 无法确认时转 manual review 或 pass-through。

### 17.10 `unresolved` 数量过高

风险：语义校验长期不能给出可靠结论，人工复核队列膨胀，自动流程停在前置检查。

缓解：

- 分标签统计 unresolved 原因；
- 只有经过回放集校准的检查才启用 enforce；
- 对高频 unresolved 改进夹具和校验器，不把未知批量改成通过或拒绝；
- 低风险结构项优先进入有预算的真实模型实验，用回答和评分消解不确定；
- 只有来源、规则、答案矛盾和隐藏事实等高风险项进入人工复核或透传。

## 18. 发布与资格门禁

### 18.1 Shadow 发布条件

- 新字段 schema 校验通过；
- 不改变现有 candidate flow；
- 默认授权行为通过测试；structure_debug 可保守停止，full_iteration 缺配置会明确失败；
- source/mode 决策可审计；
- semantic unresolved 不被报告为 passed；
- hard fixture 全部命中；
- 无隐私或 hidden answer 泄漏。

### 18.2 Enforce 发布条件

- Writer/weak answer 上下文隔离测试全部通过；
- source-faithful 与 controlled synthesis factual check 区分正确；
- 未授权 controlled synthesis/adaptation 数量为 0；
- source locator、rule validity 和 conclusion contract 门禁通过；
- execution scope 越权阶段调用数量为 0；
- no-safe-operator 正常透传；
- 主链无已知 hard fixture；
- weak/manual-review 仍可进入 exploration；
- reference/rubric 重建顺序集成通过；
- full_iteration 能调用强模型、弱模型和 Judge，完成效果归因、Memory 更新与下一轮决策；
- soft unresolved 不会大量堆积到人工队列，hard/safety unresolved 不会进入正式评分；
- 全量 pytest 通过。

### 18.3 Operator Forced Qualification

每个生成算子至少准备：

- 2 个 source-faithful 正例或明确不适用例；
- 2 个 controlled/adaptation 正例或明确不适用例；
- 2 个来源违规反例；
- 2 个决定性事实消融例；
- 2 个干扰事实消融例；
- 2 个名称/顺序交换例；
- 2 个泄漏注入例；
- 2 个邻近算子反例。

controlled/adaptation 的 forced qualification 用例必须由资格任务显式授权，授权不得外溢到自然路由或其他实验。

资格要求：

- hard leakage 进入主链数量为 0；
- world/mode 合规率 100%；
- Writer 上下文 hidden-field 泄漏数量为 0；
- 名称/顺序交换一致率 100%；
- 干扰事实消融保持率达到预设门禁；
- 决定性事实消融产生预期语义变化；
- 至少有多个独立样本经真实评分命中目标 failure；
- `score_increased` 不计入成功。

这些比例只对一批资格样本计算，不进入单题门禁。例如“竞争存活率90%”表示20个资格候选中至少18个通过，不表示某个候选的Judge置信度0.88就必须拒绝。单题只使用 `passed/failed/unresolved/not_applicable` 和明确证据决定去向。

未通过算子保持 suspended 或只允许 forced qualification。

## 19. 完成定义

只有同时满足以下条件，本方案才算完成：

1. 第 28 号方案中的四种 evolution mode 已落地；
2. 任务授权与样本资格已分离，controlled synthesis/adaptation 默认关闭且不能被 Router、Memory 或算子资格绕过；
3. 原题已拆分为观察、主张、原则、规则、答案方向和派生总结；
4. 每个候选都有单一 world、可审计 fact ledger、稳定 source locator 与 `global_fact_key`；
5. 真实规则具有来源、版本、适用范围和有效状态，失效或 unresolved 规则不会作为当前规则；
6. source-faithful 不新增事实，controlled/adaptation 只新增合法登记事实；
7. 每个候选具有 conclusion contract，唯一答案要求具有公开事实与有效规则依据；
8. Planner、Writer、Validator、Reference Rebuilder 和 Weak Answer 的上下文权限通过测试；
9. O10–O33 已全部逐项审查，O14 已成为全局信息闭包原则；
10. Rule/Hybrid Router 使用同一 authorization-aware、mode-aware slot 语义；
11. 无安全算子正常透传，不再默认 O10；
12. 校验器覆盖来源、规则有效性、结论契约、可答性、完整泄漏标签、竞争、消融、名称交换、顺序交换和信息量平衡；
13. 适用的语义校验使用 `passed/failed/unresolved`，不适用时使用 `not_applicable`；低风险 unresolved 进入预算内模型实验，高风险 unresolved 进入人工复核或透传；
14. 完整泄漏标签已同步到定向重试、统计、Memory 和回放夹具；
15. hard risk、定向重试、exploration、manual review 和 pass-through 分流与第 28 号方案一致；
16. 旧参考答案、Rubric、Score Prompt 和旧分数已隔离；
17. 新参考答案和 Rubric 在弱模型回答前完成重建和核验；
18. 弱模型只看到最终题面；
19. execution scope 能阻止未授权阶段；正式入口要求 full_iteration，缺少完整模型和评分配置时明确失败，不会静默降级；
20. 结构校验不再被解释为已有效进化；
21. `score_increased` 保持负收益语义；
22. 历史数据和 pass-through fallback 可运行；
23. 必要 schema、单元测试、集成测试和全量 `pytest -q` 通过；
24. 无无法解释的临时代码、调试字段、旧双轨或未清理兼容开关。
25. 强模型或 Reference Verifier、弱模型、Scoring Judge 和 Effect Analyzer 均已接入正式主流程，不能相互替代；
26. 每轮效果分析后生成机器可执行的 `next_round_decision`，完整流程能够自动继续、换算子、返回直接父题或终止分支；
27. 人工复核只处理少量高风险边界样本，不是普通候选的默认终点。
28. L2 只做候选选择前的结构可答性检查；新参考答案与强模型核验只对选中候选运行。
29. 历史旧 `needs_manual_review` 仅在没有高风险证据时由兼容层映射为 exploration；新契约的高风险 `needs_manual_review` 不进入正式评分。
30. 单标签最多重试一次、单候选总计最多重试两次，统一风险映射在各消费阶段保持一致。

最终验收标准不是生成器是否遵守了更多文字规则，而是：

> 题面只把合法、同世界、可用于推理的材料交给回答模型；材料如何组织、规则如何应用、竞争解释如何淘汰和最终结论是什么，仍必须由回答模型自行完成。正式流程必须持续调用强模型、弱模型和 Judge，完成验证、回答、评分、效果归因、经验更新和下一轮决策；只有真实实验稳定暴露目标能力边界后，系统才确认问题进化有效。
