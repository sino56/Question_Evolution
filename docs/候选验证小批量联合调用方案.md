# 候选验证小批量联合调用方案

> 版本：v1.0  
> 日期：2026-07-26  
> 状态：方案已确定，尚未实施  
> 上位方案：[模型输入与调用效率后续优化总览](模型输入与调用效率后续优化总览.md)  
> 前置方案：[树搜索共享前缀与输入复用优化方案](树搜索共享前缀与输入复用优化方案.md)

## 1. 目标

在生成阶段同父节点小批量方案稳定后，将题目合法性验证和难度增益验证中重复的固定指令合并为小批量请求，减少实际远端调用数和重复输入 token。

每个候选仍保持独立验证、独立标签、独立失败和独立回退。本方案不是组内比较器，也不新增更严格的候选拒绝规则。

## 2. 为什么单独拆分

验证联合调用与生成联合调用的不变量不同：

- 生成允许多个 operator 共享父节点上下文，但输出目标不同；
- 验证要求每个候选使用相同规则独立判定，不能受兄弟候选质量影响；
- 验证输出 enum、hard risk 和 candidate flow 会进入下游，映射错误风险高于普通文本生成；
- 验证公共上下文通常比生成短，收益必须单独测量，不能从生成阶段收益外推。

因此不把它追加到原共享前缀方案中，也不与 reference、rubric、answer 或 scoring 合并。

## 3. 首版范围

纳入：

1. `validate_evolved_question.py` 中需要 LLM 的进化题合法性验证；
2. `validate_difficulty_gain.py` 中的主难度增益验证。

暂不纳入：

- 本地 deterministic validator；
- 弱探测回答生成和弱探测判定；
- reference answer 生成；
- rubric 生成；
- answer collection；
- Qwen/GPT scoring；
- 不同父节点、不同 validator 版本或不同模型参数的混合批次。

弱探测首版排除，是因为它包含额外生成行为并影响 exploration 分流，失败和随机性边界与普通 validator 不同。

## 4. 可合并条件

候选只有在以下条件全部相同时才能进入同一验证批次：

- validation stage；
- model 和不含密钥的服务端身份；
- system prompt、validation prompt 和 schema 版本；
- temperature、max tokens 等请求参数；
- 同一 run/round；
- 同一直接父节点或同一 candidate group；
- 相同的原题上下文；
- 尚未被本地 hard-risk 规则终止；
- 输入长度估算未超过安全阈值。

分组键建议为：

```text
validation_batch_key = hash(
  stage + run_id + round + parent_id
  + model_identity + prompt_version + schema_version
  + request_parameters + original_prompt_fingerprint
)
```

## 5. 批次大小

- 初始 A/B 只使用 batch size 2；
- 验证稳定后允许最大 3；
- 不因等待凑批阻塞关键路径，设置很短的本地 flush 条件；
- 队列关闭、frontier 完成或达到 size 上限时立即提交；
- 只有 1 个候选时直接使用 compact single，不等待其他候选。

批次大小是输入组织参数，不改变每组最多选择多少 exploration candidate 等业务预算。

## 6. 输入协议

联合请求只共享固定验证指令和原题上下文：

```json
{
  "validation_protocol_version": "difficulty_gain_bundle_v1",
  "original_question": "...",
  "candidates": [
    {
      "candidate_id": "c1",
      "evolved_question": "...",
      "operator": "O2"
    },
    {
      "candidate_id": "c2",
      "evolved_question": "...",
      "operator": "O4"
    }
  ]
}
```

必须在 prompt 中明确：

1. 对每个候选相对于原题独立判断；
2. 不进行候选间比较、排名或相互引用；
3. 一个候选的问题不得影响其他候选标签；
4. 每个输出必须回显原始 `candidate_id`；
5. 输出条数必须与输入候选数一致；
6. enum 只允许使用现有 validator schema 已定义值。

优先使用服务端原生 structured output（如果当前提供商可靠支持），否则继续使用严格 JSON + 本地解析。structured output 只是降低解析错误的可选能力，不能成为正确性依赖。

## 7. 输出协议与独立映射

响应结构示例：

```json
{
  "results": [
    {
      "candidate_id": "c1",
      "label": "probable_gain",
      "risk_tags": [],
      "reason": "..."
    },
    {
      "candidate_id": "c2",
      "label": "weak_gain",
      "risk_tags": [],
      "reason": "..."
    }
  ]
}
```

解析器必须：

- 按 ID 映射，禁止按返回数组位置映射；
- 检查重复 ID、未知 ID、缺失 ID 和数量不一致；
- 对每个 item 单独校验 enum 和字段；
- 保留成功 item，失败 item 进入 single fallback；
- 不生成 batch 级 `hard_reject` 或平均标签。

## 8. 本地验证与分流语义

执行顺序：

```text
候选生成
  -> 现有本地 deterministic checks
  -> 对仍需 LLM 判断的候选按 key 小批量分组
  -> 独立解析结果
  -> 现有 difficulty/candidate selection 逻辑
```

必须保持：

- hard label、hard risk tag 和模板化简化信号继续覆盖 exploration；
- `weak_gain`、`needs_manual_review` 在无 hard risk 时仍可进入 exploration；
- `no_gain` 仍按现有条件决定 pass-through 或 exploration；
- 不新增“组内较差所以拒绝”的逻辑；
- 每个 candidate group 的 exploration 数量和每轮总预算不变。

## 9. 部分失败与回退

以下情况触发候选级 single fallback：

- 缺失某个 candidate ID；
- 单个 item JSON/schema 无效；
- 单个 item enum 非法；
- 单个 item 内容明显引用了其他候选而无法独立解释；
- batch 响应被截断但仍能安全提取部分完整 item。

以下情况整个 batch 回退为单候选：

- 响应完全不可解析；
- 无法可靠识别任何 candidate ID；
- 服务端拒绝请求或上下文超限；
- batch prompt/schema 版本不兼容。

已成功解析并持久化的 item 不得重跑。回退请求进入统一并发调度器，且全局在途仍不得超过 20。

## 10. Checkpoint 与审计字段

建议在现有 `validation_result` 或 `difficulty_gain_validation` 内追加可选审计信息：

```json
{
  "validation_execution": {
    "mode": "bundle_v1",
    "validation_bundle_id": "...",
    "bundle_size": 2,
    "item_index": 0,
    "fallback_to_single": false,
    "input_projection_version": "difficulty_validation_v1"
  }
}
```

不得重命名或删除现有 label、risk tag、reason 等字段。历史记录缺少该审计对象时按 single legacy 处理。

原始 batch 响应先原子持久化，再逐 item 发布 checkpoint；其幂等规则遵循[模型请求幂等去重与精确恢复方案](模型请求幂等去重与精确恢复方案.md)。

## 11. 配置建议

```text
VALIDATION_BUNDLE_ENABLED=false
QUESTION_VALIDATION_BUNDLE_ENABLED=false
DIFFICULTY_VALIDATION_BUNDLE_ENABLED=false
VALIDATION_BUNDLE_SIZE=1
VALIDATION_BUNDLE_MAX_SIZE=3
VALIDATION_BUNDLE_FLUSH_MS=25
VALIDATION_BUNDLE_FALLBACK_TO_SINGLE=true
VALIDATION_BUNDLE_PROTOCOL_VERSION=bundle_v1
```

默认关闭且 size 为 1。首轮只打开一个 validator，不能同时打开题目验证和难度验证后再归因收益。

## 12. 建议代码落点

- 新增 `validation_bundle.py`：分组、稳定排序、prompt 渲染、按 ID 解析和候选级 fallback。
- `validate_evolved_question.py`：保留本地规则，只有 LLM 部分接入 bundle。
- `validate_difficulty_gain.py`：主验证接入 bundle；弱探测保持独立。
- `multi_operator_search.py`、`branch_pipeline.py`：在同父候选齐备或 flush 条件满足时提交验证批次。
- `vertical_operator_search.py`：只在同一 frontier 内合并，不跨父节点混批。
- `pipeline_runtime.py`：接入全局调度器、请求账本和 bundle 指标。

## 13. 测试方案

### 13.1 单元测试

- 相同 key 的 2 个候选合并，不同 key 不合并；
- 输出按 candidate ID 映射，返回顺序变化不影响结果；
- 缺失、重复、未知 ID 被准确识别；
- 单 item 失败只回退该 item；
- 成功 item 不因其他 item 失败而重跑；
- hard risk、本地 validator 和 enum 语义不变；
- `weak_gain`、`needs_manual_review` exploration 行为不变；
- batch size 和全局并发上限同时生效；
- 单候选不等待凑批。

### 13.2 抗串扰测试

构造一组明显合法候选和一组明显非法候选，分别测试：

- 单独验证；
- 合并验证且交换输入顺序；
- 与极强/极弱兄弟候选混合。

比较每个候选的 label、risk tags 和理由要点，确认不存在明显的相对排名效应或顺序效应。

### 13.3 真实 A/B

固定样本、模型、参数和候选集合，比较 single 与 bundle：

- 实际远端调用数；
- 总输入/输出 token；
- 单候选平均延迟与 frontier 完成时间；
- JSON/schema 解析成功率；
- 候选标签一致率、hard risk 一致率；
- 最终 candidate flow 和真实评分结果；
- fallback 比例。

## 14. 验收标准

1. 候选 ID 映射正确率 100%；
2. 任一候选失败不会覆盖或丢弃其他候选成功结果；
3. hard risk 和 candidate flow 语义与 single 基线一致；
4. batch 模式实际远端调用数和总输入 token 有明确下降；
5. 解析失败率和 fallback 成本没有抵消主要收益；
6. 顺序交换和强弱候选混合测试无系统性串扰；
7. 全局并发峰值仍不超过 20；
8. 若验证公共前缀过短、收益不足或质量漂移，则保持 single，不继续扩大批次。

## 15. 风险与回退

- 模型可能隐式比较候选，因此批次必须小、输出必须逐项独立，并做顺序扰动测试。
- 一个超长候选可能拖累整个 batch，因此需要输入长度阈值并允许单独发送。
- 批量 JSON 更易截断，因此最大批次固定为 3，首轮为 2。
- validator 对业务分流敏感，任何不一致先回退单候选，不能通过放宽解析掩盖错误。
- 本方案的收益可能小于生成阶段；只有端到端指标证明净收益后才默认启用。
