# 树搜索共享前缀与输入复用优化方案

- 文档版本：v1.0
- 制定日期：2026-07-26
- 文档状态：方案已确定，尚未实施
- 适用范围：`multi_operator_branch` 横向多算子搜索，以及按直接父节点展开的纵向算子叠加搜索
- 前置方案：《基于父节点的多算子分支搜索方案》《树搜索效率优化方案》《实验迭代速度优化方案》《纵向算子叠加方案》
- 目标读者：负责题目生成 Prompt、搜索调度、远端模型调用、断点恢复和实验验收的工程师

## 1. 方案摘要

当前树搜索会从同一个已评分父节点领取多个 operator 分支。不同兄弟分支的父题、参考答案、样本画像、过分诊断、历史状态和大部分生成约束相同，差异主要集中在 operator 内容规格和该分支的重试反馈。

模型通过远端 OpenAI-compatible API 调用，项目无法控制模型服务的 KV cache、prefix cache、实例路由或缓存生命周期。因此，本方案不依赖任何模型侧缓存能力，也不把供应商返回的缓存命中作为优化成立条件。

本方案采用两项互补措施：

1. Prompt 规范化与输入压缩：把公共约束、父节点上下文和 operator 任务拆成稳定的内部结构，删除重复序列化、重复说明和无意义空字段，降低每次请求的输入长度；
2. 小批量兄弟 operator 联合生成：将同一直接父节点下的 2 至 3 个首次生成任务合并为一次远端 API 请求，父节点公共上下文只发送一次，并按 operator ID 返回相互独立的结果。

联合生成只作用于题目进化阶段。生成结果拆分后，每个分支继续独立执行：

```text
候选校验
-> 参考答案
-> Rubric 与 Score Prompt
-> 候选模型回答
-> Qwen/GPT Judge
-> 父子分数比较
-> 搜索状态与 Memory 更新
```

本方案不合并参考答案、Rubric、候选回答或 Judge 请求，不减少 trial/repeat，不修改评分聚合，也不共享任何分支业务产物。

## 2. 背景与问题定义

### 2.1 当前搜索形态

当前横向搜索以直接父节点为中心，通过动态有界窗口领取多个 operator 分支。纵向搜索在降分节点成为新 frontier 后，也会在新的直接父节点下建立兄弟 operator 分支。

对任意直接父节点，现有逻辑可以抽象为：

```text
parent P
  +-- operator Oa -> generation request A
  +-- operator Ob -> generation request B
  +-- operator Oc -> generation request C
```

三个请求都会重复携带父节点 P 的大段上下文。即使分支下游可以并行，输入 token 仍按请求数重复计算。

### 2.2 当前 Prompt 布局的复用障碍

当前 operator Prompt 将 operator 身份、目标、题型、内部内容规格放在前部，将样本画像、父题、参考答案、候选答案和 Rubric 放在后部。不同 operator 从很早的位置开始分叉，无法在客户端将父节点公共内容只发送一次。

当前题目生成请求采用单条 user message。远端 API 每次接收一个完整 Prompt，客户端复用字符串对象或缓存模板只会减少很小的本地拼接成本，不会减少发送给远端模型的 token。

### 2.3 优化边界

在不能控制模型侧实现的前提下，只有两类收益是项目可以确定获得的：

- 缩短每个请求实际发送的 Prompt；
- 将多个共享父节点上下文的生成任务放进同一次请求，使公共内容只出现一次。

仅仅把相同文字排列成“前缀”，但仍分别发送多个请求，不构成可确认的远端计算优化。因此本文中的“共享前缀”特指同一次联合生成请求内共享一份父节点输入，不特指 KV cache。

## 3. 目标、非目标与业务不变量

### 3.1 优化目标

本方案的目标是：

1. 降低同一父节点兄弟分支题目生成阶段的总输入 token；
2. 降低题目生成 API 请求数和请求固定开销；
3. 保持每个 operator 的候选、重试、校验、评分和状态归属独立；
4. 同时支持 step 和 stream 搜索调度模式；
5. 同时兼容横向多分支和纵向多层搜索；
6. 中断恢复后不重复调用已经成功并完成检查点发布的 operator；
7. 提供可量化的 token、调用量、延迟、失败和候选质量指标；
8. 能通过配置完整回退到现有单 operator、旧 Prompt 布局。

### 3.2 非目标

本方案明确不做以下事情：

- 不要求、修改或部署远端模型服务的 KV cache、prefix cache；
- 不依赖远端会话、缓存句柄、sticky session 或特定推理框架；
- 不把多个不同父节点放入同一个生成请求；
- 不合并不同深度或不同 frontier 的任务；
- 不合并参考答案生成、Rubric 生成、候选回答或 Judge 评分；
- 不把多个 Judge repeat 合成一个模型输出；
- 不减少现有回答 trial、Judge repeat 或评分模型数量；
- 不复用随机采样答案、Rubric、Judge 结果或 Memory 结果；
- 不修改边界候选定义、父子比较方式或终止条件；
- 不新增综合质量分、近似评分或新的前置否决规则；
- 不通过 bundle 绕过全局请求池、请求预算、评分预算或样本超时。

### 3.3 必须保持的业务不变量

实施后必须继续满足：

- 每个分支使用稳定的 `parent_node_id + operator_id` 身份；
- `candidate_group_id = parent_node_id`，`candidate_id = branch_id`；
- 每个 operator 最多形成一个有效候选分支；
- 同一 operator 的 API 重试、原有校验重试和精确重复重试继续独立计数；
- `not_applicable` 只能来自带非空原因的结构化 operator 结果；
- 兄弟候选仍按确定的 `generation_sequence` 顺序登记题目哈希；
- 每个子节点只与直接父节点比较；
- `child_score_rate < direct_parent_score_rate` 仍是自动边界候选的分数条件；
- `score_increased` 仍是负收益，不进入成功状态，也不写 operator success memory；
- Qwen Judge 的在线决策地位、评分聚合和 GPT 实验轨道不变；
- Memory 的业务准入、内容、写入时机和幂等规则不变；
- 正式产物继续使用 partial、checkpoint、manifest 和原子发布机制；
- bundle 不得领取超出动态分支窗口或剩余边界名额的新分支。

## 4. 备选路径与选型结论

### 4.1 路径一：只做 Prompt 压缩

做法：保持一条分支一次请求，只缩短静态说明、规范动态 JSON、删除安全可省略的空字段。

优点：

- 改动小；
- 分支隔离与重试语义天然保持；
- 不引入联合输出解析和批量失败问题。

缺点：

- 每个兄弟分支仍重复发送完整父节点上下文；
- 只能降低单次请求 token，不能明显减少生成请求数；
- 当公共上下文远长于 operator 规格时，主要重复成本仍然存在。

### 4.2 路径二：Prompt 压缩加小批量兄弟联合生成

做法：先构造一份公共父节点上下文，再附加 2 至 3 个彼此独立的 operator 任务，一次返回多个结果；失败结果按 operator 单独回退。

优点：

- 是客户端可独立控制的真实公共输入复用；
- 可以同时降低输入 token、请求次数和固定网络开销；
- 与当前动态分支窗口天然匹配；
- 结果拆分后仍可复用原有完整闭环。

缺点：

- 需要新的联合输出协议和部分失败处理；
- operator 可能出现交叉污染；
- 单次输出变长，截断和 JSON 解析风险增加；
- 需要改造 step/stream 两种生成调度入口。

### 4.3 路径三：全链路请求合并

做法：继续合并参考答案、Rubric、候选回答或 Judge 请求。

该路径不纳入当前方案。它会引入回答间横向比较、Judge 相关性、repeat 独立性丢失、重试爆炸半径扩大等问题，直接影响现有评测契约。

### 4.4 选型结论

正式方案采用“路径二 + 路径一”：

- 核心收益来自题目生成阶段的小批量兄弟联合生成；
- Prompt 规范化与压缩作为联合生成的基础能力，并逐阶段独立灰度；
- 下游评价阶段保持独立调用，只允许不改变语义的输入整理；
- 远端供应商如果自行提供缓存，视为额外收益，不进入方案依赖和验收标准。

## 5. 目标架构

### 5.1 总体架构

```text
Search Coordinator
    |
    | 领取已受 branch_window 和 remaining_boundary_slots 限制的分支
    v
Evolution Bundle Planner
    |
    | 按 direct parent、model、prompt layout、attempt type 分组
    | 默认 bundle_size=2，最大 3
    v
Shared Prompt Builder
    |
    +-- 公共规则和输出协议                 x 1
    +-- 直接父节点公共上下文               x 1
    +-- operator task Oa                   x 1
    +-- operator task Ob                   x 1
    v
远端题目生成 API
    |
    v
Bundle Response Parser
    |
    +-- Oa generated / not_applicable / invalid
    +-- Ob generated / not_applicable / invalid
    v
按 generation_sequence 顺序登记与拆分
    |
    +-- 成功分支 -> 原有 validation 及下游完整闭环
    +-- 局部失败 -> 仅该 operator 单分支重试
    +-- 重复候选 -> 仅该 operator 执行精确重复重试
```

### 5.2 组件职责

#### Prompt Input Model

负责把现有 Prompt 输入拆成两类内部结构：

- `SharedEvolutionContext`：直接父节点及所有兄弟任务共同使用的内容；
- `OperatorGenerationTask`：某个 operator 独有的内容规格、输出固定值和重试反馈。

该结构仅用于构造请求，不成为新的业务判断层。

#### Evolution Bundle Planner

负责判断哪些已领取分支可以联合，并按稳定顺序切分为小 bundle。它不得自行领取新分支，也不得扩大 `operator_plan`。

#### Shared Prompt Builder

负责生成旧版单 operator Prompt、压缩版单 operator Prompt和联合 Prompt。Prompt 布局必须显式版本化，禁止在同一实验目录无版本混写。

#### Bundle Response Parser

负责把联合 JSON 输出映射回 operator。解析器只做结构校验、operator 身份校验和字段完整性校验，不判断题目质量。

#### Bundle Generation Executor

负责远端调用、bundle 级 API 重试、原始响应检查点、部分结果发布以及失败 operator 的单分支回退。step 和 stream 模式必须复用同一个执行器。

## 6. Prompt 输入模型

### 6.1 公共父节点上下文

`SharedEvolutionContext` 建议包含：

```json
{
  "prompt_layout_version": "operator_bundle_v1",
  "parent_node_id": "sample-001::root",
  "prompt": "父题文本",
  "reference_answer": "父题参考答案",
  "candidate_answer": "父题代表性候选答案",
  "rubric": [],
  "sample_profile": {},
  "overscore_diagnosis": {},
  "evolution_state": {},
  "operator_route_context": {}
}
```

`parent_node_id` 用于请求审计和结果映射，不得要求模型把它写入题面。

公共上下文只能包含对 bundle 内所有任务完全一致的字段。如果某字段会因 operator 而变化，必须移动到 operator task，不能为了追求共享比例错误地提升到公共区。

### 6.2 Operator 独立任务

`OperatorGenerationTask` 建议包含：

```json
{
  "operator_id": "O10_evidence_sufficiency_ladder",
  "generation_sequence": 1,
  "goal": "...",
  "required_question_shape": "...",
  "avoid": "...",
  "content_spec": {},
  "ability_axis": "...",
  "default_evaluation_focus": [],
  "generation_feedback": null
}
```

`generation_feedback` 仅用于单 operator 重试。当前方案不把带不同重复原因或校验拒绝原因的重试任务与首次任务混在同一个 bundle 中。

### 6.3 规范化和压缩规则

允许的输入整理包括：

1. 公共父节点字段只序列化一次；
2. 共享的角色、边界、反脚手架约束和输出协议只写一次；
3. operator task 只携带该 operator 独有内容；
4. JSON 使用稳定字段顺序和统一紧凑分隔符；
5. 只省略语义上明确为可选、且当前值为空的字段；
6. 删除同一 Prompt 内语义完全重复的说明；
7. 使用短而稳定的内部字段名，但不得把内部字段名暴露到生成题面；
8. 保留父题、参考答案、Rubric、画像和诊断中的原始业务信息，不进行摘要改写；
9. 对超长但确有重复的历史状态，只能依据明确白名单投影字段，不能由 LLM 或启发式自动摘要；
10. Prompt 内容变化必须提升 `prompt_layout_version`。

禁止的“压缩”包括：

- 删除 operator 的能力轴、invariants、正负控制或禁止捷径；
- 把父题或参考答案改写成摘要；
- 删除影响生成判断的画像、诊断或历史失败信息；
- 将多个 operator 的内容规格合并成一个模糊任务；
- 为缩短输入而修改输出业务字段含义。

### 6.4 旧 Prompt 兼容

Prompt 构建器应先抽取结构化中间表示，再提供多个 renderer：

```text
legacy_single
compact_single_v1
operator_bundle_v1
```

第一阶段的 `legacy_single` renderer 必须与当前输出逐字节一致，用于证明重构没有暗中修改旧路径。完整回滚使用：

```text
EVOLUTION_PROMPT_LAYOUT=legacy_single
EVOLUTION_OPERATOR_BUNDLE_SIZE=1
```

## 7. 联合生成协议

### 7.1 Bundle 资格

只有同时满足以下条件的任务可以进入同一个 bundle：

- 已由 Search Coordinator 正式领取；
- `parent_node_id` 完全相同；
- 使用相同模型、base URL、temperature 和输出协议；
- 使用相同 `prompt_layout_version`；
- 属于同一直接父节点和同一 frontier 深度；
- 都是该 operator 的首次正常生成尝试；
- 都没有 `validation_reject_reason`、`search_generation_feedback` 或其他独立重试上下文；
- 合并后估算输入和输出不超过配置的安全上限；
- bundle 大小不超过已领取分支数、`branch_window` 和最大 bundle 配置。

以下任务必须使用单分支请求：

- 精确重复后的重新生成；
- 原有校验失败后的重新生成；
- bundle 局部解析失败后的回退；
- 只有一个剩余边界名额时领取的唯一分支；
- 不具备稳定 operator ID 的 legacy 生成任务；
- 合并后可能超过服务输入或输出上限的长上下文任务。

### 7.2 分组键

建议使用：

```text
bundle_group_key =
  model
  + base_url_identity
  + prompt_layout_version
  + parent_node_id
  + node_depth
  + generation_attempt_type
```

API key 不进入持久化业务字段。`base_url_identity` 只保存不可逆摘要或逻辑服务名，不能保存带凭据的 URL。

### 7.3 Bundle 大小

建议默认：

```text
EVOLUTION_OPERATOR_BUNDLE_ENABLED=false
EVOLUTION_OPERATOR_BUNDLE_SIZE=1
EVOLUTION_OPERATOR_BUNDLE_MAX_SIZE=3
```

灰度顺序：

```text
1 -> 2 -> 3
```

不建议第一阶段使用大于 3 的 bundle。过大的联合任务会增加输出截断、operator 串扰、单请求延迟和失败爆炸半径。

实际 bundle 数量为：

```text
effective_bundle_size = min(
    configured_bundle_size,
    claimed_sibling_count,
    remaining_boundary_slots,
    safe_input_capacity,
    safe_output_capacity
)
```

Bundle Planner 只能组合已经领取的分支。它不能因为配置值更大而提前领取新的 operator。

### 7.4 请求格式

联合 Prompt 应先给出一次公共规则和公共上下文，再给出有序任务列表：

```text
角色与全局边界

公共父节点上下文
{shared_context}

独立 operator 任务
[
  {operator task A},
  {operator task B}
]

隔离要求
- 每个 operator 独立生成一道完整题目。
- 不比较、引用、融合或复用其他 operator 的候选。
- 每个结果只能执行对应 operator。
- 一个 operator 不适用不影响其他 operator。

输出协议
返回一个 JSON 对象，results 中每个 operator 恰好一项。
```

### 7.5 响应格式

建议响应：

```json
{
  "results": [
    {
      "operator_id": "O10_evidence_sufficiency_ladder",
      "status": "generated",
      "evolved_prompt": "...",
      "evolution_strategy": "...",
      "ability_axis": "...",
      "target_subclaim": "...",
      "boundary_hypothesis": "...",
      "expected_qwen_failure": "...",
      "expected_evaluation_focus": [],
      "notes_for_reference": "..."
    },
    {
      "operator_id": "O12_conjunctive_necessity",
      "status": "not_applicable",
      "not_applicable_reason": "非空、可审计的原因"
    }
  ]
}
```

解析器不得依赖数组顺序映射 operator，必须按 `operator_id` 显式映射。返回顺序可以与请求顺序不同，但发布和重复登记仍按原 `generation_sequence` 排序。

### 7.6 输出长度控制

联合请求的输出上限不能简单无限乘以 operator 数。应同时设置：

- 单 operator 预期输出预算；
- bundle 输出安全上限；
- 远端服务最大输出上限；
- 输入长度安全阈值；
- 长父题或长 Rubric 的强制单分支回退阈值。

若响应因长度截断、缺少闭合 JSON 或缺少部分 operator，成功项不得重新调用；仅对未能确认成功的 operator 执行单分支回退。所谓“确认成功”必须来自边界完整、字段完整且通过严格校验的独立结果对象，不得用启发式补全一个被截断的 operator 结果。

## 8. 结果拆分、重试与错误处理

### 8.1 拆分顺序

收到联合响应后按以下顺序处理：

1. 保存 bundle 原始响应检查点；
2. 校验顶层 JSON 和 `results` 类型；
3. 校验每个 `operator_id` 唯一且属于本次请求；
4. 分别解析每个 operator 结果；
5. 将成功结果转换为现有 evolved result；
6. 按 `generation_sequence` 排序；
7. 依次执行精确重复登记；
8. 为每个分支发布独立 generation checkpoint；
9. 将成功分支送入原有校验和下游流水线；
10. 对局部失败分支创建单 operator 回退任务。

### 8.2 部分失败隔离

以下问题只影响对应 operator：

- 结果缺失；
- operator ID 重复；
- 返回未知 operator ID；
- `evolved_prompt` 为空；
- 该 operator 的字段结构非法；
- `not_applicable` 缺少原因；
- 该 operator 生成题目触发精确重复；
- 该 operator 未通过原有本地校验。

其他 operator 的已确认成功结果必须保留，不能因同一 bundle 中存在坏项而全部重试。

### 8.3 Bundle 级失败

以下问题属于 bundle 级失败：

- 网络错误、限流、超时或远端 5xx；
- 整体为空响应；
- 顶层内容完全无法解析；
- 响应没有任何可确认的合法 operator 结果。

处理顺序：

```text
沿用现有 API 重试策略重试整个 bundle
-> bundle 重试耗尽
-> 将每个尚未成功的 operator 降级为单分支请求
-> 单分支仍失败时沿用现有 branch_error 语义
```

已经通过检查点确认成功的 operator 永远不进入 bundle 重试或单分支回退。

### 8.4 精确重复处理

联合生成会让多个兄弟候选同时返回，但题目哈希仍按稳定顺序登记：

```text
generation_sequence 1 先登记
generation_sequence 2 再登记
generation_sequence 3 最后登记
```

若后序候选与父题或已登记兄弟题重复：

- 该 operator 使用单分支请求重试一次；
- 重试 Prompt 包含原有重复反馈；
- 其他成功兄弟不受影响；
- 第二次仍重复时标记 `duplicate_exhausted`；
- API 重试和校验重试计数不受影响。

这样可以在改变“首次调用是否联合”的同时，保留现有重复判定顺序和最终状态语义。

### 8.5 原有校验重试

初次 bundle 结果拆分后，每个 operator 独立执行现有本地复杂度/可回答性校验。某个分支需要携带 `validation_reject_reason` 重试时，必须使用单 operator Prompt，不得重新绑定已经成功的兄弟分支。

### 8.6 结构化不适用

每个 operator 可以独立返回 `not_applicable`，但必须包含非空原因。一个 operator 不适用不能导致整个 bundle 被判失败，也不能改变其他 operator 的适用性。

## 9. 搜索调度集成

### 9.1 与动态分支窗口的关系

Search Coordinator 继续先执行：

```text
dispatch_count = min(
    remaining_boundary_slots,
    available_in_flight_slots,
    pending_selected_operator_count
)
```

Bundle Planner 只消费这些已领取记录。联合生成不会改变：

- `selected_operator_ids`；
- operator 顺序；
- `in_flight_branch_ids`；
- 边界目标；
- 未领取 operator 的 pending 状态。

### 9.2 与 step 模式的关系

step 模式在一个 wave 内取得同一父节点的多条 dispatch record 后，先交给统一的 Bundle Generation Executor。执行器完成拆分、顺序去重和 generation checkpoint 后，再把独立分支送入现有候选校验、参考答案、Rubric 和评分阶段。

旧实现按 `generation_sequence` 逐条调用生成；新实现仍按该顺序登记结果，但首次远端调用可以合并。

### 9.3 与 stream 模式的关系

现有 stream pipeline 会按父节点和 `generation_sequence` 串行执行 generation handler。实施联合生成后，generation 阶段需要支持“bundle work item”：

- `submit()` 收到同一父节点的多条新记录时按序分组；
- generation worker 对一个 bundle 只发起一次远端调用；
- 结果拆分后按分支分别写 generation checkpoint；
- 每条分支从 validation 队列继续推进；
- 单分支重试仍走原 generation handler；
- 下游 worker、队列大小和请求池上限保持不变。

step 和 stream 不得分别实现两套 Prompt、解析或回退逻辑。两种模式只负责提供任务和消费拆分结果。

### 9.4 与纵向搜索的关系

纵向模式只能组合同一直接父节点下、同一深度的兄弟 operator：

```text
允许：parent P1 -> [O10, O12]
允许：parent P2 -> [O15, O17]
禁止：P1 的 O10 与 P2 的 O15 合并
禁止：depth 1 与 depth 2 的任务合并
```

同一样本仍按层推进。Bundle 不取消层级屏障，也不改变 frontier 资格、直接父子比较或最大深度控制。

### 9.5 与公平请求池的关系

一个 bundle 是一次真实网络请求，只申请一个 GPT 请求池名额，公平键继续使用样本或直接父节点身份。

由于 bundle 请求比单 operator 请求更长，必须增加输入长度和预计输出长度硬上限，避免一个大 bundle 长时间占用服务容量。第一阶段不引入复杂 token-weighted 请求池；只有真实指标证明长请求破坏公平性时，才单独立项。

## 10. 状态、检查点和恢复

### 10.1 稳定 Bundle ID

建议：

```text
bundle_id = sha256(
  model
  + prompt_layout_version
  + parent_node_id
  + ordered_branch_ids
  + generation_attempt_type
)
```

`ordered_branch_ids` 必须按 `generation_sequence` 排序。相同输入、配置和分支集合应得到相同 `bundle_id`。

### 10.2 检查点层级

建议保存：

1. bundle request manifest：bundle ID、operator 列表、Prompt 摘要、配置摘要；
2. bundle raw response trace：沿用现有压缩 trace sidecar，不放入主业务 JSONL；
3. bundle parse checkpoint：记录每个 operator 的解析状态；
4. per-branch generation checkpoint：保存拆分后的现有分支记录；
5. fallback checkpoint：记录某个 operator 是否已经进入单分支回退。

Bundle 检查点只用于恢复和诊断，分支检查点仍是下游业务事实来源。

### 10.3 恢复规则

恢复时按以下顺序判断：

1. per-branch generation checkpoint 已存在：直接从下一阶段继续；
2. bundle raw response 和 parse checkpoint 完整：重新拆分或补发缺失分支，不重新调用远端；
3. bundle 请求已登记但没有确认响应：按现有未确认真实调用规则处理；
4. fallback checkpoint 已登记：只恢复对应单分支任务；
5. 已成功 operator 不因其他 operator 的恢复再次进入请求。

如果进程在远端完成响应、但本地尚未持久化响应时崩溃，客户端无法证明调用结果，此场景与当前单请求模式相同，不能声称绝对避免重复远端调用。

### 10.4 正式业务字段

不新增临时顶层字段。需要跨阶段保留的 bundle 审计信息放入：

```json
{
  "meta_info": {
    "question_evolution_metadata": {
      "prompt_layout_version": "operator_bundle_v1",
      "generation_request_mode": "bundle",
      "bundle_id": "...",
      "bundle_size": 2,
      "bundle_operator_ids": ["O10", "O12"],
      "bundle_parse_status": "completed",
      "fallback_to_single": false
    }
  }
}
```

`bundle_id` 和 operator 列表是审计字段，不得进入参考答案、Rubric、Score Prompt、候选回答或 Judge 输入。

## 11. 各阶段输入优化策略

### 11.1 题目进化阶段

这是当前方案唯一执行跨分支联合请求的阶段。优化包括：

- 公共父节点上下文只出现一次；
- 公共生成规则只出现一次；
- operator 内容规格保持独立；
- 首次生成可使用 bundle；
- 重复或校验重试回退为单 operator；
- Prompt 布局版本化并保留 legacy renderer。

### 11.2 参考答案阶段

当前输入核心是每个进化后的不同题目，不存在稳定的兄弟公共业务上下文。该阶段不做联合请求，也不缓存或复用随机回答。

只允许清理无意义的包装文本和重复静态说明；任何内容变化都需单独 Prompt A/B，不能搭随 bundle 实施一起上线。

### 11.3 Rubric 阶段

不同分支的问题和参考答案不同。Rubric 直接影响评分，不在第一阶段修改其业务 Prompt，也不联合多个分支生成 Rubric。

后续如需压缩，只能独立版本化、独立灰度，并证明 Rubric 项数、权重、负向约束、可判定性和评分分布没有不可接受变化。

### 11.4 候选回答阶段

不同兄弟分支题目不同。同题多 trial 的独立采样是评测协议的一部分，禁止结果复用和联合输出。

### 11.5 Judge 阶段

评分 Prompt、answer trial 和 Judge repeat 保持原样。虽然它们包含大量重复 Rubric，但将多个回答或 repeat 放入一个请求会引入相关性和横向比较偏差，因此不属于本方案。

如果未来只调整单请求内的字段顺序或静态文字，必须作为独立评分协议变更评估，不能用“输入压缩”名义绕过评分一致性验收。

## 12. 配置设计

建议新增：

```text
EVOLUTION_PROMPT_LAYOUT=legacy_single
EVOLUTION_PROMPT_COMPACTION=false
EVOLUTION_OPERATOR_BUNDLE_ENABLED=false
EVOLUTION_OPERATOR_BUNDLE_SIZE=1
EVOLUTION_OPERATOR_BUNDLE_MAX_SIZE=3
EVOLUTION_BUNDLE_FALLBACK_TO_SINGLE=true
EVOLUTION_BUNDLE_MAX_INPUT_CHARS=0
EVOLUTION_BUNDLE_MAX_OUTPUT_TOKENS=32768
```

语义：

- `EVOLUTION_PROMPT_LAYOUT`：选择旧版、压缩单任务或联合 Prompt renderer；
- `EVOLUTION_PROMPT_COMPACTION`：启用经过验收的空字段和重复说明压缩；
- `EVOLUTION_OPERATOR_BUNDLE_ENABLED`：总开关；
- `EVOLUTION_OPERATOR_BUNDLE_SIZE`：目标 bundle 大小；
- `EVOLUTION_OPERATOR_BUNDLE_MAX_SIZE`：代码允许的硬上限，首版不超过 3；
- `EVOLUTION_BUNDLE_FALLBACK_TO_SINGLE`：局部或整体失败时是否回退单分支；
- `EVOLUTION_BUNDLE_MAX_INPUT_CHARS`：远端 tokenizer 不可得时的本地安全阈值，0 表示使用内置保守值；
- `EVOLUTION_BUNDLE_MAX_OUTPUT_TOKENS`：联合响应上限，不得超过服务端能力。

CLI 应提供对应参数，并由 `run_loop.sh`、`run_loop.ps1` 透传。运行摘要和 manifest 必须记录实际值。

配置约束：

```text
bundle_enabled=false -> bundle_size 强制视为 1
bundle_size < 1 -> 启动失败
bundle_size > bundle_max_size -> 启动失败
bundle_max_size > 3 -> 首版启动失败
bundle Prompt 与 legacy layout 不兼容时 -> 启动失败并给出明确错误
```

## 13. 性能模型与指标

### 13.1 理论输入收益

设：

- `C`：公共父节点与公共规则 token；
- `Oi`：第 i 个 operator 独有 token；
- `E`：联合输出协议额外 token；
- `n`：bundle 中 operator 数。

单分支请求总输入约为：

```text
single_total = n * C + sum(Oi)
```

联合请求总输入约为：

```text
bundle_total = C + sum(Oi) + E
```

理论节省：

```text
saved_input = (n - 1) * C - E
```

只有当公共上下文足够长且 `saved_input > 0` 时才值得合并。Bundle Planner 应允许基于长度估算拒绝低收益合并。

### 13.2 请求级指标

每个题目生成请求至少记录：

- `generation_request_mode = single | bundle | single_fallback`；
- `bundle_id`、bundle 大小和 operator 数；
- 输入字符数；
- API 返回的 `prompt_tokens`、`completion_tokens`、`total_tokens`，如存在；
- 本地估算 token，仅在 API usage 缺失时使用并标记为 estimated；
- 请求排队、首响应和总耗时；
- API 重试次数；
- 响应是否截断；
- 合法结果数、局部失败数和 fallback 数。

不得在性能事件中写入完整 Prompt、参考答案、模型回答、API key 或私有 base URL。

### 13.3 搜索级指标

每轮至少汇总：

```text
eligible_operator_tasks
bundled_operator_tasks
bundle_coverage_rate
generation_api_calls_saved
generation_prompt_tokens_single_baseline
generation_prompt_tokens_actual
generation_prompt_token_reduction_rate
bundle_parse_success_rate
partial_failure_rate
single_fallback_rate
p50 / p95 generation latency per operator
p50 / p95 generation latency per parent
validation_pass_rate
duplicate_rate
not_applicable_rate
boundary_candidates / 100 scored branches
```

API 未返回 token usage 时，token 降幅报告必须明确标记为估算值；不能把字符数直接写成精确 token。

### 13.4 收益边界

本方案只直接减少题目生成阶段的输入和请求。完整分支仍包含参考答案、Rubric、多个回答 trial 和多次 Judge，因此端到端总 token 降幅会小于生成阶段降幅。

性能报告必须同时给出“题目生成阶段收益”和“完整搜索收益”，不得只报告局部高比例并暗示整个流水线获得同等降幅。

## 14. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| operator 交叉污染 | 候选融合其他 operator，归因失真 | 明确隔离指令、按 ID 独立输出、bundle 最大 2 起步、专项内容测试 |
| 输出截断 | 后部 operator 丢失或 JSON 不完整 | 最大 bundle 3、长度预检、部分成功保留、缺失项单分支回退 |
| 单请求失败爆炸半径扩大 | 多个 operator 同时延迟 | bundle 级有限重试、之后拆成单请求、已成功项不重试 |
| Prompt 压缩改变生成分布 | 候选质量或难度收益下降 | layout 版本化、legacy 对照、逐阶段灰度、候选质量非劣验收 |
| 兄弟重复竞态 | 相同题被同时接受 | 结果按 generation_sequence 原子登记，后序重复单独重试 |
| 恢复时重复调用 | 成本增加或状态重复 | raw response 先落盘、per-branch checkpoint、稳定 bundle ID |
| 大请求破坏公平性 | 其他样本尾延迟增加 | bundle 大小与输入长度硬上限，保留公平请求池，监控 p95 |
| 远端 usage 缺失 | token 收益无法精确计算 | 同时报字符数和标记明确的本地估算，真实 usage 优先 |
| 纵向模式跨父节点误合并 | 路径和评分基线污染 | 分组键强制包含 direct parent 和 depth |
| 回滚后实验混写 | 结果难以复现 | Prompt/layout/config 进入 manifest，不同配置不得共用实验目录 |

## 15. 实施阶段

### 阶段 A：基线与可观测性

实施内容：

- 为题目生成调用补充 input chars、API usage、耗时、重试和模型标识事件；
- 统计同一父节点下公共输入与 operator 独有输入长度；
- 建立现有单 operator 请求数、token 和候选质量基线；
- 保存固定输入的 legacy Prompt golden fixtures；
- 不修改任何实际 Prompt 或模型调用方式。

退出条件：能够从性能事件复原每个父节点的生成调用数和输入量，且不记录敏感内容。

### 阶段 B：Prompt 中间表示与旧路径等价

实施内容：

- 抽取 `SharedEvolutionContext` 和 `OperatorGenerationTask`；
- 增加 Prompt renderer 接口；
- 使用 `legacy_single` renderer 复现当前 Prompt；
- 增加稳定序列化和 Prompt hash；
- 保持 bundle 关闭。

退出条件：代表性 operator、空字段、中文文本和复杂 Rubric fixture 的 legacy Prompt 与改造前逐字节一致；现有测试全部通过。

### 阶段 C：压缩版单 operator Prompt

实施内容：

- 新增 `compact_single_v1`；
- 删除经过清单确认的重复说明和安全空字段；
- 保持一个 operator 一次请求；
- 对候选生成质量做 legacy/compact A/B；
- 不修改 Rubric、回答和 Judge Prompt。

退出条件：输入 token 明显下降，结构解析率、校验通过率、重复率和边界产出没有超过验收阈值的退化。

### 阶段 D：Bundle 大小 2，step 模式灰度

实施内容：

- 增加 Bundle Planner、联合 Prompt 和响应解析器；
- 只合并同一直接父节点的首次生成任务；
- 增加局部失败保留和单分支回退；
- 保持按 generation_sequence 登记；
- 在横向 step 模式启用 bundle size 2；
- 其他模式保持单请求。

退出条件：固定响应下最终分支投影与单请求模式一致；真实 A/B 达到 token 和质量验收标准。

### 阶段 E：stream 与纵向模式接入

实施内容：

- generation queue 支持 bundle work item；
- 拆分后按分支写 checkpoint 并进入 validation；
- 纵向模式只组合同一 frontier 父节点和同一深度任务；
- 增加 step/stream/纵向恢复测试；
- bundle size 仍保持 2。

退出条件：三种模式的分支身份、父子比较、重复登记、终止原因和恢复结果均正确。

### 阶段 F：Bundle 大小 3 与自适应降级

实施内容：

- 仅在 size 2 已稳定后灰度 size 3；
- 根据输入长度、输出截断、解析失败和 fallback 历史选择 1、2 或 3；
- 自适应逻辑只缩小 bundle，不改变 operator 顺序或成员；
- 保留固定 size 模式用于可复现实验。

退出条件：size 3 相对 size 2 有可测收益，且没有造成质量、失败率或 p95 延迟不可接受退化；否则默认保持 size 2。

### 阶段 G：其他阶段的保守输入整理

实施内容：

- 分别评估参考答案和 Rubric 阶段的重复静态说明；
- 每个阶段独立版本化、独立 A/B、独立回滚；
- Judge Prompt 和 trial/repeat 协议保持冻结；
- 不引入跨回答或跨评分联合请求。

该阶段不是题目生成 bundle 上线的前置条件，不应与阶段 D/E 同批发布。

建议按现有架构增量修改：

### `prompts/operators/base.py`

- 未知 operator 继续立即报错。

### `question_evolution.py`

### 新增 `evolution_bundle.py`

- 封装 Bundle Planner、稳定 bundle ID、联合 Prompt 调用、响应拆分和局部回退计划；

- 不改变 `claim_branches` 的领取和窗口计算；
- dispatch record 继续携带稳定 `generation_sequence`；
- 可增加只读的 bundle eligibility 投影，但不能由此领取额外分支。

### `multi_operator_search.py`

- 在 step 和 stream 的 generation 入口统一调用 Bundle Generation Executor；
- step 模式按 parent 和 sequence 分组；
- stream 模式提交 bundle work item，拆分后继续独立流水线；
- 保持现有公平请求池和下游阶段调用；
- 性能汇总增加 bundle 指标。

### `branch_pipeline.py`

- generation 阶段支持一个 work item 对应多条已领取分支；
- 每条拆分结果分别写 generation checkpoint；
- 保持 validation 以后每个 queue item 对应一条分支；
- 单分支重试继续使用原有串行顺序；
- compact/full checkpoint 保留策略继续生效。

### `vertical_operator_search.py`

- 复用同一个 Bundle Planner 和 Executor；
- 分组键加入直接父节点和深度；
- 不跨 frontier、不跨深度合并；
- 不改变 operator stack、frontier 和直接父子比较。

### `run_loop.sh` 与 `run_loop.ps1`

- 读取并显示新增配置；
- 将配置传入横向和纵向搜索入口；
- 写入运行摘要和 manifest；
- 默认保持关闭和 size 1。

### Schema 与文档

- 仅为 `meta_info.question_evolution_metadata` 增加可选 bundle 审计字段；
- 历史记录缺失这些字段时按 single/legacy 处理；
- 不要求迁移旧 JSONL；
- 更新 schema README、运行配置说明和性能事件字段说明。

## 17. 测试计划

### 17.1 Prompt 单元测试

必须覆盖：

1. `legacy_single` 与当前 Prompt 逐字节一致；
2. 公共父节点在 bundle Prompt 中只出现一次；
3. 每个 operator ID 和内容规格恰好出现一次；
4. operator 输出固定字段与对应 spec 一致；
5. 输入 dict 顺序变化不影响规范化 Prompt hash；
6. 仅允许白名单空字段被省略；
7. 父题、参考答案、Rubric 和画像的业务文本不被摘要或改写；
8. Prompt layout 版本变化会改变 manifest 配置摘要。

### 17.2 Bundle Planner 测试

必须覆盖：

1. 只组合相同 `parent_node_id` 的分支；
2. 不跨深度或 frontier 合并；
3. 不组合不同模型、Prompt 版本或参数；
4. 不组合重复重试和校验重试；
5. bundle 大小不超过配置、窗口和剩余边界名额；
6. 长输入自动降级为更小 bundle 或 single；
7. operator 顺序与 `generation_sequence` 一致；
8. Planner 不创建或领取新的分支。

### 17.3 响应解析测试

必须覆盖：

1. 正常多 operator 响应正确拆分；
2. 返回顺序变化仍按 ID 映射；
3. 缺失一个 operator 时保留其他成功项；
4. 重复 ID、未知 ID 和空题目只影响对应项；
5. `not_applicable` 必须带非空原因；
6. 截断 JSON 中只有边界和字段均完整的独立结果可以保留，禁止补全残缺结果；
7. 完全不可解析时触发 bundle 级重试；
8. 已成功 operator 不进入 fallback。

### 17.4 搜索与重试测试

必须覆盖：

1. 两个兄弟生成相同题目时按 sequence 确定接受者；
2. 后序重复 operator 单独重试一次；
3. 校验失败只重试对应 operator；
4. API、校验和重复计数器保持独立；
5. hard risk 和原有 validation 语义不变；
6. `score_increased` 仍不进入成功终止或 operator success memory；
7. boundary target 只限制新领取分支，不丢弃已在途结果；
8. bundle 失败不阻塞同一样本后续 operator 或其他样本。

### 17.5 step、stream 与纵向集成测试

使用固定模拟响应，对同一输入比较：

```text
legacy single + step
compact single + step
bundle size 2 + step
bundle size 2 + stream
bundle size 2 + vertical
```

比较内容：

- operator 尝试集合；
- branch/node/candidate ID；
- 候选文本映射；
- 精确重复处理；
- validation 结果；
- 回答 trial 和 Judge repeat 数量；
- Qwen 聚合分数；
- 父子分数关系；
- 分支终态、frontier 和终止原因；
- Memory 内容和幂等键；
- 正式产物与 manifest 完整性。

允许差异仅限于 Prompt layout、bundle 审计字段、远端请求次数、运行时间、trace ID 和性能指标。

### 17.6 故障恢复测试

分别在以下位置中断：

- bundle 已领取但尚未调用；
- 请求成功但 raw response 尚未落盘；
- raw response 已落盘但尚未拆分；
- 部分 operator checkpoint 已发布；
- fallback 已创建但尚未调用；
- 一个 bundle 分支进入 validation，另一个仍在 fallback；
- stream pipeline 已拆分但尚未进入下游；
- 纵向某个 frontier 的部分兄弟已完成。

恢复后必须证明：

- 已确认成功分支不重复调用；
- 未完成 operator 不丢失；
- 重复题哈希不重复登记；
- 边界计数和 Memory 不重复增加；
- 最终 manifest 可校验；
- 业务投影与未中断运行一致。

### 17.7 全量回归

运行：

```bash
pytest -q
```

新增行为还应单独运行 Prompt、search coordinator、branch pipeline、multi-operator runner、vertical runner 和评分不变量相关的小型测试文件，便于定位失败。

## 18. 真实 A/B 实验与验收标准

### 18.1 实验分组

在相同输入、模型、temperature、operator 列表、分支窗口、请求池、trial/repeat 和评分配置下比较：

- A：`legacy_single`，bundle size 1；
- B：`compact_single_v1`，bundle size 1；
- C：`operator_bundle_v1`，bundle size 2；
- D：仅在 C 稳定后增加 bundle size 3。

每组至少覆盖 30 个具有两个以上候选 operator 的直接父节点，并至少重复三次性能运行。模型具有随机性时，不要求候选文本逐字一致，应比较结构、质量和边界统计。

### 18.2 正确性硬门槛

任何候选方案必须满足：

- 没有新增或遗漏已领取 operator；
- 没有跨父节点或跨深度结果污染；
- branch/node/candidate ID 映射正确率 100%；
- trial/repeat 数量和 Judge 聚合规则完全不变；
- boundary target 不溢出；
- 已成功 operator 恢复时不重复执行；
- Memory 准入、内容和幂等行为不变；
- 正式产物和 manifest 全部通过校验。

### 18.3 第一阶段性能目标

对于符合 bundle 条件的题目生成任务，建议使用以下验收目标：

- bundle size 2 相对两个 single 请求，题目生成输入 token 中位数下降至少 25%；
- 题目生成真实 API 调用数下降至少 35%；
- 单个父节点完成首批题目生成的墙钟时间中位数下降至少 15%；
- bundle 顶层解析成功率不低于 98%；
- single fallback 率不高于 10%；
- 因输出截断造成的 fallback 率不高于 2%。

这些数字用于灰度退出判断，不构成未经实测的性能承诺。若远端 API 不返回 token usage，25% token 指标只能作为估算观察项，调用数、字符数和墙钟时间仍作为硬证据。

### 18.4 质量非劣目标

相对 legacy single 基线：

- 本地与正式校验通过率下降不超过 5 个百分点；
- 精确重复率上升不超过 5 个百分点；
- `not_applicable` 比例不得出现无法由 operator 适用性解释的系统性突增；
- `boundary_candidates / 100 scored branches` 相对下降不超过 10%；
- 人工抽检不得发现系统性 operator 融合、引用兄弟结果或题面暴露内部控制字段；
- Rubric、回答和评分统计不得因生成请求合并之外的协议变化产生差异。

若性能达标但质量非劣目标未通过，应回退 bundle 或修改联合 Prompt，不得仅以 token 节省为由上线。

### 18.5 Bundle size 3 准入

只有同时满足以下条件才进入 size 3：

- size 2 已完成至少三次稳定真实运行；
- parse、fallback、截断和质量指标均通过；
- size 3 相对 size 2 仍有额外 token 或请求收益；
- p95 父节点生成延迟没有显著恶化；
- 人工抽检未发现更强的 operator 串扰。

不满足时，正式默认保持 size 2。

## 19. 灰度发布与回滚

### 19.1 发布顺序

```text
阶段 A 指标基线
-> 阶段 B legacy renderer 等价重构
-> compact single 离线与小流量 A/B
-> 横向 step + bundle size 2
-> 横向 stream + bundle size 2
-> 纵向搜索 + bundle size 2
-> 视收益决定是否启用 size 3
```

每次灰度只改变一个主要变量。不得同时修改 operator 内容、Rubric Prompt、Judge Prompt、分支窗口和 bundle 大小，否则实验结果无法归因。

### 19.2 回滚层级

从轻到重：

1. 将 bundle size 从 3 降为 2；
2. 将 bundle size 从 2 降为 1，保留 compact Prompt；
3. 关闭 Prompt compaction，切回 `legacy_single`；
4. 保持现有搜索模式、分支状态和下游流程不变。

回滚不得删除已经发布的分支产物。同一实验目录若已经使用不同 Prompt layout 或 bundle 配置，应拒绝继续混写，必须从有效 checkpoint 使用相同配置恢复，或创建新实验目录。

### 19.3 自动降级条件

单次运行中出现以下情况时，可以只对后续未领取或未调用任务自动降级：

- 连续 bundle 顶层解析失败；
- fallback 率超过配置阈值；
- 输出截断率异常；
- 远端返回与长请求相关的明确错误；
- p95 生成延迟持续恶化；
- bundle Prompt 超过安全输入阈值。

自动降级只允许 `3 -> 2 -> 1`，不能自动扩大 bundle。降级事件必须写入性能日志和运行摘要。

## 20. 安全与审计

- 不在日志、metrics、manifest 或错误消息中输出 API key；
- base URL 只记录逻辑服务名或摘要；
- 完整 Prompt 和模型原始响应继续进入受控 trace sidecar，不进入常规日志；
- bundle raw response 只保存一次，各分支保存 trace 引用，避免重复扩大产物；
- 错误日志只保留 operator ID、bundle ID、状态和截断后的非敏感原因；
- 任何新增配置和 Prompt layout 都进入 manifest 配置摘要；
- 不把 operator 规格、bundle ID 或兄弟候选信息传入下游回答和评分阶段；
- 不提交本地 `config.py`、API key 或真实私有请求样本。

- Prompt 中间表示、legacy renderer、compact renderer 和 bundle renderer 已完成；
- step、stream 和启用中的纵向搜索模式都使用同一 Bundle Executor；
- bundle 只作用于同一直接父节点首次题目生成；

- checkpoint、恢复、trace、manifest 和正式产物可审计；
- 默认配置仍可安全回退到 legacy single；
- 新增小型 pytest 和全量 `pytest -q` 通过；
- 固定响应等价性测试通过；
- 至少 30 个合格父节点、至少三次真实性能运行完成；
- 输入 token、调用数、延迟、fallback、校验和边界产出报告齐全；
- 正确性硬门槛和质量非劣目标全部通过；
- 运行文档、配置说明、schema 说明和回滚方法已同步更新。

如果只有代码和模拟测试完成、但真实 A/B 尚未完成，文档状态只能写“代码已接入，真实验收待完成”，不能标记为完整实施。

## 23. 最终原则

本方案优化的是“同一直接父节点的输入如何更少地发送给远端模型”，不是模型推理服务本身，也不是搜索业务判别。

必须始终坚持：

```text
共享父节点输入，不共享分支结果；
联合首次生成，不联合独立评价；
减少重复 token，不减少证据链；
局部失败局部回退，不让一个坏项污染整个 bundle；
保持父子比较、评分协议和 Memory 语义不变；
先用 size 2 证明收益，再考虑 size 3；
无法证明质量非劣时，优先回退而不是追求表面吞吐。
```

只有保持这些边界，输入复用才能成为树搜索的效率优化，而不是新的题目生成或评分协议。
